## 发现（按严重度排序）

### F1 · 🟡 M4「TUI 不认识 `Usage`」的前提是错的

**设计原文**（`design.md:35`）：

> `ys-tui-coding` **不依赖 `ys-runtime`** ⇒ TUI 不认识 `Usage`，只能由 app 推**已投影的结论**。

**实测**：`crates/ys-tui-coding/Cargo.toml` 直接依赖 `ys-core`：

```toml
ys-core = { path = "../ys-core" }
```

且已在多处使用：`transcript.rs:8`（`Message, Role, StopReason, ToolCallId`）、
`draw.rs:33`（`StopReason`）、`commands.rs:20`（`ContentBlock, EffortLevel, Message, Role`）。
`Usage` 就在 `ys_core` 里。

**问题**：硬约束「不依赖 `ys-runtime`」是真的（防 TUI 认识 `Agent`），但它**推不出**
「TUI 不认识 `Usage`」。设计把两条不同的边界混成一条，并用它论证「判别必须在 app 完成」。

**影响**：结论（判别在 app 侧）**仍然正确**，但理由错了。理由错会让后来的维护者以为
「TUI 加个 `ys-core` 依赖就能自己算」——而它本来就有那个依赖 —— 从而绕过这条纪律。

**建议（易修复）**：`design.md:35` 改成：

> TUI **不依赖 `ys-runtime`**（编译器强制，防它认识 `Agent`），但**依赖 `ys-core`**,
> 技术上可以读 `Usage`。判别仍留在 app 侧，理由是 ①UI 线程无 runtime 上下文
> ②provider 语义的解释权应集中在 `ys-core`，不撒到渲染层。

### F2 · 🟡 派生 `miss` 的聚合语义有未写明的前提（当前数据满足）

`design.md` §3 定义：

```rust
/// `miss = input_tokens.saturating_sub(hit)` —— 可推导，故不存储。
pub fn cache_split(&self) -> Option<(u32, u32)>;
```

§4.3 用「删掉落地的 `miss`」把 `Usage` 从 32 B 压回 24 B。**内存结论成立**，但需追问：
`miss = input − hit` 在**跨轮聚合**后还成立吗？

#### 构造性反例

一个回合 3 轮：1 轮报 `input=1000, hit=900`，2 轮**有 input 但无缓存读数**（`input=1000, hit=None`）：

| 量 | derive 口径 | 正确值 |
|---|---|---|
| `miss` | **2100** | **100** |
| 命中率 | **30.0%** | **90.0%** |

即：若存在「有 prompt 但缓存字段缺席」的轮次，`derive` 会把它们的**整个 input**
当成未命中，命中率被严重低估。

#### 实测：当前数据**不触发**

用真实日志验证这个前提是否满足：

| 检查项 | 实测值 |
|---|---|
| `round_usage` 记录总数 | 4,915 |
| `cache_read` 字段缺失 | **0**（字段总是存在，无值时写 `0`） |
| `input == 0`（整个 usage 缺失） | 704（14.3%） |
| 其中 `hit > 0`（即有 hit 却无 input，会触发 F2 的形态） | **0** |
| 同时含「有读数轮」与「无读数轮」的会话 | 3 个（如 `1793013602`：68/182 轮 `input==0`） |
| 这 3 个会话里 derive 与正确口径的差异 | **0**（两种算法给出 95.98%，完全一致） |

原因：缺报的轮次是 `(0, 0)` —— **input 与 hit 同时为 0**。`(0,0)` 相加不改变
`input − hit`，所以 derive 与正确口径恒等。

**结论：F2 是「前提依赖」缺陷，不是当前缺陷。** 它取决于一条 provider 未承诺的性质：
*「缓存读数缺席时，`input_tokens` 也一定为 0」*。真实数据 4,915 条全部满足，但：
- 这是**观察归纳**，不是契约；换 provider / 换对话形态（如 provider 回 prompt 但不回缓存明细）
  就可能不成立；
- `context.md` 自己列过 `input > 0 且缓存两字段为 0` 是「provider 异常上报」形态；
- `cache_tokens()` 的归一逻辑里，OpenAI 形状还能从 `prompt_tokens_details` 推出 miss，
  而 DeepSeek 形状直接用两栏 —— 两条路径对「缺席」的表达不同。

**建议（需讨论）**：不必现在改接口，但必须**把前提写进 doc 并加一条守卫**：

1. `cache_split()` 的 doc 加一句：「本函数**假设** provider 在缓存明细缺席时 `input_tokens`
   也为 0；若该假设破裂，聚合后的 `miss` 会偏大、命中率会偏小。」
2. 在适配器归一处置一个**断言或 debug 日志**：`hit > 0 && input == 0` 或
   `hit.is_none() && input > 0` 时记一条异常（当前 0 次，将来能发现破裂）。
3. 跨轮用例补一条：`(1000, Some(900))` + `(1000, None)` ⇒ 断言当前行为（命中率 30%），
   **把已知错误行为钉住**，而不是让它静默漂移。

> 这条是本设计中**唯一需要新增文档承诺**的点。它不改 `Usage` 大小，也不改接口签名。

### F3 · 🟡 压缩失败漏账 + doc 措辞会误导

`design.md` R5 / ADR D5 已如实记录缺口。问题不在「没修」，而在措辞：
`RunResult.compaction_usage` 的 doc 写「本回合压缩消耗」，失败时它是零值 ——
读者会理解成「没压过」，实际可能是「压了但失败、已经烧了钱」。

**建议（易修复）**：doc 改成「本回合**成功**的压缩消耗；失败路径不计（已知缺口）」。

### F4 · 🟡 `RunFinished.usage ≠ 总花费` 的三角关系只写在 Rust doc

`usage` / `compaction_usage` / `两者之和` 的关系写在 `RunResult` 的 doc 里，
但 `--json` 的消费者**看不到 Rust doc**。他们读 `RunFinished.usage` 当账单 —— 正是本需求要修的错。

**建议（易修复）**：`RunFinished` 的 JSON 不变（逐字节承诺），但在
`docs/architecture.md` 的输出三分节补一句「`usage` 只含主对话轮；压缩见
`RoundUsage{purpose:"compaction"}`，两者相加才是本回合总花费」。

### F5 · 🟢 分期依赖表述自相矛盾

`design.md` §8.1 一处说「③ 依赖前两者的数据」，另一处说「② 与①无依赖，可先做」。实际：
②（归因）不依赖①，③（可见）依赖①②的产物。建议统一为「①② 可并行，③ 最后」。

## 改进建议

### 易修复（低风险快速改进）

1. `design.md:35` 的边界理由改准确（F1）——它现在以「硬约束」的口气写了一条错推论。
2. `RunResult.compaction_usage` 的 doc 加「成功」限定（F3）。
3. `architecture.md` 补「本回合总花费怎么看」（F4）。
4. 统一 §8.1 分期表述（F5）。

### 需讨论（需要团队决策）

5. **F2 是否现在就加固**。两个立场：
   - **不动接口**：前提已被 4,915 条实测满足，加 doc + 探针 + 钉行为用例即可；
   - **`miss` 回退 `Option<u32>`**：语义对称、不依赖 provider 性质，但 `Usage` 涨到 32 B
     （每条 `RoundUsage` 事件、每份 `run_end` 都跟着涨）。

   本报告倾向前者：这不是当前缺陷，而是一条应被**显式化**的隐含假设。
   把它写清楚比付 8 B/事件的代价更划算。

6. **F2 的测试补强**：现有 6 条变异测试全部是**单轮**。应加一条跨轮用例
   （`(1000, Some(900))` + `(1000, None)`），把聚合行为钉住 ——
   无论将来选哪个方向，这条用例都是回归防线。

### 架构级（影响面大）

7. **`Usage` 同时是「存储类型」与「可聚合类型」，两者的信息需求不同**。
   存储只需 provider 原样读数；**聚合后却不足以重建命中率**（需知道哪些轮缺席）。
   若将来接入更多可选桶（`cache_write`、音频、图像），这个矛盾会复现。
   建议在实现 P0-1 时明确写下这句，并考虑把「命中率的聚合上下文」
   放在 `TurnStats` 而非 `Usage` ——本设计其实已经这么做了，只是没说明为什么必须如此。

## 总体评价

**整体健康度：🟢 良好，可进入实现；有 1 处文档承诺需补，2 处理由/措辞需修正。**

做对的部分：

- **实证驱动**：14.3% 的调用整个 usage 缺失、19.4% 的会话全程无读数、21.4% 的会话
  `meta.input_tokens` 已丢 —— 这三组数据把「未上报」从边缘情况变成主要场景，
  直接支撑 `Option` 化决策，也让「不做价格层」的范围裁剪有据。
- **内存结论可验证**：24 B / 32 B 是 `size_of` 实测，并主动证伪了候选方案的 40 B。
  这是三个候选方案里唯一一个把「性能论据」当成可证伪命题来处理的。
- **诚实度高**：R1–R8、D5 都写了「不修」与代价。ADR 甚至记录了与业界相反选择的换算公式。
- **P0-1 裁决理由扎实**：A 会让同一 prompt 报出两个数（23848 → 258 vs 23848），
  这一条独立成立，不依赖「业界怎么做」。
- **归因机制克制**：三个候选收敛于 `RunResult` 兄弟字段，没有为未确认的第二用途
  建账本（~640 行被否），而第二个用途只需再加一个字段（~6 行）。

**审核过程中被推翻的一次判断**（记录在此，因为它说明为什么需要实测）：

我最初认为 F2 是「**几乎必然触发**的严重缺陷」，理由是把 14.3% 的 `input==0` 当成
「有 prompt 但不报缓存」。回查后发现那 704 条是 `(input=0, hit=0)` ——
**整个 usage 缺失**，`(0,0)` 相加不改变 derive 结果。3 个「混合上报」会话逐一验算，
两种口径给出完全相同的 95.98%。**F2 从 P0 降到 P1。**

**推荐下一步**：

1. 按「易修复」4 条改文档（半小时内，无代码风险）；
2. 补 F2 的跨轮用例（钉住当前行为）+ 适配器异常探针（发现前提破裂）；
3. 然后按 ①② → ③ 进入实现。

实现可以开始。**唯一在 P0-1 定稿前需确认的是 F2 的处理立场**——
「写进 doc + 探针」还是「`miss` 回退 `Option`」，因为后者会改接口签名。
