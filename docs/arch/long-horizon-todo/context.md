# 长程任务的闭环（todo × subagent）— 架构上下文

> 产出：`/arch-explore`（2026-09-23）。基线：`master` @ `aba3ece`（工作区干净）。证据均带 `文件:行号`。
> **需求原话**：「重新考虑 todo 的设计，我们需要提供**长程任务的成功率**和**闭环能力**。它可以和 subagent
> 结合起来，比如**主 agent 按照 todo 派发 subagent** 等等、**agent 按照 todo 逐个完成**等等」。
>
> 前置产物（都在本仓，**已定案**）：
> - [`../hooks-and-plugins/`](../hooks-and-plugins/) —— todo 作为 **plugin 装配缝的试金石**（ADR-0021）
> - [`../subagent/`](../subagent/) —— subagent 派发（ADR-0022）
> - [`../../design-plans/2026-09-15-follow-up.md`](../../design-plans/2026-09-15-follow-up.md) —— 追问（**设计完，未实现**）
>
> **结论先行：这不是 v1 的增量，是换了问题类别。** v1 问「缝在哪」（**能力装配**）；本文问「谁推进、状态活多久」
> （**控制流 + 状态**）。而 v1 给 todo 定的状态位置 —— **对话上下文**（ADR-0021 决策 5）—— **恰好是长程任务里最先消失的地方**。

---

## 1. 需求变更的含义（必须先对齐）

| | v1（`hooks-and-plugins`，已定案） | v2（本文） |
|---|---|---|
| 要解决的问题 | 第三方怎样**不加改核心**地加一个功能 | 长程任务怎样**不烂尾** |
| todo 的角色 | **试金石**（拿它验证装配缝） | **主体**（要真正提升成功率） |
| 成功的判据 | 「6 处连锁点 → 1 处登记」 | 「成功率 + 闭环」 |
| 状态住哪 | **对话上下文**（ADR-0021 决策 5：真值 = 最后一次调用的 `arguments`） | **待定** —— 见 §3.3，v1 的答案正是软肋 |

> **两件事仍正交**：v1 的装配缝（`ToolPlugin`）与 v2 的闭环**不冲突也不互相满足**。
> v1 的缝做完，todo 依然是个「写得漂亮但会被压缩吃掉」的工具。

---

## 2. 关键输入：长程成功率靠什么（本仓之外）

这决定了「该建什么」，故放在现状之前。

| 证据 | 结论 |
|---|---|
| **Plan-and-Act**（Erdogan et al., 2025） | 规划/执行分离后 WebArena-Lite **9.85% → 57.58%**；**动态重规划**一项比 ReAct **+34 pp** |
| **Goal2Skill**（RMBench） | **32.4% vs 9.8%** 基线；消融：**结构化 memory** 贡献最大，**显式验证 + 反思**次之 |
| 综述 [Long-Horizon Agent Planning](https://www.emergentmind.com/topics/long-horizon-agent-planning) | 分层规划 + 记忆增强的架构普遍抬高成功率 |

**归纳出三处增益来源**，且**三处没有一处是「给模型一个 todo 工具」**：

1. **规划与执行分离** —— 规划者往往是**独立的**（甚至专门训练的），不是同一个模型给自己写便签；
2. **状态的持久化与结构化** —— 住 memory，**不住对话上下文**；
3. **验证 / 反思回路** —— **这是控制流**，不是状态。

> ⚠️ **v1 的 todo 只沾第 2 条的边，且沾的还是最弱的那一半**（结构化，但不持久）。第 3 条完全没沾 ——
> 而 `notes.md` ① 早就自己校正过：「**持久化 ≠ 确保完成，两者正交。被持久化的停滞计划仍然是停滞的。**」

## 3. 现状：v1 的 todo 放到长程上会怎样

### 3.1 v1 的既有定义（一句话）

`todo` 是一个**工具**（判据链 `docs/extension-points.md:16-26`：模型决定何时做 ⇒ Tool）；语义照 Claude Code
`TodoWrite` 的「**每次传完整列表**」；真值 = **最后一次调用的 `arguments.todos`**，UI 侧反向扫会话即得
（ADR-0021 决策 5）。零 `details`、零重放、零新事件。

### 3.2 三个**已经写下来**的缺口

| # | 原文 | 出处 |
|---|---|---|
| 1 | 「模型**必须看见**列表才能推进工作」⇒ 列表只能住**对话上下文** | ADR-0021 决策 2（这正是它拒绝 `details` 的理由） |
| 2 | 「**todo 状态会被压缩摘要掉**（与 skills 的 R6 同型）。缓解：最后一条 todo 调用仍在 `arguments` 里，模型可重读」 | `hooks-and-plugins/design.md` §7.3 |
| 3 | 「**持久化 ≠ 确保完成**，两者正交……被持久化的停滞计划仍然是停滞的」 | `hooks-and-plugins/notes.md` ① |

**第 2 条的「缓解」很弱**：压缩摘的就是**旧消息**，而任务越长，那条 todo 调用越早变成旧消息。
**越需要它，越容易没有。**

### 3.3 一个关键事实：压缩摘要**已经**是一份 todo —— 只是无类型

`crates/ys-component/src/compact.rs:92-110` 的 `DEFAULT_SUMMARY_SYSTEM_PROMPT` 逐字要求这些节：

```
## Progress      - Done / In Progress / Blocked
## Next Steps    剩余工作，按顺序
## Files        已读/已改的精确路径
```

**这三节就是一份 todo 清单**（进度 + 待办 + 已触碰的产物）。而且 —— 与 §3.2 第 2 条相反 ——
**它是唯一能活过压缩的东西**，因为它**就是**压缩产物。

> ⇒ **结构性结论**：长程任务里真正活下来的「计划」是**摘要里的一段散文**，不是 `todos` 数组。
> 今天这两者**互不知道对方存在**：模型可以一边在 `## Next Steps` 里写「还剩 3 项」，一边在 `todos`
> 数组里维护一份完全不同的列表，且**没有任何机制让它们一致**。

### 3.4 轮数上限：单回合装不下长程

`RunLimits.max_rounds` 默认 **10**（`crates/ys-component/src/limits.rs:39`）。长程任务必然撞 `MaxRounds`
（`basic.rs:114-133`）⇒ **回合结束，控制权回到 `app_loop`**。

> ⇒ 「长寿」只能靠**多回合**实现，**不能**靠单回合堆轮数。而「多回合」今天的唯一机制是
> **follow-up** —— 它**设计完了但没实现**，且默认**关**、上限默认 **1**（`design-plans/2026-09-15-follow-up.md:89`）。

## 4. 现有架构（可复用的三块）

### 4.1 三级控制流（判据：**是否结束当前回合、另起一个新回合**）

| 层级 | 定义 | 位置 | 增回合数 | 实现状态 |
|---|---|---|---|---|
| **轮**（Round） | 回合内一次「模型调用 +（可能的）工具执行」 | `basic.rs` `loop`（`:89`） | 否 | ✅ |
| **回合**（Turn） | 一次输入 → 一个最终回答 | `run_turn`（`basic.rs:44`） | 否 | ✅ |
| **压缩**（Compaction） | 轮边界的上下文家务 | Step 4b（`basic.rs:134`） | 否 | ✅ |
| **追问**（Follow-up） | **回合之间**、**系统**发起 | `app_loop`（`design-plans/2026-09-15-follow-up.md:49-63`） | **是** | ❌ **未实现** |

`app_loop.rs` 的 `Request::Prompt` 臂今天**就是一个回合**（`app_loop.rs:101-159`）；follow-up 的设计是
把它包进 `while let Some(msg) = pending.take()` 循环 —— **这是闭环唯一已设计好的落点**。

### 4.2 subagent 的缝（ADR-0022，已定案）

| 决策 | 内容 | 对本文的意义 |
|---|---|---|
| **D1** | 派发走**窄 trait 注入**（`ys-tool::SubagentRunner`），照 `Summarizer` 同构 | 「todo → subagent」若要走，**工具内部**即可完成，零新机制 |
| **D3** | 子 tool 表 = 父表**去掉派发工具** ⇒ **结构上不可递归** | ⚠️ 子**会**拿到 `todo` 工具（见 §5 未澄清 Q4） |
| **D17** | 支持**并行**派发（同批 N 个 `subagent` 调用并发） | ⚠️ N 个并行子 agent 与**共享 todo 状态**的关系待定（Q5） |
| **D18** | 工具名 = `subagent`；参数 `prompt` / `description` / `model` | —— |
| **D19** | 子 agent **继承完整系统提示骨架** ⇒ 每次派发 ~18.1k est token | **成本是闭环设计的硬约束**：批量派发的成本闸门 |
| **D10** | 子 usage **上卷**进 `TurnStats` | 闭环的成本可观测 |

### 4.3 判断链（决定新需求落哪个桶）

`docs/extension-points.md:16-26`：

```
1. 只想知道 → Event
2. 模型决定何时做 → Tool ；  无论模型怎么想都必然发生 → 下一条
3. 回合之内 → 工具内部做 ；  回合之间 → Follow-up
```

> ⇒ **「todo 写计划」落 Tool**（模型决定记什么、何时记）；**「未完成就再来一轮」落 Follow-up**
> （必须发生，不能靠模型自觉）。**这两件事天然是两个机制** —— 这条判断是本轮最重要的落点结论。

## 5. 约束

| 维度 | 约束 | 来源 |
|---|---|---|
| **技术** | `ys-core`/`ys-event`/`ys-protocol` **零 tokio**；`ys-tui-coding` **不依赖** `ys-runtime`（编译器强制） | `CLAUDE.md` |
| 技术 | **不跨动态库边界传 trait object** ⇒ 运行期插件出局（静态装配） | `CLAUDE.md` |
| 技术 | **Agent 无状态**（ADR-0010）：不持有 session / events；状态归**接线器** | ADR-0010 |
| **性能** | **工具面必须恒定** ⇒ 前缀每轮变动 = 每轮多付 **~9,000 token**（静态加工具的 **52 倍**） | `toolset.rs:66-72`、ADR-0021 |
| 性能 | **派发成本**：每子 ~18.1k est 子 system（D19），**必然 miss 缓存** | `subagent/design.md` §4.3 |
| **演进** | **不设计假想未来需求**；新控制流须走判断链，**开新路必须显式记账**（动 `BasicLoop` 是最高爆炸半径） | ADR-0014、`notes.md` ③ |
| 演进 | `ContentBlock::ToolResult` 是 **JSONL 落盘契约**，变体**无** `#[non_exhaustive]` | `ys-core/message.rs:19-33` |
| 组织 | 单作者项目；**文档/注释/commit 用中文**；关键逻辑须**变异测试** | `CLAUDE.md` |

## 6. 需求范围

### 范围内（本轮 arch-design 应回答）

1. **闭环的「环」合在哪一层**（轮内 / 回合之间 / 子 agent）—— §7 Q1；
2. **todo 状态的落点**（能否活过压缩）—— §7 Q2；
3. **todo 与 subagent 的结合形态** —— §7 Q4；
4. **与 v1 的关系**：v1 的 P0/P1 是否仍照做、todo 是否仍是第一个消费者 —— §7 Q6。

### 范围外（明确不做）

- **模型调用重试 / 429 处理** —— 独立缺口（truncation-guard 报告已列）。
- **`/compact` 命令的占位问题** —— 独立缺口（`capabilities.rs:194-200` 实为 `clear_session`）。
- **落盘持久化 todo（`~/.yushan/tasks/`）** —— ADR-0021 已否；**但那是为「todo 而 todo」否的**，
  在长程目标下**可以翻案**（Q2-b），故**不算范围外，算待决**。
- **多角色 agent 定义 / roster / workflow 引擎** —— `subagent/design.md` §6「明确不做」已划。

### 关键场景

| # | 场景 | 今天会发生什么 |
|---|---|---|
| **S1** | 「把这 12 个文件里的 API 用法统一」—— 一个回合做完 | todo 有用：轮内可见、压缩前有效 |
| **S2** | 同上，但撞 `max_rounds`（10） | 回合以 `MaxRounds` 结束，**无任何机制自动续** ⇒ 烂尾 |
| **S3** | 长任务跑到中途触发**压缩** | `todos` 数组被摘要掉；`## Next Steps` 里留一段散文 ⇒ 二者可能不一致 |
| **S4** | 主 agent 按 todo **逐个派 subagent** | 今天可行（工具内部调 `SubagentRunner`），但**无成本闸门**、无「已派/未派」状态 |
| **S5** | 用户中途打断（Ctrl+C） | `Abort` 生效、回合取消；**todo 状态留在会话里**，下次可续（v1 的既有优点） |
| **S6** | 派发中某个 subagent 失败 | 父侧 `ToolResult{is_error:true}`（ADR-0002 双通道）；**该 todo 是否重试无人负责** |

### 异常 / 边界

- **无限套娃**：follow-up 触发 follow-up（`design-plans/2026-09-15-follow-up.md:88-93` 的护栏 ①，上限默认 1 ⇒
  长程闭环需要**更高的上限**，护栏要重新设计）。
- **状态分叉**：模型改写 todo 列表时**丢掉**某项（「每次传完整列表」语义下，漏传 = 删除）。
- **并行写冲突**：D17 并行派发时，N 个子 agent 各自的 todo 互不可见。

## 7. 已澄清（第二轮，2026-09-23）

> 下表每题保留**原选项**（供对照），加一行 **已定**。

### Q1 ★ 闭环的「环」合在哪一层？—— **已定：回合之间（b）**

todo 是**工作计划清单**，**每轮都要去看**（`notes.md` ① P2b）。

| 选项 | 落点 | 强制力 | 代价 |
|---|---|---|---|
| a. 轮内 | 模型自己看着 todo 逐个做 | **无**（靠自觉） | 0 新机制 |
| **b. 回合之间 ✅** | follow-up：有未完成项 ⇒ 再起一轮 | **有**（代码触发） | 需先实现 follow-up；护栏要改 |
| c. 子 agent | 每个 todo 派一个 subagent | 有（但只对已派发的） | **成本 ×N**（每个 ~18.1k 子 system） |

> ⚠️ 「**每轮都要去看**」是本轮新增的**最硬约束** —— 它把 todo 从「被动查询」变成「**主动可见**」，
> 直接撞前缀缓存经济学，见 §8.1。

### Q2 ★ todo 状态住哪？—— **已定：持久化，且全部完成后删除**

| 选项 | 机制 | 是否新核心契约 |
|---|---|---|
| a. 对话上下文（v1 现状） | 反向扫会话 | 否，但**被压缩吃掉** |
| **b. 落盘 ✅** | 文件 / 外部存储 | 否（app 侧）—— ADR-0021 否过，**此处翻案** |
| c. 让压缩摘要写它 | 摘要的 `## Next Steps` 已是 todo（§3.3） | 否（改摘要提示词） |
| d. session 保留标记 | 新字段 | **是**（v1 明确不做） |

> ⚠️ 选了 b ⇒ **真值源搬出会话**，与 ADR-0021 决策 5 正面冲突，见 §8.2。
> 💡 选项 c **不废**：持久化解决「活过压缩」，c 解决「摘要里那段散文与 todo 不一致」—— 见 §8.2 末。

### Q3 谁决定「下一个 todo」—— **已定：写计划 = Tool；推动 = Follow-up**

两个机制共存，照 §4.3 判断链。

### Q4 ★ todo 与 subagent 的结合形态？—— **已定：主 agent 按 todo 执行；subagent 只做简单任务（a）**

| 选项 | 形态 | 结论 |
|---|---|---|
| **a. 主 agent 读 todo 执行，偶发派子 ✅** | 模型在轮内发起 | **采纳** |
| b. todo 工具自己派发 | 工具内部编排 | **不做**（编排不进工具） |
| c. 子 agent 读写同一份 todo | 共享状态 | **不做**（子根本拿不到 todo，见 Q5′） |

> ⇒ D19 的 ~18.1k/次 子 system 成本**只在偶发的简单子任务上付**，不是每个 todo 都付。

### Q5 并行派发与 todo —— **已定：不共享**

随 Q4：子 agent 拿不到 todo ⇒ 无并行写冲突。

### Q5′（新）子 agent 是否具备 todo 能力？—— **已定：否，只有主 agent 具备**

⇒ 子表 = 父表 − {`subagent`, `todo`}。
> ⚠️ 这**改动了 ADR-0022 D3**（原：子表 = 父表 − 派发工具），并对**工具表顺序**下了一条硬规则，见 §8.3。

### Q6 与 v1 的关系 —— **已定：P0 与 P1 都做；顺序 `P0 → P1 → subagent → todo`**

依据见 §8.5。一句话：**P0 变强了、P1 换了理由**。todo 是否仍是「第一个消费者」**不再重要** ——
两个工具都要加，先加哪个都行；P1 的验收标准（指纹保持绿）不依赖消费者是谁。

### Q7 交互形态 —— **已定：TUI 侧栏简单展示**

`CodingView.todos` + 侧栏（v1 原计划是底部面板，改为侧栏）。

## 8. 由答案推出的新约束（**本轮真正新增的部分**）

### 8.1 ⚠️ todo 每轮可见 × 前缀缓存经济学 —— 最硬的新问题

**要求**：todo 每轮都要能看到（Q1），且状态**会变**（完成一项就变）。

**判据已在**（`arch/prompt-delivery/notes.md` 第 50-56 行）：内容是**常量** ⇒ 常驻；**会变** ⇒ 才谈注入，且**必须走 `messages` 尾部，绝不改 `system`**（ADR-0021 决策 1 的硬约束）。todo 会变 ⇒ **尾部注入是其正当形态**，与既有 ADR 一致。

**但频率是新的，且能省一个数量级**：

| 频率 | 成本 |
|---|---|
| **每轮**注入 | 每轮都是全新尾部 token ⇒ 每轮 **1.0×** 全付（note 里 **443/轮** 的估算就是按这个口径） |
| **每回合**注入一次 | 回合内第 2..N 轮它已在**前缀**里 ⇒ 只有追加那一刻付 **1.0×**，其余轮次 **0** ⇒ 便宜约 **10×** |

> ⇒ **建议形态：一回合追加一次，且状态未变则跳过。**
> 「每轮都看得到」由此**成立**：追加的那一块留在历史里，回合内每一轮都在上下文中。

**待定（设计阶段回答）**：
- **追加点**：回合开始的哪一处（`app_loop` 拼 `AgentInput`？还是 `BasicLoop` Step 2 之后）？
- **块大小上限**：UI 只显示 ≤5 行，注入给模型的可以更多 —— 上限是多少？
- ⚠️ **不要每回合无条件追加**：状态没变还追加 ⇒ 上下文里**堆 N 份副本**，且模型看到互相矛盾的旧清单
  （prompt-delivery 已点名的坑）。**状态变化才追加。**

### 8.2 ⚠️ 真值源从「会话」迁到「外部存储」

| | v1（ADR-0021 决策 5） | v2（Q2 已定） |
|---|---|---|
| 真值 | **会话里最后一次 `todo` 调用的 `arguments`** | **外部存储**（持久化） |
| 新增状态 | **零** | 一份独立于会话的状态 |
| `/new` 语义 | 「todo 归零是**正确**的语义」（v1 原话） | **需重述**：新会话 ⇒ 新计划？还是沿用？ |

**必须回答的**（设计阶段）：
- 住哪：独立文件（如 `~/.yushan/...`）？还是会话文件的特殊记录？（后者与 `/new` 天然绑定，前者需处理孤儿）
- `/export` 是否带走 todo？
- 进程重启后如何恢复、与会话如何对应（一个会话一份 todo？）
- **「全部完成后删除」的执行者**：建议**代码**（全部 `Completed` ⇒ 清空）—— 「确保完成」本就在 A4 的控制流那一半，
  靠模型自觉就退回 v1 的缺点。
- **是否需要终止态**：v1 只有 `Pending / InProgress / Completed`。若用户/模型要**放弃**一项，
  没有 `Cancelled` 它会永远卡在未完成 ⇒ **永不满足「全部完成」⇒ 永不删除**。

> 💡 **§3.3 的发现不废**：持久化解决「活过压缩」，但压缩摘要里的 `## Next Steps`（散文）
> 仍可能与 todo（结构化）**不一致**。二者要不要对齐（让摘要写 todo / 让 todo 喂摘要），是个独立的小决策。

### 8.3 ⚠️ 工具表顺序：子表必须仍是父表的**字节前缀**

ADR-0022 D3 让子表 = 父表去掉派发工具，**理由是子 tools JSON 是父的字节前缀 ⇒ 命中 prompt cache**。
Q5′ 再摘一个 `todo` ⇒ **被摘的两项必须都是后缀**，否则前缀断掉、缓存优势消失。

> ⇒ **硬规则：`todo` 与 `subagent` 必须都排在工具表末位**（两者之间的先后不影响公共前缀长度）。
> 这条同时约束 v1 的 `EXPECTED_ORDER`（`toolset.rs:40-50`）与 `subagent/design.md` §6 P2 步骤 5（「第 10 项末位」）。

### 8.4 follow-up 的护栏必须重设计

`design-plans/2026-09-15-follow-up.md:88-93` 的三样护栏是为「commit 后同步文档」设的：

| 护栏 | 原设计 | 长程闭环需要 |
|---|---|---|
| 防套娃 | 计数 + 上限**默认 1** | 上限 1 **显然太小**；判据应从「计数」改为「**有未完成 todo 才继续**」（`notes.md` ① P2b） |
| 开关 | **默认关** | 长程任务下是否该默认**开**？（取决于 Q6/产品定位） |
| 非 git 仓库 | 静默跳过 | 判据换成「有无 todo」，与 git 无关 |

另：`max_rounds = 10`（`limits.rs:39`）不变 —— 长程靠**多回合**，不靠堆轮数（§3.4）。

### 8.5 P0 / P1 在本轮的新地位（Q6 的依据）

**P0 仍然必做**，且多了两条理由、多了一个**它盖不住的缺口**：

| # | 内容 |
|---|---|
| 1 | **subagent 加第 10 个工具 + 改 `prompt.rs:107`** ⇒ 前缀必变，需 tripwire 使之**显式**（`subagent/design.md` D7 亦点名先行） |
| 2 | **todo 加第 11 个**（§8.3 规定末位） |
| ⚠️ 3 | **缺口**：§8.1 的「每回合注入 todo 块」**不碰前缀、碰 `messages`** ⇒ **P0 的字节指纹测不到它**。需**另一类锚点** —— 注入点 / 块大小上限 / **状态未变时不追加** —— 属**回合形状**测试，与字节指纹并列，不是它的扩展 |

**P1 仍然必做，但理由换了 —— 从「给第三方开缝」换成「我们自己有两份表」**：

- ⚠️ 它的**唯一消费者从来不是第三方**：todo 与 subagent **都是我们自己的**。ADR-0021 §7.1 自承上限是
  「**不改 `ys-*`，但改 `Cargo.toml` + 一行登记**」。**拿「第三方」当理由，正是 ADR-0014 否掉 hook 系统时用的那把尺子。**
- ✅ **今天就有、更硬的理由**：§8.3 要求 **子表 = 父表 − {`todo`, `subagent`}** 且**必须是父表的字节前缀**
  （ADR-0022 D3 的缓存理由）；而 `subagent/design.md` §6 P2 步骤 5 已写着「**启动期建 child registry**」。
  ⇒ 要维护的**不再是「一份工具表」，而是「两份必须前缀一致的工具表」**。

| | 没有 P1 | 有 P1 |
|---|---|---|
| 父表 | `vec!` 字面量 + `EXPECTED_ORDER`（两处手工同步） | `builtin_plugins()` **一处声明** |
| 子表 | **再手写一份**，且必须与父表**前缀一致**（漂一个 byte 就废缓存，而测试全绿） | 从**同一份**声明 `filter` 出来 |
| 加第 11 个工具 | 改 **2 份表 × 6 处** | **1 行** |

**顺序：`P0 → P1 → subagent（第 10 个）→ todo（第 11 个）`。**
**P1 必须在加工具之前做完** —— 否则「指纹保持绿」这个验收信号就没了：加工具**本身**就让指纹变红，
到那时分不清哪部分变化来自搬家、哪部分来自新工具。

## 9. 后续建议

- **建议进入 `arch-design`** —— 本轮已把落点收敛为：回合之间闭环（Q1）+ 持久化状态（Q2）+ 主 agent 执行（Q4）
  + 两个机制（Q3）+ 主 agent 独占 todo（Q5′）+ 侧栏展示（Q7）；**§8 的五条新约束**是设计的输入。
- **建议先用 `prototype` 验证两件事**（都很便宜）：
  1. **§8.1 的注入形态**：一回合追加一次 + 状态变才追加 —— 看长任务里上下文增长与模型行为；
  2. **`max_rounds = 10` 下长程任务的实际烂尾率** —— 用现有 e2e 跑一个多文件任务，看它停在哪。
- **不建议**在 §8.1/§8.2 定下来之前动 `BasicLoop`（`notes.md` ③：「动 `BasicLoop` 是最高爆炸半径」）。
- **7 个问题全部闭环**；Q6 的结论（§8.5）同时给出本轮的**落地顺序**：`P0 → P1 → subagent → todo`。
