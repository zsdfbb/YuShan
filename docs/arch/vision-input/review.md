# 图像输入（Vision Input）— 架构质量分析报告

> 审核对象：`docs/arch/vision-input/design.md`（355 行）+ `context.md`
> 审核日期：2026-11-05 ｜ 维度：全量（可行性 / 可维护性 / 可理解性 / 性能与可靠性）
> 方法：文档断言逐条对照**当前源码**核实；关键守护声明做**注入实验**实测。

## 分析范围

- **对象**：设计方案（`design.md`），非已落地代码
- **维度**：全量四维 + 基础软件重点（错误处理 / 并发 / 资源管理）
- **来源**：`design.md`、`context.md`、`crates/` / `adapters/` / `apps/` 真实源码

**核心结论**：方案方向正确、分层干净，**但 §5 与 §9 赖以站立的一条安全假设是假的**，
且实测证伪。这条不修，K2「静默丢图」不但没被治，反而会被放大成**整条消息消失**。

## P0 详述：R1 + R2 —— 实测证伪「编译期守护」

### design.md §5 的原文断言

> | 上层**没有**解析器（无适配器支持） | **编译期不可达**（`ContentBlock` 有 `#[non_exhaustive]`，但适配器必须显式处理 —— 见 §8 变异测试） |

### 实测：不成立

**实验 1 —— 给 `ContentBlock` 加 `Image` 变体，全仓编译：**

```
$ ./scripts/cargo-build.sh check --workspace --all-targets
--- error 总数 --- 0
```

**加了一个新变体，77 个生产构造点、60 个引用文件、39 个测试二进制，零编译错误。**

原因：`#[non_exhaustive]` 的作用是**禁止跨 crate 穷尽匹配**（强制外部 match 写 `_` 臂），
它**不是**「加变体时提醒你去更新 match」的机制。恰恰相反 —— 它保证每个 match 都有 `_` 臂，
于是新变体被 `_` 臂**静默吞掉**。设计把它当成了穷尽性守护，方向正好相反。

**实验 2 —— 端到端跑通 `translate_request`：**

```rust
// 注入一条只有 Image 块的消息，调 translate_request，看真实出站 JSON
PROBE 出站 JSON = {"model":"test","messages":[],"stream":true,"stream_options":{...}}
```

出站 **`"messages":[]`** —— 不是「图片被丢掉、文字还在」，是**整条消息人间蒸发**。

### 根因

`adapters/model-openai-compatible/src/lib.rs:1259-1330`：

```rust
let mut text_content = String::new();          // :1259
ContentBlock::Text { text } => text_content.push_str(text),   // :1264
// …
_ => {}                                        // :1311  沉默吞掉 Image

if !text_content.is_empty() || !tool_calls.is_empty() {   // :1316  推送条件
    messages.push(ChatMessage { content: Some(text_content), … });
}
```

Image 分支若不把内容注入 `text_content` / 新增的 `image_url` 数组，**推送条件为假 ⇒ 整条
消息不 push**。这是比 `_ => {}` 本身更隐蔽的一层：`_ => {}` 只是丢块，§5 的修法（把 `_`
换成显式臂）若没同时改 `:1316` 的推送条件，**图片照样消失，而且看起来像是修过了**。

### 衍生风险 R3：静默点数量未知

`ContentBlock::Text` 的引用分布在 **35 个文件 / 184 处**，其中带通配臂的重点位置：

| 文件 | 通配臂数 | 后果 |
|---|---|---|
| `apps/coding-agent/src/main.rs` | 10 | `message_bytes` 少算（静默） |
| `adapters/model-openai-compatible/src/lib.rs` | 6 | **正是 R2** |
| `apps/coding-agent/src/subagent.rs` | 6 | `[unknown content block]` |
| `crates/ys-tui-coding/src/draw.rs` | 6 | 不渲染 |
| `crates/ys-tui-coding/src/transcript.rs` | 3 | 不渲染 |
| `crates/ys-session/src/jsonl.rs` | 3 | — |
| `crates/ys-loop/src/compact.rs` | 2 | 摘要丢弃 |
| `crates/ys-loop/src/turn_budget.rs` | 2 | **R7** |
| `crates/ys-loop/src/token.rs` | 1 | **K3** |

§8 的改动清单只列了 19 行，**没有**覆盖全部 35 个文件 —— 但这未必是漏项：多数是测试
或本就该走 `_` 的语义。问题是**没有任何机制告诉你「哪些 `_` 是安全的」**。

### 建议

**放弃「编译器当保镳」这个假设**，改为机制化的三步（这也是既有 `p2_3` 用例的思路）：

1. **`#[non_exhaustive]` 不能当守护用**。删掉 §5 那句断言，避免后继实现者以为加变体
   后编译失败就万事大吉。
2. **写一个「块集合」快照测试**，照 `crates/ys-tui-coding/src/transcript.rs:538` 的
   `p2_3_only_text_and_tool_use_produce_lines` 形态：断言「当前已处理的块集合」
   （`{Text, ToolUse, ToolResult}` → 加 Image 后 `{…, Image}`）。任何新变体不进白名单即红。
3. **`translate_request` 加一条「消息数守恒」断言**：入站 N 条消息（含 Image 块）⇒
   出站消息数不得少于「非空消息数」。这一条能直接抓住 R2 的整条消失。
4. `_ => {}` **换成显式 `Image` 臂 + 显式 `unreachable` 式兜底**：让兜底名留日志。

## P1 详述

### R4 —— `MediaCache` 的锁与 IO 边界未定义

§3.4 只写了 `struct MediaCache { Mutex<HashMap<…>> }`，没有说明：

- **读盘发生在锁内还是锁外**。若锁内读 32 MiB 文件 + base64 编码（约 2.4 M 字符），
  所有并发请求串行化，且 `MutexGuard` 跨 `.await` 需要 `tokio::sync::Mutex`。
- **base64 编码是否 `spawn_blocking`**。32 MiB 的 base64 编码是 CPU 密集（约 40 MiB
  输出），在 async 任务里直接做会阻塞执行器。本仓是单 TUI + 子 agent，影响有限，
  但子 agent 并发看图时会叠加。

建议：先查后算（查缓存不持锁 → 未命中则**锁外**读盘+编码 → 再持锁插入）。
设计里把这条写成明确的时序。

### R5 —— 缓存无上界

缓存键是 `(path, mtime, len)`，同一路径改写会**新增**一条而不是替换 ⇒ 陈旧条目永久
驻留。32 MiB 图 base64 后约 **41 MiB**，几张 4K 截图就能吃掉数百 MB。
建议：加 LRU 上界（按总字节，如 128 MiB）与条目数上限。

### R6 —— 占位是**写入历史**的，且不可恢复

§5 与 D6 说「读不到 ⇒ 文本占位 + 继续回合」。但占位文本是替换进 **`ContentBlock` 内容**
的 —— 若这个替换发生在**消息落盘时**，则永久固化：用户补回原图、恢复文件后，历史里
已经是死文本，永远不再重试。

若替换只发生在**出站时的临时副本**上则无此问题。**设计没有区分这两种语义**，这是
必须在 §5 明确的关键点。建议：**占位只在出站临时副本上生成，绝不写回 `ContentBlock`**；
并补一条测试（「文件补回后下一回合能正常送图」）。

### R7 —— 第二个 token 估算器未治

`crates/ys-loop/src/turn_budget.rs:37-38`：

```rust
ContentBlock::ToolResult { content, .. } => crate::token::estimate_text_tokens(content),
_ => 0,
```

这独立于 `token.rs`，§6 只列了 `token.rs`。若 `turn_budget` 用于回合预算判定，
Image 块在此记 0 ⇒ 预算低估。需确认它是否覆盖图片，或明确写「不计入，理由是…」。

## P2 / 其他

### R8 —— 行号与字段失真（逐条实测）

| 设计原文 | 实际 | 说明 |
|---|---|---|
| §8 `Image { id, path, detail }` | §3.1 是 `Image { path, detail }` | **两处自相矛盾**，`id` 从何而来不明 |
| §3.5 `basic.rs:1409` 折叠点 | 折叠在 `:1413-1417` | 近似 |
| §7 `jsonl.rs:91-102` 跳过 | 跳过在第 `:170` | 失真 |
| §3.1 `ocr/mod.rs:537` `dims_from_header` | `:537` 是 `}` | 失真（函数位置更早） |
| §8 `request.rs` `#[serde(untagged)]` 使纯文本字节不变 | `ChatMessage` 派生 `Deserialize`（`:50`），`untagged` 枚举会**改变反序列化错误路径** | 本仓响应解析**不用** `ChatMessage` ⇒ 仅测试受影响，风险低但应写明 |
| §3.4 `MediaError::TooLarge` | §3.1 未定义 `ImageDetail` | 类型清单不完整 |

**「约 93 处构造点」**（context）与实测不符：`ToolResult {` 共 **168** 处，
生产 **77** 处、测试 91 处。§8 已正确指出「编译器当保镳」在这里**确实成立**
（结构体字面量是穷尽的，加字段必然编译失败）—— 与 R1 的 enum 情形正好相反，
这个对比值得写进设计，因为它解释了「为什么 ToolResult 安全、ContentBlock 不安全」。

### 优点（应保留）

1. **「像素字节永不跨 crate 边界」**：干净、可测试、与依赖方向一致。这是本设计最强的一点。
2. **§3.7 的已知代价如实写明**（路径是引用不是快照），并把「完全可复现」明确列为非目标 —— 取舍诚实。
3. **§9 测试矩阵有 13 条**，其中「字节不进会话文件」「出站时才读盘」「原图改内容送出跟着变」
   三条正好钉住 B/C 接缝，质量高。
4. **明确不引 `image` crate**：省掉一个大依赖，代价（不缩放）已写进 §10。

## 总体评价

**整体健康度：良好，但有一条 P0 假设必须先拆掉。**

方案的架构判断是对的 —— 字节不进会话、单一 IO 点、两层门控，都经得起推敲。
`§3.7` 把「路径是引用不是快照」的代价如实写出来，是本仓文档质量的正面样本。

**最大风险不是某个具体 bug，而是一句被写进设计的错误安全假设。**
§5 声称 `#[non_exhaustive]` 提供了编译期守护，实测证明：加变体后全仓零编译错误，
且一条纯 Image 消息会**整条静默消失**。这个假设若不纠正，实现者会以为「编译器帮我兜住了」，
而实际后果比设计要治的 K2 更严重。

**推荐下一步行动**（按顺序）：

1. **先改 §5 + §8**：拆掉错误假设，补上 `translate_request:1316` 这一行（P0）
2. **再补两条测试设计**：「消息数守恒」+「块集合白名单」（P0）
3. 补 §3.4 的锁边界与缓存上界（P1）
4. 其余行号/字段修正（P2）
5. 之后才进 `§11` 的实施顺序 —— 第一步 `ys-core::media` 纯函数不受上述任何问题影响，
   **可以并行先做**

**放行判断**：建议**有条件放行** —— `ys-core::media`（§11 步骤 1）可立即开工，
不依赖上述任何修正；`ToolResult.media` 与适配器改造（步骤 2-4）需等 R1/R2 的设计
修订落地后再启动。
