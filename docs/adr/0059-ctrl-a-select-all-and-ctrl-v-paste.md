# 0059 — `Ctrl+A` 全选、`Ctrl+V` 应用内粘贴

两个键位改动，同一条判据：**「终端压不压成同一个控制字符」决定一个键能不能用，而应用能
决定的是别把唯一的入口赌在那上面**。① `Ctrl+A` 从行首改为全选（行首留在 `Home`）；
② `Ctrl+V` 读系统剪贴板并插入输入框（终端自己的粘贴键仍是 `Ctrl+Shift+V` / `⌘V`）。

## Status

accepted（2026-10-26）—— 已实施。

落点：`crates/ys-tui-coding/src/events.rs`（键位分派 + 模块头键位表）、`run.rs`
（`read_system_clipboard` / `clipboard_readers` / `run_reader`、`handle_round` 的读段）、
`app.rs`（`App::pending_paste`）、`commands.rs`（`KEYBINDINGS` / `KEY_HELP_BRIEF`）。

## 背景

### 1. 全选只有一个「多数终端按不出来」的键

ADR-0057 把全选放在 `Ctrl+Shift+A`，并在同处记下了代价：多数终端把 `Ctrl+Shift+字母`
压成同一个控制字符（`Ctrl+A`），那个键按不出来。当时保留 `Ctrl+A` 的 readline 语义
（`beginning-of-line`）是为了不丢「跳到行首」。

实际使用里这条权衡站不住：**行首本来就有第二个入口** —— `Home`（ADR-0057 已把它改成
输入当前行行首）。也就是说 `Ctrl+A` 与 `Home` 长期是同义的，而全选在绝大多数终端上
**一个可用入口都没有**。「两个键做同一件事」与「一个功能没有键」同时存在。

### 2. `Ctrl+V` 在应用里是死键

终端的粘贴键是 `Ctrl+Shift+V`（Linux / Windows）或 `⌘V`（macOS）：由**终端**读剪贴板，
把内容包成 bracketed paste 交给应用（`Event::Paste`）。裸 `Ctrl+V` 不走这条路 —— 它在
raw 模式下就是控制字符 `0x16`，终端不解释它，字节**到得了应用**。本仓此前没有接这个字节，
于是它什么都不做：用户按下去像按了个坏键。

## 决策

### 1. `Ctrl+A` = 全选输入框；行首走 `Home`，行尾走 `End` / `Ctrl+E`

| 键 | 行为 |
|---|---|
| `Ctrl+A` | **全选输入框**（随后 `Backspace` / `Delete` / 打字替换整段） |
| `Ctrl+Shift+A` | 全选（等价 —— 压不成它的终端退化的正是 `Ctrl+A`，两档同义） |
| `Home` / `End` | 输入**当前行**的行首 / 行尾 |
| `Ctrl+E` | 行尾（与 `End` 同义，保留） |

**为什么可以丢掉 `Ctrl+A` 的 readline 语义而不能再丢 `Ctrl+E`**：`Home` / `End` 已经
完整覆盖行首 / 行尾，`Ctrl+A` 是**冗余的第三个入口**；`Ctrl+E` 同理冗余，但保留它零成本
（不与任何功能冲突），而删掉它只能换来「更一致」这一种收益。

**为什么这样反而更可靠**：`Ctrl+A` 是裸控制字符，**所有终端都送得到**；`Ctrl+Shift+A`
依赖 `DISAMBIGUATE_ESCAPE_CODES`。把全选放在裸键上，等于把「终端能力」这个变量从
「全选能不能用」里摘掉。ADR-0057 的 C 方案（`Ctrl+A` 改义为全选）当时因「丢
`beginning-of-line`」被否决 —— 那条否决理由在本仓**不成立**，因为行首当时已有 `Home`。
本 ADR 推翻那个否决。

### 2. `Ctrl+V` = 读系统剪贴板并插入输入框

- `events.rs` 只置位 `App::pending_paste`（该模块不做 IO），`run.rs` 在**本轮末尾**读出来
  插进缓冲 —— 与 `pending_clipboard` 同一套「意图 → 执行」交接，方向相反。
- 读取只走**本机工具**（`wl-paste` / `xsel --clipboard --output` / `xclip -o` / `pbpaste`，
  `WAYLAND_DISPLAY` 有值时 Wayland 优先，顺序与写入链一致）。**不发 OSC 52 读请求**：
  读形态要求终端把内容回写到 stdin，而 stdin 正被 crossterm 的事件读取占着 —— 两路读同一
  字节流会互相吞事件（终端应答被事件解析器吃掉时，用户按的键也一并丢）。写是单向的，
  读不是，故读取只走工具。
- 读失败（没有工具 / 工具非 0 退出 / 内容为空 / 非 UTF-8）⇒ **什么都不发生**，只清标志。
  不清输入框、不插空串：「按了没反应」可恢复，「草稿被清空」不可恢复。此时用户改用终端的
  粘贴键 —— 那条路与本功能互补，不冲突。
- 有选区时 `insert_str` 先消费选区（粘贴替换整段），与 `Ctrl+C` 之后按粘贴的 GUI 直觉一致。

### 3. 读取**同步**，写入**异步**

写入（`spawn_writer`）spawn 完就走，不等子进程 —— 每次复制搭一笔进程启动成本是可接受的。
读取不行：用户按 `Ctrl+V` 期待内容是**当场出现**的，所以 `run_reader` 用 `Command::output()`
等它结束。开销是 UI 线程上的一次短命子进程（本地进程通信，毫秒级），发生在**按键之后**，
不在渲染路径上。

### 4. 同一轮里**先读后写**

`handle_round` 的顺序固定为：鼠标事件 → 键盘事件 → 读（`pending_paste`）→ 写
（`pending_clipboard`）。两者同一轮同时非空只发生在「上一轮刚复制、这一轮又按粘贴」
（X11 下 `xsel` 接管 selection 需要一点时间）。先写后读会把**刚复制的草稿**读回来插进
输入框（「我明明粘的是别处的内容」）；先读后写最坏是读到旧剪贴板 —— **粘到旧内容可删、
可预期，静默改写输入框是破坏性的**。

## 代价

- **`Ctrl+A` 的 readline 语义没了**：肌肉记忆为 `beginning-of-line` 的用户会发现自己选中了
  全文。`Home` 是替代，且这正是本条的目的。
- **`Ctrl+V` 在 SSH / 容器里无反应**：远端没有本机剪贴板工具。这不是回归（此前也无反应），
  但「应用内粘贴」和「终端粘贴」从此是两个键、两种行为，`/keybind` 里必须写明。
- **`Ctrl+V` 阻塞 UI 线程一次子进程**：工具缺失时会走完整条候选链（逐个 `ENOENT`），
  延迟以毫秒计，但确实在按键路径上。不做能力缓存：探测结果会因安装工具 / 切换会话而失效，
  而缓存一个「不可用」会让用户装了工具也没反应。
- **尾随换行原样保留**：`xsel` / `pbpaste` 输出常带一个换行，`wl-paste` 已用 `--no-newline`
  压掉。不去猜「哪个换行是工具加的」—— 猜错一半，而多出的换行在输入框里可见、可删。

## Considered Options

### A. 保留 `Ctrl+A` = 行首，只加 `Ctrl+V`

- 否决理由：用户报的第一个需求就是「一个键选中全部再删掉」。`Ctrl+Shift+A` 在多数终端
  按不出来，等于这个需求没被解决。

### B. 全选放 `Ctrl+Shift+A`，另给行首别的键

- 否决理由：全选的可用性依赖终端能力，而 `Ctrl+A` 已经与 `Home` 冗余。把**可靠的那个键
  留给不可靠的功能**是本末倒置。

### C. `Ctrl+V` 走 OSC 52 读

- 否决理由：见决策 2 —— 与 crossterm 的事件读取抢同一个字节流，会吞键。收益也不明确：
  支持 OSC 52 写的终端不少，支持读的显著更少。

### D. 粘贴走异步（后台读，读完再插）

- 否决理由：用户按 `Ctrl+V` 之后输入框会先「什么都没变」再跳一下，而插入位置以**读取完成
  时**的光标为准 —— 期间用户挪了光标，内容就插到别处。同步读把这个窗口压到没有。
