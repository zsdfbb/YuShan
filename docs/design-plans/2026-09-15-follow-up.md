# Follow-up（追问）设计计划

> 日期：2026-09-15（**修订：2026-11-06**）
> 决策记录：ADR-0014（为什么有 follow-up，却没有 hook 系统）
> 性质：**新增能力的设计**。本文件只讲 follow-up；不含任何 hook 系统内容。
>
> ⚠️ **本文的代码骨架已于 2026-11-06 按 as-built 重写**（§3.1 / §3.3 / §3.4 / §5 / §6）。
> 旧稿假设的 `Request::Prompt` 臂内 `while pending.take()` 循环**已于 ADR-0041（2026-10-17）删除**，
> 且当时的落脚文件 `apps/coding-agent/src/follow_up.rs` 也一并删除。
> **判断与护栏仍然有效；骨架与改动面是新的。** 质量分析见
> `docs/arch/cross-turn-advance/review.md`。

## 1. 背景与动机

**需求**：agent 在一个回合里执行 `git commit` 之后，希望**自动**再起一轮，让它检查并更新
`AGENTS.md`（及同类文档），保证文档与代码一致。

**为什么不能用提示词 / 工作流**：两者都依赖**模型自觉** —— 它可能忘记、可能判断错。
要做到「每次提交后必然发生」，触发必须是**代码**，不是提示。

**为什么不是 hook 系统**：见 ADR-0014。简言之 —— 手里只有一个真实消费者，
按项目自身的「**不设计假想未来需求**」，通用 hook 系统**有意推迟**。

## 2. 概念边界（必须先分清）

三级结构（前两级已存在，第三级为本计划新增）：

| 层级 | 定义 | 代码位置 |
|---|---|---|
| **轮**（Round） | 回合内一次「模型调用 +（可能的）工具执行」 | `BasicLoop` 的 `run_turn`（`basic.rs:428`） |
| **回合**（Turn） | 一次输入 → 一个最终回答 | `run_turn_once`（`app_loop.rs:1454`） |
| **追问**（Follow-up） | 回合**结束后**、由系统发起的**下一个回合** | **新增**（`app_loop`，§3.1） |

与相邻概念的区别 —— 判据是**「是否结束当前回合、另起一个新回合」**，**不是**"谁发起"：

| | 谁发起 | 位置 | 增回合数 |
|---|---|---|---|
| 轮内工具 | 模型 | 回合内 | 否 |
| 插话 `Steer` | 用户 | 回合内（轮边界） | 否 |
| 压缩 `Compaction` | 循环 | 回合内（轮边界） | 否 |
| **追问** | **系统** | **回合之间** | **是** |

> **两个易混点**（都记在 `CONTEXT.md`）：
> - **追问 ≠ 插话**：`Steer` 不增回合数（`basic.rs:168` 的轮边界拉取注释：轮内的额外输入，不是新一轮）。
> - **追问 ≠ 压缩**：压缩在**回合之内**、轮边界，且**已实现**（`basic.rs:236` 的 `plan`→`execute`）；
>   `/compact` **命令**也已不是占位（`capabilities.rs:511` 的 `pub async fn compact`）——那是**独立缺口**，与本计划无关。
>   > **状态更新**（2026-10，compaction 加固闭环后）：`/compact` 命令**不再是占位**——
>   > 真压缩已落地（`apps/coding-agent/src/capabilities.rs` 的 `pub async fn compact`），见
>   > `docs/design-final/compaction.md` §8 [已关闭] 与 commit `dc5277d`。

## 3. 设计

### 3.1 形状：**新增一个调用点**，不是包循环

⚠️ **旧稿此处已被推翻。** 旧稿要在 `Request::Prompt` 臂里包一个
`while let Some(msg) = pending.take()` 循环，那个循环已由 ADR-0041 删除。

**现行结构**：`run_turn_chain`（`app_loop.rs:1304`）是三条调用点的**唯一回合实现** ——
`Request::Prompt`（`:570`）、`Wake::SubagentReturned`（`:426`）、
`Wake::BackgroundReturned`（`:483`）。

⇒ follow-up 是**第四个调用点**，与追问前那次回合**顺序**执行：

```rust
Request::Prompt(message) => {
    let raw_user_text = crate::sessions::user_text(&message);
    let message = expand_skill_invocation(message, &config.skills);

    // 回合前记一次 HEAD（检测基准）
    let head_before = follow_up::git_head(&worktree.get().map(|b| b.path.as_path()));

    let outcome = run_turn_chain(..., message, raw_user_text).await?;

    // 追问**至多一次**，且由**结构**保证（没有计数器、没有循环）
    if let Some(next) = follow_up::should_follow_up(&outcome, head_before.as_deref(), config) {
        let message = follow_up::harness_input(next);   // Role::Harness
        run_turn_chain(..., message, None).await?;       // None ⇒ 不贡献标题素材
    }
}
```

**为什么不用 `while` 循环**：追问至多一次是**结构事实**，不是运行期约束。
一个顺序的 `if` 让「不可能套娃」由代码形状保证 —— 与旧 `follow_up.rs` 里
`TurnKind::Review` 恒返回 `None` 的思路同源，但更窄（连枚举都不需要）。

**为什么尾部 `emit_view()` 不需改动**：两次 `run_turn_chain` 都在**同一个臂内**顺序执行，
尾部（`:972`）那次刷新看到的是 `stats` / `turns` **累加后**的值 ⇒ 读数正确。
这一点与 `Wake::*` 两臂不同 —— 那两臂 `continue` 跳过了尾部刷新，才需要各自补
`build_view`（`:446` / `:503`）。**本设计不 `continue`，不自补 view。**

**关键约束：一个函数一个 seam。** 不引 `trait`、不引 registry、不引 `HashMap`。
将来若要「可插」（多点、多来源），再把这**一个函数**升级成列表 —— 那是加法，不是重写。
**今天不预埋任何抽象。**

### 3.2 检测：HEAD 前后对比

```rust
/// `git rev-parse HEAD`；非 git 仓库 / 无 git / 命令失败 → None
fn git_head(ws: &Path) -> Option<String>;
```

回合开始前记一次、结束后再记一次，**两者不等**即视为「这一回合里发生过提交」。

**为什么不解析命令参数**（在 tool args 里找 `git commit`）：**脆** —— `git ci`（别名）、
`a && git commit`、`bash -c "..."`、`git -c x=y commit` 都能绕过。

**为什么不装 `.git/hooks/post-commit`**：要往**用户仓库**里写文件，越界；且「谁读标记、何时读」
要额外设计。

**好处**：HEAD 对比**也覆盖用户自己**的提交，不只是 agent 的。

### 3.3 三样护栏（缺一不可）

1. **防套娃 —— 已由结构消除**。旧稿用「`follow_ups` 计数 + 上限（默认 1）」；
   现行形状**没有循环也没有计数器**：追问分支只出现一次、且它自己不再递归
   ⇒ 追问回合里若又提交，**不可能**触发第二次。这是更强的保证（无法被配置调坏）。
2. **开关**：**默认关**。不是每个用户都想让 agent 每次提交都改文档。
   `Config` 的 `user_config` 增字段（照 `max_turn_duration_secs` 的形态，`config.rs:161`），
   来源 `YUSHAN_FOLLOW_UP_ON_COMMIT`（照 `Config::from_env` 的越权形态，`config.rs:252`）。
3. **非 git 仓库静默跳过**：`git_head` 返回 `None` 时视为「检测不可用」，不追问、不报错。
4. **只在正常收场后追问**（**新增，旧稿缺**）：`outcome` 是 `Err`
   （模型/工具失败）或 `StopReason::{Cancelled, Truncated, MaxRounds, NoOutput}` ⇒ **不追问**。
   理由：ADR-0041 撤完工复核时确立同一原则 ——「用户中止永远赢」，非正常收场不该再追加成本。

### 3.4 改动面（**零依赖环**）

| 落点 | 改什么 |
|---|---|
| `apps/coding-agent/src/app_loop.rs` | `Request::Prompt` 臂两次 `run_turn_chain`（§3.1）；`run_turn_chain` 返回 `TurnOutcome` 而非 `()`（§3.6） |
| **新增**小模块 `apps/coding-agent/src/post_turn.rs` | `git_head` + `should_follow_up` + `harness_input`（纯函数，易测） |
| `apps/coding-agent/src/config.rs` | 开关字段（`config.rs:161` 的 `user_config` + `:252` 的 `from_env`） |
| `apps/coding-agent/src/app_loop.rs` 模块注释 | 不变量 ④（`:54`）措辞需同步（§3.7） |

> ⚠️ **不要叫 `follow_up.rs`** —— 那是 ADR-0041 显式删除的文件名，复用会让后人读成回退。

**不碰** `ys-loop` / `ys-runtime` / `ys-protocol`。这也正是把追问放在 `app_loop`（而非 `BasicLoop`）的理由：
「多回合驱动」本就归 `app_loop`（ADR-0010 附注），且 `RunResult` 住在 `ys-loop`，
 hook 若从 `ys-component` 碰它会成**依赖环**（详见 ADR-0014）。

`git_head` 的实现照 `worktree.rs:445` 的 `git()`（`Command::new("git").arg("-C")…`，
清 `GIT_DIR` / `GIT_WORK_TREE`），不从 `worktree.rs` 导出
（它是 `WorktreeError` 私有实现，跨模块复用会把错误类型绑死）。

### 3.5 扩展轴（将来往哪长）

| 轴 | 今天（甲） | 将来 |
|---|---|---|
| **① 触发条件** | HEAD 变化 | 工具 X 跑了 / 文件出现 / 每 N 回 / 用户规则 |
| **② 判断来源** | 硬编码函数 | 从配置读 → 由插件提供 |
| **③ 追问内容** | 固定字符串 | 模板（带 diff / 路径）→ 插件生成 |

三条轴今天都**不实现**，但 seam 的形状（「回合结束 → 问一次 → 可选追加一个回合」）已为之留好。
注意：轴①③若要长到「回合**外**触发」（定时 / 外部事件），**本设计的 `if` 追加不够** ——
那种触发需要 ADR-0047 的跨回合队列，见 §6.2。

### 3.6 前置改动：`run_turn_chain` 必须交出 `TurnOutcome`

**这是本设计唯一不能绕开的结构改动。**

`run_turn_chain` 今天的签名是 `-> Result<(), AppLoopError>`（`app_loop.rs:1320`）⇒
**调用方拿不到 `StopReason` 与 `RunResult`**。而护栏 ④（只在正常收场后追问）需要它们。

```rust
// 前
async fn run_turn_chain(..., message: Message, raw_user_text: Option<String>)
    -> Result<(), AppLoopError>;
// 后
async fn run_turn_chain(..., message: Message, raw_user_text: Option<String>)
    -> Result<TurnOutcome, AppLoopError>;
```

`TurnOutcome` 已是现成类型（`type TurnOutcome = Result<RunResult, LoopError>`），四条返回路径都是小改写：

| 返回路径 | 现在 | 改后 |
|---|---|---|
| 正常收场（`:1398` 的 `Ok(())`） | `Ok(())` | `Ok(outcome)` |
| UI 收摊（`:1395` 的 `return Err(e)`） | `Err(e)` | 不变 |
| `run_turn_once` 返回 `Err(AppLoopError)` | `?` 上抛 | 不变 |
| 回合失败（`TurnOutcome::Err`） | 已落日志、不传播 | 装进 `Ok(Err(..))` 返回 |

**三个现有调用点**（`:426` / `:483` / `:570`）改为 `….await?;`（丢掉值即可）——
它们不需要追问，也不必解构结果。追问只在 `Request::Prompt` 臂用返回值。

> 备选（**不推荐**）：不动签名，另开一条 `AtomicU8` 记最后 `StopReason`。
> 否决理由：隐式共享状态、跨回合残留、与「一个回合一条结果」的单一路径相背。

### 3.7 不变量 ④ 的措辞需同步：`app_loop.rs:54`

现文：

> **④ 每次用户输入恰好跑一个回合**（ADR-0041 撤回 ADR-0027 决策 2 的完工复核）

本设计落地后它变假。但 **ADR-0041 的决策本身不退** —— 它撤的是「模型自称完工后
系统再追问一次」（无条件复核），而 follow-up 是「**外部可观测的事实**（HEAD 变了）
触发的追加回合」。两者区别：

| | 触发条件 | 依据 |
|---|---|---|
| ADR-0041 撤掉的完工复核 | 模型说「我做完了」 | 模型自述，不可验证 |
| 本设计的 follow-up | `git rev-parse HEAD` 前后不等 | **外部可观测**，不依赖模型自述 |

⇒ 不变量 ④ 应改为：

> **④ 一个回合链恰好跑一个回合；追加回合只能由「外部可观测事实」触发**
> （ADR-0041 撤掉的是模型自述触发的完工复核；follow-up 的 HEAD 对比属另一类）

**同时须改**：`run_turn_chain` 的文档（`:1291` 的「目前总是一回合」）。

## 4. 非目标

- **不建 hook 系统**（ADR-0014）。
- **不处理「回合后动作里不需要模型」的那类**（跑 linter、`git push`）—— 那只是「跑个命令」，
  不是追问；而 YuShan 不做 `app_loop` 内的任意 `exec`（工具都走循环）。**别为它设计。**
- **不碰 `/compact`** —— 它已落地（`capabilities.rs:511`），与本设计无关，不要在这里动它。

## 5. 测试

- **变异测试**（本项目约定）：把 `should_follow_up` 的 `head_before != head_after` 判据
  改成恒 `true` ⇒ 「HEAD 不变那么追问」用例**必须变红**。
- HEAD 变化 → 恰好追问 **1** 轮（且只 1 轮）。
- HEAD 不变（回合内没提交）→ **不**追问。
- 开关为关 → **不**追问。
- 非 git 仓库 → 静默跳过，回合正常收尾。
- **`StopReason::Cancelled` → 不追问**（护栏 ④）。
- **`StopReason::MaxRounds` / `Truncated` / `NoOutput` → 不追问**。
- **回合失败（`TurnOutcome::Err`）→ 不追问**（但失败本身照既有路径落日志）。
- **追问轮里又提交 → 仍只追问 1 轮**（结构保证；用两次 HEAD 变化验证）。
- 追问轮的 `Envelope.turn` **递增**（消费者可见）。
- 追问轮的输入 `Role` 是 **`Harness`**（与 `subagent_placeholder` 同规）。
- 两次 `run_turn_chain` 后状态行读数正确（尾部 `emit_view()` 看到累加后的 `stats`）。

## 6. 风险 / 待定

### 6.1 已定（2026-11-06）

- **预算共享，且默认值下不构成限制**。`deadline` 在 `run_turn_chain` 入口算
  （`app_loop.rs:1322-1323`），两条链各有自己的预算 ⇒ **追问独立预算**。
  而默认 `max_turn_duration` 是 **48h**（`config.rs:431-434`）⇒ 实际不可触及，
  **不为它加机制**。仅当用户把预算调到接近真实任务时长时，追问可能因预算耗尽而跳过 ——
  这是**可接受且自愈的**（`:1654` 的 `budget_exhausted` 分支会先发说明行）。
- **追问输入的呈现**：`Role::Harness`（`subagent.rs:1229` 已定此约定：
  「这条输入由 harness 产生、用户没说过 —— 区分来源」）。
- **检测的 `cwd` 口径**：`worktree.get()`（`WorktreeHandle`，`/resume` 后可改），
  与 `run_turn_chain` 回合末写 meta 取工作区的方式一致（`:1357`）。

### 6.2 真正的限制（写在这里，不要当缺陷修）

**追问只在「用户刚说完话」之后发生。** 因为它是 `Request::Prompt` 臂里的一次顺序追加：
若用户在 agent 回合结束后**再没敲字**，`Request::Prompt` 不会再触发 ⇒ **不会追问**。

三个具体后果：

1. **`-p` / `--json` 永远不追问**。那两条路径走 `main.rs` 的 `run_single_turn`，
   **不经过 `app_loop`** ⇒ 本设计对它们零影响。这是有意的（一次性任务不需要「再看一件事」）。
2. **TUI 下用户提交后立刻失焦 ⇒ 本轮不追问**。
3. 要覆盖「回合外触发」需 ADR-0047 的跨回合队列（`Delivery{origin: System}`）——
   成本高一个数量级，**本设计不做**。两者不是同一件事（见 `docs/arch/cross-turn-advance/context.md`）。
