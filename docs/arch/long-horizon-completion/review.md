# 长程任务的「完成」— 设计质量分析（`/arch-validate`）

> 日期：2026-10-08。对象：[`design.md`](design.md)（+ ADR-0027 / ADR-0028）。
> 本文**只做评审**，不改设计、不改代码。所有判断尽量带 `文件:行号` 或算式。
> **处置（2026-10-09）**：本报告是**时点快照**；逐条撤销/采纳见 [`design.md`](design.md) §9（评审修订）与两 ADR。
> 同日的另一条独立输入（同类软件调研）见 [`design.md`](design.md) §10 与 [`research.md`](research.md)。
> 其一例外：风险 2 / 建议 1 的前提（「必须放弃『零协议变体』」）**不成立** —— §4.6.1 用 `is_turning` 判别式在**零新协议变体**下解决了 UI 冲突。
> 风险 1（短回合被追问）已按 §4.1 抬高门槛（`REVIEW_MIN_ROUNDS = 5`）缓解。

## 0. 结论速览

| 维度 | 判定 | 一句话 |
|---|---|---|
| 可行性 | 🟢 | 三处改动都落在已验证的既有机制上；两处（`-p` 预算、UI 修复）比设计写的更重 |
| 可维护性 | 🟡 | 缝隙干净、纯函数可测；但「零协议变体」不变量已与已拍板的 UI 修复冲突 |
| 可理解性 | 🟡 | 概念少、命名清楚；但 `Cancelled` 变成**三义**、`turn_count` 混计 |
| **性能与可靠性** | 🔴 | **② 会给几乎每一次「用过工具」的请求都加一个完整回合**；48h 下的会话落盘 I/O 未评估 |

**总评**：① 方向正确且落点干净；**② 是全局风险最高的部分**（高频 + 成本 + 它不是本次故障的证据驱动项）；
③ 设计合理但受「沙箱内 bind 受限」影响**难以在本环境自验**。

## 2. 可行性

| 项 | 判定 | 依据 / 保留 |
|---|---|---|
| ① `config.rs` + `resolve_limits` | 🟢 | 既有 `context_window` / `compaction` 同款形状；`resolve_limits`（`main.rs:361`）是唯一接线点 |
| ① wall-clock 预算（`app_loop`） | 🟢 | `Boundary::Abort` 既有机制、`BasicLoop` 在轮边界读取；零 `BasicLoop` 改动成立 |
| ① wall-clock 预算（`-p` / `--json`） | 🟡 | `run_single_turn`（`main.rs:715-724`）**不传 boundary**，且与消费者 `join!`。要加计时器得重构这个函数 + 传合成 boundary。**设计写的「同一处改动，属加法」偏乐观** |
| ② `follow_up.rs` + `pending.take()` | 🟢 | 逐字复用设计稿既有缝；`should_review` 是纯函数 |
| ② `rounds >= 2` 判据 | 🟡 | `RunResult.rounds: u32` 是 `pub`（`crates/ys-loop/src/result.rs:7`）✅。**边角**：首批工具调用被截断整批作废、模型改小步收尾时，`rounds ≥ 2` 但**没有工具真的执行过** ⇒ 复核会在一次「纯文本收尾」后触发（假阳性，轻微） |
| ③ 重试 + 超时落适配器 | 🟢 | 适配器**有 tokio**（`adapters/model-openai-compatible/Cargo.toml`：`rt, time, io-util, net`）与 `reqwest` ✅；不碰 `Model` trait / `ModelError` / `BasicLoop` |
| ③ 本地回环 TCP 测试 | 🔴（环境） | `llm-api-unavailable/context.md` §约束自陈「**沙箱内 bind 会被拒**」⇒ ③ 的验收测试**可能在开发环境跑不起来**，只能靠断言式单测 + 人工复现 |
| UI 修复（已拍板「修」） | 🔴 | 见 §3-问题 1 与 §6-风险 2：**TUI 在回合开始处没有任何信号** |

**可行性小结**：三处主改动都可行。真正被低估的是 **UI 修复**与 **`-p` 预算**这两处「顺带」——它们不是加法。

## 3. 可维护性

**好的部分**

- ② 的缝是**复用**而非新建：设计稿（`2026-09-15-follow-up.md` §3.1）已定义 `pending.take()` 循环，ADR-0024 认定其为落点 ⇒ 不会出现两套「回合边界续跑」。
- `should_review` 是纯函数、`TurnKind` 是二态枚举 ⇒ 可脱离 `app_loop` 重型测试台单测，变异靶明确。
- ③ 的三条硬规则（未吐 delta 才重试 / HTTP 语义判可重试 / 有界退避）都是可断言的。

**问题**

1. 🔴 **`design.md` §5 不变量 #1 与已拍板范围冲突**。不变量写「**零新协议变体**」，
   但 UI 修复（用户已确认「修」）需要 TUI 区分「这条 `UserMessage` 是系统复核」——
   而实测确认 TUI 侧**拿不到任何回合开始信号**：`is_turning` 只由 `begin_local_turn`（`app.rs:194-198`）置位，
   `begin_turn` 是 sink 侧、不发事件（`apps/coding-agent/src/channel.rs:277`），
   `apply_event` 对 `UserMessage`（`app.rs:91-101`）**不置 `is_turning`**。
   ⇒ 要么改 `Outbound` / `AgentEvent` 加变体（**打破不变量 #1**），要么在 TUI 里「按内容匹配复核文案」（脆弱、违反「不嗅探内容」的直觉）。
   **设计必须就此补一节，不能只写「修」。**（另见 §6-风险 2。）

2. 🟡 **③ 的重试策略被锁进单个适配器**。设计以「只有 1 个消费者」否决了 `RetryingModel` 装饰器（理由成立），
   代价是：可重试性判定 + 退避参数**与 OpenAI 兼容方言绑死**。第二个适配器出现时要复制一遍。

3. 🟡 **错误传播面的既有短板未纳入**：`ModelError::Provider(String)` 无结构（`crates/ys-model/src/error.rs:8`），
   设计选择「不改」是对的（避免 breaking），但这也意味着**重试决策永远无法上升到 `ys-loop`**——这是个要长期接受的既成事实，应在设计里写明。

4. 🟡 **测试矩阵缺一条**：设计给 ①②③ 都列了测试，但没有一条**端到端**验证「48h 形态」——
   即「一个回合跑很多轮 + 触发多次压缩 + 复核 + 预算」的组合。这类组合 bug 恰是本项目的历史高发区（CLAUDE.md 自陈）。

## 4. 可理解性

**好的部分**：`TurnKind` / `should_review` / `REVIEW_PROMPT` / wall-clock 预算——概念数少，命名直白；复核文案英文、纯常量、可逐字节断言。

**问题**

1. 🟡 **`Cancelled` 变成三义**：用户 Ctrl+C、wall-clock 预算到点、（以及 `-p` 下的同类）。设计靠一条 `Outbound::Output` 区分，
   但 `RunFinished.stop_reason` 会进 `TranscriptLine::Summary`（`app.rs:141-146`）落进转写 —— **一个 48h 会话的转写里，操作者无法从摘要行分辨「人停的」还是「预算停的」**。
   这不是致命，但对「48h 无人值守」的复盘是实质损失。

2. 🟡 **`turn_count` / `meta.turns` 混计用户回合与复核回合**（设计已记，`design.md` §4.7 / ADR-0027 Consequences）。
   影响面：状态行数字、`--resume` 后读到的 `meta.turns`。无按回合计费，影响可控，但语义上「用户说了几句」不再等于 `turns`。

3. 🟢 ②的「只问一次」用二态枚举表达，比布尔量/计数器更自解释；这点优于候选甲。

## 5. 性能与可靠性

### 🔴 风险 1（最高）：② 给**几乎每一次用过工具的请求**都加一个完整回合

- 门槛是 `rounds >= 2`，即「本回合调用过工具」——这**正是绝大多数 coding 交互**（读一个文件、跑一条命令都算）。
- 后果：**日常单轮问答也被追问一次**「真的完成了吗」，代价 ≈ 一个空轮（候选丙估 ≈6k token-当量）+ 一次往返延迟。
  按候选丙自己的估算，对短回合是 **+50~60%** 成本/延迟。
- 设计写的是「复核比普通工具轮还便宜」——**单次确实便宜，但它是高频的**；把这个乘法做出来，才是完整结论。
- **且它不是本次故障的证据驱动项**：实证失败（`⚠ 10 rounds`）由 ① 直接解决；② 是**用户主动要求**的预防项，
  与本仓「不设计假想未来需求」的纪律存在张力（**用户已拍板，此处只作记录，不主张推翻**）。
- **若可动**：把门收窄到「回合**较长**」才复核（如 `rounds >= N` 或工具调用次数 ≥ M），
  可保住「长任务不被早收」的收益、同时消除日常噪音。这是一个可量化取舍，值得在实现前定 N。

### 🔴 风险 2：会话落盘在 48h 下是 O(n) 全量重写

- 实测 `crates/ys-session/src/jsonl.rs:128-131`：`append` = `push` + **`flush_to_file()`（tmp + rename 整文件重写）**。
  `replace_all` 的注释（`:142-152`）自陈「`append` 每次都全量重写整个文件」，并说压缩路径已避免 O(n²)。
- 48h ≈ 29k 轮 × 每轮 2~3 条消息 ⇒ **~10⁵ 次全文件重写**。压缩把文件大小压在几 MB 级，
  但**总 I/O 量级与「每 48h 十万次 rename」的耐用性/延迟**，设计完全未评估。
- **附带**：每次 append 都是 tmp+rename（原子，好），但**无 fsync** ⇒ 断电可能丢最后若干条。

### 🟡 风险 3：成本不可观测（被推迟的「软警告」其实是 48h 的必需品）

- 设计 §6 把「软警告 / 可观测性」列为「不做，记账」。但 48h 一次 ≈ **300M token-当量**（`design.md` §4.2）。
- **无人值守**场景下，「现在花到哪了、还有多久到预算」应当可见；数据源（`RunResult.rounds` / `usage`）**已经在手**，是加法。
- 建议：从「不做」提升为「本轮做」或至少「与 48h 预算同一批」。

### 🟡 风险 4：去掉轮数上限后，防打转只剩一条粗阀

- `MAX_CONSECUTIVE_ERRORS`（`basic.rs:14`）命中分支为空（`basic.rs:514-520`，只有注释）。
- ⇒ 「模型原地打转」只剩 **48h wall-clock 预算**这一条，且它**很粗**（小输出空转可持续数小时才到点）。
- 设计如实记账了这一点（好）；但应明确写出**这是一次「用一个更粗的阀换掉一个更细的阀」的交换**，而不是「没损失」。

### 🟡 风险 5：重试不提供「停服容忍」

- 有界退避总等待 ≤ ~60s（5 次、cap 30s）。⇒ **超过约一分钟的 provider 故障仍会终止 48h 回合**。
- 这是必要的界，但要在设计里写明**重试解决的是「抖动」而不是「停机」**，免得使用者误以为 48h 无人值守已稳。

### 🟡 风险 6：48h 数字本身是**估算**，无原型验证

- `design.md` §4.2 的「3k–29k 轮」全部源自**单一实测样本**（`10 rounds / 60.9s`，读密集型任务）。
- 该样本的每轮耗时在 bash 偏重任务上可能差 3 倍以上；① 的默认值、② 的成本、③ 的超时阈值都建立在这个估算上。
- 本技能一贯建议（`design.md` §6 也自陈）**先 prototype**——本设计**尚未**做。

### 🟢 站得住的部分

- 背压/内存：两回合**顺序**执行，峰值不叠加；这个推理正确。
- 「只在未吐 delta 时重试」这条规则直接封死「重复输出」，是正确的硬规则。
- `system` / `tools` 不动、复核只走 `messages` 尾部：与缓存前缀经济学一致。
- 「只问一次」由结构（`TurnKind` 早退）保证，删掉即测试变红：变异可测。

|---|---|---|---|---|

## 7. 改进建议（分层）

### 易修复（改文档即可）
1. **更新 `design.md` §5 不变量 #1**：不再声称「零新协议变体」；补一节说明 UI 修复的形态与它所需的协议/UI 改动。
2. **把「成本/时长可观测」从 §6「不做」移到「做」**（数据源已在手，属加法）——48h 无人值守下它是必需品。
3. **补 §8**：`-p` / `--json` 在 wall-clock 预算触发时的**退出码**与 stderr 措辞。
4. **写明 ③ 的边界**：重试治「抖动」不治「停服」；`ModelError` 无结构是长期既成事实。
5. **写明 ①②③ 是一次「细阀换粗阀」的交换**（去掉轮数上限的代价），而非无损失。

### 需讨论（影响行为，需拍板）
6. **②的门是否收窄**（例如 `rounds >= N` 或工具调用数 ≥ M 才复核），以保护日常交互的延迟与成本。**建议在实现前定 N**。
7. **UI 修复的形态二选一**：(a) 零协议改动——在 `apply_event` 的非回显 `UserMessage` 分支同时置 `is_turning`，复核仍显示为**用户行**（接受语义瑕疵）；
   (b) 新增区分信号（`Outbound` 变体或 `AgentEvent` 字段），把它渲染成 **System 行**——**打破不变量 #1**、blast radius 进 `ys-protocol`/`ys-tui-coding`。
8. **`Cancelled` 三义是否拆开**：加 `StopReason::BudgetExhausted` 需改 `BasicLoop`（一次爆炸半径交换）。若不拆，接受「摘要行分不出人停/预算停」。

### 架构级（超出本设计，记账 + 另立）
9. **会话落盘从「每次 append 全量重写」改为追加 + 周期性压实**：48h 下 O(n) 重写的累积代价未被任何设计覆盖。
10. **`MAX_CONSECUTIVE_ERRORS` 空分支的处置**：要么实现、要么删除常量（留着一个空的守卫比没有更糟——它给人虚假的安全感）。
11. **`llm-api-unavailable` 的两个完整性缺口**（200 + 非 SSE 错误体、无 `[DONE]` 的半截流）：48h 下**静默丢工作**，
    比缺重试更危险，应尽快单独设计（本设计已记账）。

## 8. 对「是否可以先实现」的建议

- **① 与 ③ 可以先做**：落点干净、判据明确；③ 注意本环境可能无法跑 TCP 验收测试。
- **② 建议先定两件事再动手**：(a) 门槛是否收窄（建议 #6）；(b) UI 修复形态（建议 #7）——这两者都改设计与测试面。
- **48h 的宣称需要一次 prototype**（哪怕是把现有 e2e 任务跑到远超 10 轮，量出真实的每轮耗时与压缩次数），
  否则 ① 的默认值与 ②/③ 的成本结论都建在一个样本上。
