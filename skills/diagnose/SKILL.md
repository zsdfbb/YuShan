# Diagnose

针对疑难 Bug 的规范化方法。只有在有明确理由时才能跳过某个阶段。

在探索代码库时，使用项目的领域词汇表建立相关模块的清晰心智模型，并检查你正在接触的区域的 ADR。

## 阶段 1 — 构建反馈回路

**这是核心技能。** 其他都是机械操作。如果你有一个快速、确定性、可被 agent 运行的通过/失败信号来判断 Bug，你就能找到根因 —— 二分法、假设检验和打日志都只是消耗这个信号而已。如果没有这个信号，再怎么盯着代码看也没用。

在此投入不成比例的精力。**要激进。要有创意。拒绝放弃。**

### 构建方式 —— 大致按此顺序尝试

1. **失败的测试** —— 在能触达 Bug 的任意接缝处：单元测试、集成测试、端到端测试。
2. **Curl / HTTP 脚本** —— 针对正在运行的开发服务器。
3. **CLI 调用** —— 使用 fixture 输入，将 stdout 与已知正确的快照进行比对。
4. **无头浏览器脚本**（Playwright / Puppeteer）—— 驱动 UI，在 DOM/控制台/网络上做断言。
5. **回放捕获的 trace。** 将真实的网络请求/负载/事件日志保存到磁盘；在隔离环境中通过代码路径回放。
6. **一次性测试框架。** 启动系统的最小子集（一个服务，mock 依赖），通过单个函数调用执行 Bug 代码路径。
7. **属性 / 模糊测试循环。** 如果 Bug 是"有时输出错误"，运行 1000 个随机输入寻找失败模式。
8. **二分测试框架。** 如果 Bug 出现在两个已知状态（commit、数据集、版本）之间，自动化"在状态 X 启动、检查、重复"流程，以便使用 `git bisect run`。
9. **差异循环。** 将相同输入分别通过旧版本和新版本（或两种配置），比对输出。
10. **HITL bash 脚本。** 最后的手段。如果需要人工点击，用 `scripts/hitl-loop.template.sh` 驱动**他们**，使循环仍然结构化。捕获的输出反馈给你。

构建正确的反馈回路，Bug 就解决了 90%。

### 迭代优化循环本身

把循环当产品对待。一旦你有了**一个**循环，问自己：

- 能不能让它更快？（缓存设置、跳过无关初始化、缩小测试范围。）
- 能不能让信号更精确？（针对具体症状做断言，而不是"没崩溃"。）
- 能不能让它更确定？（固定时间、设置随机种子、隔离文件系统、冻结网络。）

一个 30 秒的不稳定循环比没有循环好不了多少。一个 2 秒的确定性循环是调试的超级武器。

### 非确定性 Bug

目标不是完美的复现，而是**更高的复现率**。循环触发 100 次、并行化、增加压力、缩小时间窗口、注入 sleep。一个 50% 概率复现的 Bug 是可调试的；1% 则不可 —— 持续提高复现率直到可调试为止。

### 当真的无法构建循环时

停下来，明确说出来。列出你尝试过的方法。向用户请求：(a) 能复现该问题的环境访问权限，(b) 捕获的工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产环境探测工具的许可。**不要**在没有循环的情况下进行假设。

在拥有自己确信的循环之前，不要进入阶段 2。

## 阶段 2 — 复现

运行循环。观察 Bug 出现。

确认：

- [ ] 循环产生的失败模式是**用户**描述的那个 —— 而不是恰好在附近的另一个失败。错误的 Bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或者对于非确定性 Bug，复现率高到可以进行调试）。
- [ ] 你已捕获确切的症状（错误信息、错误输出、缓慢的时间），以便后续阶段验证修复是否真正解决了问题。

在复现 Bug 之前不要继续。

## 阶段 3 — 假设

在测试任何假设之前，生成 **3–5 个排序后的假设**。单一假设生成会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：说明它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 Bug 消失 / <改变 Z> 会让 Bug 更严重。"

如果你无法说明预测，这个假设只是一种感觉 —— 要么丢弃它，要么完善它。

**在测试之前将排序后的列表展示给用户。** 他们通常拥有能立即重新排序的领域知识（"我们刚刚部署了一个修改 #3 的变更"），或者知道已经排除的假设。便宜的检查点，能省大量时间。如果用户不在，不必阻塞 —— 按照你自己排序继续推进。

## 阶段 4 — 探测

每个探测必须对应阶段 3 中的特定预测。**一次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查** —— 如果环境支持。一个断点胜过十条日志。
2. **有目标的日志** —— 在能够区分假设的边界处添加。
3. 永远不要"全部打日志然后 grep"。

**为每条调试日志打上唯一前缀标签**，例如 `[DEBUG-a4f2]`。最后的清理只需一次 grep。未标记的日志保留；已标记的日志删除。

**性能分支。** 对于性能回退，日志通常是错误的。取而代之：建立基线测量值（定时框架、`performance.now()`、性能分析器、查询计划），然后进行二分。先测量，再修复。

## 阶段 5 — 修复 + 回归测试

**在修复之前**编写回归测试 —— 但前提是存在**正确的接缝**。

正确的接缝是指测试在调用点处模拟了**真实的 Bug 模式**。如果唯一的可用接缝太浅（需要多个调用者的 Bug 却只有一个调用者的测试，无法复现触发 Bug 的调用链的单元测试），回归测试放在那里会产生虚假的安全感。

**如果没有正确的接缝存在，这本身就是一个发现。** 记录下来。代码库架构阻止了 Bug 被锁定。将此标记为下一阶段的问题。

如果存在正确的接缝：

1. 将最小化的复现转化为该接缝处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始（未最小化的）场景重新运行阶段 1 的反馈回路。

## 阶段 6 — 清理 + 事后分析

在宣布完成之前必须完成：

- [ ] 原始复现不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或已记录缺少接缝的问题）
- [ ] 所有 `[DEBUG-...]` 探测代码已移除（`grep` 该前缀）
- [ ] 一次性原型已删除（或移至明确标记的调试位置）
- [ ] 结果证明正确的假设已在 commit / PR 信息中说明 —— 让下一个调试者学习

**然后问：有什么本来可以预防这个 Bug？** 如果答案涉及架构变更（没有好的测试接缝、调用者关系混乱、隐藏的耦合），将具体内容移交给 `/improve-codebase-architecture` 技能。在修复**之后**而不是之前提出建议 —— 你现在拥有的信息比开始时更多。
