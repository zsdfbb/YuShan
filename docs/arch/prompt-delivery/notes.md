# 把项目约定送到模型面前的通道与成本

> 日期：2026-09-23。缘起：把「注释只写当前设计」这条规则加进 `AGENTS.md` 之后，追问
> 「能不能由 coding agent 在**写代码那一刻**主动提示，而不占 AGENTS.md 的每轮前缀」。
>
> **状态：未决，仅记录。** 结论部分已稳定；落点选择待定。

---

## 1. 结论先行

1. **「每轮注入」是最贵的形态，不是最便宜的** —— 比常驻稳定系统提示贵约 **10 倍**。
2. 决定落哪一档的判据是 **「这段文字是不是常量」**，不是「想不想更主动」。
3. 「注释只写当前设计」是**常量** ⇒ 该**常驻**。而常驻**放哪**（系统提示 vs 工具描述）**成本同级**，
   差别只在**文本邻近性**。
4. 真正的未决项只有一个：**产品内置 vs 项目可配**（§5）。

---

## 2. 成本结构（核心）

以「一条 443 est token 的规则」为例：

| 形态 | 缓存 | 每轮成本 |
|---|---|---:|
| 常驻在**稳定的** system / tools 里 | **命中（0.1×）** | **~44** |
| 每轮注入到 `messages` **尾部** | **不命中（1.0×）** | **443** |
| 每轮改 `system`（如塞时间戳） | **不命中（1.0×），且整段前缀一起废** | **全量** |

**为什么尾部注入不命中**：缓存是**字节前缀**。尾部内容每轮都是**排在最后的、全新的** token ——
前面再长也盖不住它。（DeepSeek 官方原话：*"only requests with identical prefixes
(**starting from the 0th token**) will be considered duplicates"*。）

**两个附带坑**：不删旧的 ⇒ 上下文每轮涨 443、且模型看到 N 份副本；
删旧的 ⇒ **删除点之后的缓存全废**。两头都堵。

> ⇒ **「每轮注入」的唯一正当理由是「内容必须每轮变」**（时间戳 / todo 状态 / 记忆召回）。
> **内容不变却注入 = 纯浪费。**

### 2.1 ⚠️ 对 ADR-0021 决策 1 的修正

ADR-0021 决策 1 写着：

> 「若将来做『每回合注入』，**注入必须走 `messages` 尾部，绝不改 `system`**。`system` 是每轮
> 整块重发的前缀，动它等于每轮废掉缓存。」

**那条结论仍然对** —— 改 `system` 确实是三者中最差的。但它**只比较了两种注入形态，漏了第三档**：
**稳定的常驻**。对**常量**文字，常驻比尾部注入**便宜一个数量级**。

⇒ 补一条判据（先问顺序）：

```
这段文字是不是常量？
  ├─ 是 ⇒ 常驻（系统提示 / 工具描述），并选好「离动作多近」
  └─ 否 ⇒ 才谈注入，且必须走 messages 尾部（绝不改 system）
```

## 3. 四个候选落点

| 落点 | 位置 | 缓存 | 每轮 | 时机 |
|---|---|---:|---:|---|
| `AGENTS.md`（现状） | 埋在 ~11.7k 系统提示里的一行 | 命中 | ~44 | 太早（离动作最远） |
| **`edit` / `write` 的 `spec().description`** | 紧挨「要改文件」的参数 schema | 命中 | **~4** | **生成内容之前** ✓ |
| 每条 skill 的目录行 | 系统提示**末尾**一行，正文按需载入 | 命中 | ~6 | 触发**不可靠** |
| `edit` / `write` 的**工具结果** | 结果尾部 | 命中 | 低 | **文件已写完** ✗ |
| ~~每轮尾部注入~~ | 最贴近动作 | **不命中** | **443** | 每轮 |

**一句话**：`edit` / `write` 的工具描述是唯一同时满足「**写在之前** + **缓存命中**」且位置较近的落点。

**但要精确**：它与系统提示**成本同级**，且**两者都在稳定前缀里、每轮都在场** —— 差别是
**文本邻近性**（模型读到「要改文件」的参数时紧挨着它）而不是「只在那一刻出现」。
这是**注意力层面的软优势**，不是机械优势。别把它说成后者。

**本仓已在这个通道放纪律**（只是不在 `edit` 上）：`webfetch` 的 `spec().description` 里明写
「别重复抓同一 URL」「带 `prompt` 是多一次模型调用」。同样的手法，换个工具而已。
而 `edit` / `write` 的描述现在是**一行、零纪律**：

```rust
ToolSpec::new("edit",  "Edit files with precise or fuzzy text matching. Supports batch edits.", …)
ToolSpec::new("write", "Create or overwrite files. Automatically creates parent directories.", …)
```

## 5. 未决项：产品内置 vs 项目可配

工具描述属**产品级**（`edit` / `write` 在 `adapters/tools-basic`）⇒ 写进去 = 把一种文风偏好
**强加给所有用户的项目**。

| | 做法 | 代价 |
|---|---|---|
| **a** | 产品内置一条**通用**注释纪律 | 所有项目共享；但与「**不是自带全部功能的完整 Agent 产品**」的自我定位有张力 |
| **b** | 项目可配（项目提供文字，YuShan 附到 `edit`/`write` 的描述上） | **新配置项**；`ToolSpec` 是编译期构造的，要加运行期来源；ADR-0014 会问「**第二个消费者是谁**」 |

**倾向 a，但文案限定在「通用好注释」而非「本仓的规矩」** —— 那样它就不是文风强加，
而是产品该有的一条工程纪律。成本上它是白给的：~150 B 进工具表，命中缓存后每轮 **~4 当量**。

## 6. 另两个已在库、但本记录**未采用**的通道

**① 测试（源码扫描）** —— 守规则的**机械那半**（「不写什么」的词表），**零常驻成本**。
- 本仓有强先例：`apps/coding-agent/src/toolset.rs:382` 的 `include_str!("toolset.rs")`、
  `adapters/tools-web/tests/contracts.rs` 扫 5 个源文件。
- ⚠️ **两处软肋**：词表是启发式的（实测有**假阳性**「从一开始就是 true」被误判成叙事，
  与**假阴性**「裸 `pi`」两字母不敢列）；`include_str!` 到不了全仓（先例是显式列文件），
  要全仓扫得走**运行期遍历**。
- 另一个判断：本仓既有的源码扫描测试守的是**设计不变量**（如「本模块只产出文案，打印归 main」），
  不是**文风偏好**。为口味建测试是个立场问题。

**② skill（ADR-0019）** —— 一行目录 + 正文按需载入。
- 成本 ~6/轮，比 AGENTS.md 便宜。
- ⚠️ 但**触发不可靠**：写注释时模型不会主动去载一个「注释风格」skill。
