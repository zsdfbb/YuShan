# explore-speed — 墙钟成本模型与杠杆排序

> 日期：2026-10-16
> 性质：**实证分析**（承接 [`context.md`](./context.md) 的现状与 [`research.md`](./research.md) 的同类对照，
> 并**修正两者共同的成本模型**）。
> 方法：`tmp/exp` 的 15 条 `--json` 事件流（**212 个有工具调用的轮**）+ 源码直读 + 一条新增的变异验证用例。

## 0. 一句话

**墙钟 ≈ 轮数 × 每轮模型耗时；工具执行是毫秒项。**
`research.md` §9 那条建议（工具批按连续只读段并行）**作用在毫秒项上，天花板 ≈ 0** —— 本文把它的定位改为结构清理。

（2026-10-16 实测校正，见 §6：每轮模型耗时里 **ttft ≈ 80%**、生成 ≈ 19%、**工具 ≈ 1%**。  
⇒ 固定开销是**每轮一次的 prefill + 排队**，与工具、与轮内并发都无关。）

## 1. 成本模型

```
一轮墙钟 = 模型往返（prefill + thinking + 生成） + 工具执行
                    ↑ 秒级                        ↑ 毫秒级（本地只读）
```

`context.md` 早已写下同一判断（「本地只读工具是毫秒级，一轮的开销几乎全是一次模型调用」），
但它的范围章节仍把「减少轮数」与「提高并发度」并列 —— 本文说明后者不构成杠杆。

**三个乘数，只有前两个值钱：**

| 乘数 | 量级 | 现有控制力 |
|---|---|---|
| **每轮模型耗时** | 秒级（主导） | **零**（无任何思考预算控制；缓存命中率不可见） |
| **轮数** | 线性放大 | 提示词 / 开局信息 / 参数面 |
| 工具执行 | 毫秒（只读）；**分钟级**（真命令） | 并行度只作用于前者 |

> 「分钟级真命令」在**通用**口径下指：项目自己声明的构建 / 测试 / 包管理命令。
> 本仓样本里恰好是某个具体工具链的命令，但结论不依赖它 —— 判据只是「同一条命令字符串是否被重复执行」。

## 2. 实测（`tmp/exp`，212 轮 / 15 次运行）

| 指标 | 值 |
|---|---|
| 一轮 ≥2 个调用的轮 | **165 / 212 = 78%** |
| 其中形态为 **`bash bash`** | **123 / 165 = 75%** |
| 每轮调用数分布 | 1×47 · 2×145 · 3×15 · 4×2 · 5×1 · 6×2 |
| **纯读取轮**（整轮只读文件/看目录） | **69 / 212 = 33%** |
| 分钟级真命令 | 11 次（集中在两个长运行里） |
| 按工具声明切段的收益轮 | **4**（另有 6 轮本就全只读、今天已并行） |
| 若额外承认「只读命令的 bash」 | **50**（另 40 轮只有这条能拿到） |

**两个关键对照**（同一模型、同一工具面、同一仓库，只换提示）：

| 提示 | 轮数 |
|---|---|
| **可枚举**（三个子任务，明说"三个结果一起给我"） | **2–3** |
| **开放式**（"这个仓库接下来该补什么"） | **26–66** |

⇒ **轮数由「信息需求能否事先确定」决定，不由工具吞吐决定。** 可枚举时模型一轮全要；
开放时它必须先自己构造"该看什么"的清单，而构造清单本身要花步数。

**最长一次运行（66 轮）的逐轮分类**：

| 类别 | 轮数 |
|---|---|
| 引入了新文件（有效收集） | 40 |
| 未引入任何新文件（多为同一文件的另一段） | 26 |
| 命令原样重复 | 0 |

其中约 12 轮（18%）花在**排查工作区脏状态**（哪些文件被改、失败是否早已存在）。

## 3. 结果降级的实际行为（实测 + 新用例）

`crates/ys-loop/src/turn_budget.rs` 的回合级闸门，经代码直读与新增用例确认：

- **保护条件是「是会话最新的一条消息」**（`turn_budget.rs:121` 的 `idx == last`），
  而最新那条恒为本轮刚追加的工具结果消息。
- ⇒ **当轮的大批量结果完整保留**；**下一轮再追加一条之后，它就被削成头部 + 续读指针**。
  **保质期 = 两次模型调用。**
- 降级标记**在带内**（写进回喂给模型的内容），故模型**看得见**自己被削过。
- 降级经 `replace_all` **写回会话**（`basic.rs:772`），是**持久**的，不是每次请求临时算。

**新增用例**：`plan_elisions_protects_only_the_newest_message`（`crates/ys-loop/src/turn_budget.rs`）——
两条断言分别钉住「当轮不减」与「下一轮才削」。
**变异已验证**：把 `idx == last` 改成 `idx == messages.len()` ⇒ 3 个用例变红（含本条），恢复后全绿。

> ⚠️ **尚未验证的推论**：既然标记在带内、模型看得见，那么「一次要多 ⇒ 下轮被削 ⇒ 改成小步取」
> 这条**行为塑造**是可能发生的，但**本文没有证据**。验证方法：在一个会话里故意制造一次降级，
> 比较降级**前后**的平均每轮调用数。

## 4. 对 `design.md` 的定位修正

`design.md` 设计的「连续只读段并行 + 串行屏障」本身**结构正确**（对齐同类做法、只快不慢、
两条退化路径逐字节不变），**建议保留并实施**；但它的**理由要改**：

- 旧理由「97% 的多调用轮拿不到并行」**是对的但不相关** —— 那些轮省下的是**毫秒**。
- 新理由：**结构清理**，不是提速。真实收益面 4 轮（`research.md` §9 的 2% 量级）。

**中等**
8. 上推理预算开关（provider 侧参数）。
9. 把前缀缓存不变量写成断言（行为已对，但没有测试拦得住后人加一段易变内容）。
10. 同一条昂贵命令不连跑两次（判据：命令字符串相同）。

13. 开局布局快照 —— 有两份「别做」的先例（默认关 / 明确拒绝）。
14. 相位词 + 轮进度可见性 —— 零风险、改善等待体感。

## 6. 实测（2026-10-16，逐轮读数落地之后）

读数落点：`apps/coding-agent/src/round_clock.rs`，每条事件流经消费者时按
`RoundStarted → 首个模型增量 → 末个模型增量 → 首/末个 ToolResult` 切段，
写进 `~/.yushan/logs/yushan.log`：

```
round={n} ttft_ms={} gen_ms={} tools_ms={} total_ms={}
turn={n} rounds={} elapsed={}s cumulative_rounds={} budget_remaining={}s cache_hit={} cache_miss={}
```

**TUI 与 `-p` / `--json` 两条入口同格式**（前者在 `app_loop` 的事件泵，后者在 `main::consume_events`）。

三次真实运行（`opencode-go` / `deepseek-v4.1-flash`）：

| 运行 | 轮 | ttft_ms | gen_ms | tools_ms | total_ms |
|---|---|---|---|---|---|
| A 读一个文件并作答 | 1 | 2661 | 220 | 0 | 2881 |
| | 2 | 1823 | 417 | 0 | 2241 |
| B 数各 crate 的 .rs 文件 | 1 | 3165 | 788 | 104 | 4058 |
| | 2 | 1828 | 861 | 0 | 2689 |

**四轮的合计切分**（11869 ms）：

| 段 | 合计 | 占比 |
|---|---|---|
| **ttft**（排队 + prefill） | 9477 ms | **≈ 80%** |
| **gen**（思考 + 解码） | 2286 ms | ≈ 19% |
| **tools** | 104 ms | **≈ 1%** |

⇒ **墙钟 ≈ 轮数 × (每轮 ttft ≈ 2.5s) + 生成**。

**这三次实测把第 1 节的成本模型坐实了**：工具执行占 **1%** —— 并行度那条线（`design.md` 的分段准入）
天花板确实 ≈ 0，可以正式关闭。真正的固定开销是**每轮一次的 prefill + 排队**。

**两个附带读数**：

- **思考是流式发出的**（一次 `--json` 运行里 27 条 `ModelThinkingDelta`）⇒ `ttft` 里**不含**思考，
  它是货真价实的「排队 + prefill」；思考时间落在 `gen` 里。
- **该 provider 不上报 prompt 缓存**：`input_tokens ≈ 15k/轮`，但两个缓存字段恒为空。
  读数据此归为 `cache_hit=-`（**没有读数**），而不是伪装成「0% 命中」——
  见 `round_clock.rs::turn_cache` 的两条 `None` 路径。
  ⚠️ 因此「缓存有没有生效」在这条 provider 上**仍然测不到**。
  §6.1 的逐轮序列给的是**反证**：短运行里 `ttft` 跨轮不下降
  （`2579 → 2823 → 1819`、`2681 → 2819 → 3081`），长运行里也没有衰减趋势。

## 7. 外部对照：同一条 t4 提示 vs codex（2026-10-16）

`scripts/codex-t4-compare.sh`（codex 侧）+ `e2e_bench.rs` 的 `exp/t4`（我们侧）。
两侧**分开跑、不并发** —— 打同一个网关，并发会互相抬高延迟。

| | **codex 0.160.1** | **我们** |
|---|---|---|
| **墙钟** | **128 s** | **291 s** |
| **轮（模型往返）** | **≈ 6** | **33** |
| 工具调用 | 33 | 60 |
| **每轮工具调用** | **≈ 5.5** | **≈ 1.8** |
| **每请求输入 token** | **~39k** | **~39k** |
| 输入 token（累计） | 236,411 | 1,286,802 |
| 输出 token | — | 15,664 |

**我们慢 2.3×、输入 token 多 5.4× —— 而后者几乎全部来自轮数。**

注意「每请求输入」那一行：**两边差不多（都 ~39k）**。总输入差 5.4 倍，
是 `39k × 33` 对 `39k × 6` —— **纯粹的轮数差**，不是"我们每次发得多"。

⇒ **根因是每轮做的工具调用数**：我们 1.8，codex 5.5。我们**把一个决策步拆得太细**。

> ⚠️ 由此收回 `research.md` §3.1 与本文早先的一句判断：「78% 的多调用轮 ≥2 个调用」
> 曾被当作"模型已在积极成批"的证据 —— **标准定低了**。`≥2` 不是成批；同类是 5.5。
> （也重新解释了 `bash bash` 占主导：那不是成批，是"一轮干两件小事"。）

codex 的轮数由 stderr 的 `codex` 发言标记推出（4/10/5/9/4 个 exec 分属 6 次发言）。
**交叉校验**：其冒烟测试报 `tokens used 9,385`（≈ 它的固定前缀）—— 若它真跑了 33 轮，
总输入至少 `33 × 9.4k = 310k > 236k`，**自相矛盾** ⇒ 轮数确实少。

输入 token 的构成（我们的数）：`1,286,802 ÷ 33 轮 ≈ 39k/轮`，固定前缀实测约 15k ⇒
**前缀只占每轮输入的 ~38%，其余 ~62% 是累积的会话历史**。
⇒ 前缀瘦身的天花板是输入 token 的 38%（缓存若生效还要再打折）；**但轮数才是乘数**。

### 四条保留（缺一不可）

1. **各只跑了 1 次**。同一条 t4 我们两次运行是 **33 轮 / 246 轮** —— 方差大到单次对比只算方向性证据。
2. **token 口径可能不同**。codex 报的 `tokens used` 在 OpenAI 生态里通常**不含命中缓存的部分**；
   我们那个 1.29M 是**未经缓存折算的原始输入**。⇒ 5.4× 可能被高估，但我们**不知道缓存命中了多少**。
3. **思考档位没对齐**：codex 是 `reasoning effort: high`；我们**没有任何控制**（全仓零）。
4. codex 是另一个产品：不同的系统提示、不同的工具面、不同的编排。

## 8. 为什么每轮只发 ~1.8 个调用：三个候选

链条（§7 之后）：

```text
墙钟 ≈ 轮数 × 每轮耗时            （每轮 ≈ ttft 2–3s + gen，工具可忽略）
轮数 = 决策步数 ÷ 每步工具调用数   （我们 1.8，同类 5.5）
```

⇒ **要动的是「让模型每轮多要几个」**。但在改任何东西之前，先答一个问题：
**它为什么不这么干？** 三个候选，**可分辨**：

| # | 候选 | 判别性预测 | 怎么测 |
|---|---|---|---|
| 1 | **不知道可以** —— 提示词没给尺度。现状 guideline 只说 *"send several tool calls in one message"*（`apps/coding-agent/src/prompt.rs:229-233`），**从不说"几个"** | 给出**具体尺度**后，每轮调用数上升 | 同一组提示的前后对照 |
| 2 | **知道但不敢** —— 回合级降级闸门（§3）会削掉批量结果，且**标记在带内**（模型看得见）⇒ 学会了小步取 | 在一次会话里**故意制造降级**后，该会话后续每轮的调用数**下降** | 逐轮调用数序列 |
| 3 | **不需要** —— 探索本身有依赖链：第 N 轮才知道第 N+1 轮要读什么 | 「第 N+1 轮的目标路径**出现于**第 N 轮的工具结果」的比例**很高** | 从 `tmp/exp` 的 212 轮事件流**离线算，零成本** |

**候选 3 应当先答**：它零成本、且它的答案会**约束**另外两个 ——
若依赖链本就长，则"让它一次多要"的上限本身就很低，改提示词的天花板也就不高。

（三者不互斥，可能并存；实验设计要能各自定位，不能只给一个总前后对照。）

### 8.1 候选 3 已答（零成本，`tmp/dependency_test.py`）

口径：本轮工具调用所指向的**路径**，是否在更早的**工具结果**里已经出现过。
判据落在 `tmp/exp` 的 212 轮上。

| 指标 | 值 |
|---|---|
| 带参数工具的轮 | 211 |
| 目标路径中**已见过**（任意更早轮） | 435（**52%**） |
| 目标路径中**从未出现过** | 407（**48%**） |
| 「整轮目标都在**上一轮**结果里」 | **2 / 211 = 1%** |
| 「整轮目标在**此前任意轮**就已见过」 | **57 / 211 = 27%** |

**读法**：

1. **依赖链是真的，但只解释约 3/4** —— 48% 的目标确实是真新的。
2. **约 27% 的轮整个都在重触已知路径** —— 那些路径在更早的结果里就已出现，
   理论上本可一并要掉。⇒ 这是「一次多要」那条杠杆的**上限：约省 27% 的轮**
   （33 轮 → ~24 轮）。
3. ⚠️ 但 27% 只是**上限**：路径早先"出现过"不等于模型当时**知道它需要**。
4. **且它离同类还差得远** —— 省掉 27% 只能到 ~24 轮，codex 是 **6 轮**。
   真正的差距在**单轮装多少**（5.5 vs 1.8），不在"有没有重复轮"。
   ⇒ 候选 1/2 仍是主战场，且它们要解决的是**单轮容量**，不是去重。

## 9. 固定前缀的构成：与 codex 的同题校准

**用同一句话**（"只回复两个字：收到"）跑两个实现，取**单轮**会话的 `input_tokens`
（`turns=1` ⇒ 这就是干净的前缀读数，不含历史）：

| | 输入 token |
|---|---|
| **codex** | **9,385** |
| **我们** | **14,953** |

**我们高 1.59 倍（+5,568）。** 顺带把估算器校准了：它估 ~15k，provider 报 14,953 —— **没有高估**。

构成（我们的数，估算口径）：

| 段 | token |
|---|---|
| `<project_context>`（AGENTS.md 整份） | ~4,834 |
| `<available_skills>` 目录段 | **~10,027** |
| 其余（基座 + 工具表 + guidelines + cwd） | 余量 |

**codex 的 9,385 装不下 10k 的目录段** ⇒ 同一份 56 个 skill（`~/.codex/skills` 与
`~/.yushan/skills` **逐字相同**），**它注入的形态远比我们省**：全程只读了 **1 个**
`SKILL.md`、**从未列出 skill 目录** —— 说明它那点"知道"很便宜。

### 9.1 我们为目录段付的价，兑现了吗

我们的形态是 **ADR-0019 的明文决策**（注入 `name` + `description` + `location`，
理由是"模型自主路线因此**恰好 1 次 tool round-trip**"），且 ADR 写死「**代码不替用户裁**」。
⇒ 这是一个**有意的交易**。那它是赚是赔？

零成本可测 —— 数真实会话里 `read` 过 `skills/*/SKILL.md` 的次数：

| | 次数 |
|---|---|
| 全部真实会话 | **8** |
| 其中 `diagnose` 3 / `arch-design` 2 / 其余各 1 | |
| **今天的全部基准运行** | **0** |

⇒ 历史总轮数约 400–700，**每轮固定 ~9.6k** ⇒ 为一个 skill 调用付了约 **50–80 万 token**。

**三条限定，缺一不可**：

1. 这**假定目录段未被缓存**。若缓存命中，金钱成本 ≈ 0.1×（但 prefill 时间是否也免，未测）。
2. ADR-0019 买的是**能力**（能自主发现并使用），不只看调用次数 —— 罕用的能力也可能值得有。
3. 本仓的 skill 型工作大多在别的工具里做，故**这里的低频不能外推到"产品被他人使用"的场景**。

⇒ 结论不是"删掉目录段"，而是：**这是一个可以用数据重新定价的决策，且同类存在更省的形态**。
