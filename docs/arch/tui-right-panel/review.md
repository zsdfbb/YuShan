## 改进建议

### 易修复（低风险快速改进）—— **F1/F2/F3 已全部应用**

**F1 —— 修 §3.1 的 `frame_areas`（R1，P0）｜✅ 已修**

原文档代码将纵向切分建在 `main`（已变窄的主列）上，且用 `main.width` 算 `input_height` ——
这正是决策 2 声称已消除的反馈环。修正后：

1. `Layout::vertical` 先在 `total`（整屏）上切分 ⇒ `input_height(app, total.width)` 入参不变；
2. 横向让位只作用于 `v[0]`（Chat 带）⇒ 侧栏高度 = Chat 高度。

并在两处加上「顺序不能反」的告警（`design.md` §3.1 代码注释 + 改造点表后），
因为先横切再竖切会以更隐蔽的形式复现同一缺陷。

**F2 —— 给 §5 的推送点补上真实的数据通路（R2，P0）｜✅ 已修（采 F2-a）**

设计说「复用本请求已构造的那份 `CodingView`，只替换 `panel` 字段」，但核实结果：

- `run_turn_chain`（`:1841`）整个函数体内**没有 `CodingView` 类型的局部量**（`rg` 只命中 `out_tx`/`tx`/`out` 的泛型参数）
- 视图在 `run()`（`:383`）里构造 —— 最近的一次在 `:548`/`:608`/`:646`/`:687`/`:713`，之后进 `run_turn_chain`，**出参只有 `TurnOutcome`**
- `TurnCtx`（`:1656-1693`）字段里**没有 `state_store`** —— 所以即使想现造也缺一块
- `todo_store`（`:473`）在 `run()` 里，**没传进** `run_turn_chain`

所以「复用」在物理上不成立。三条可行替代，按代价排序：

| 方案 | 做法 | 代价 |
|---|---|---|
| **F2-a（推荐）** | `run_turn_chain` 增加一个 `last_view: &mut CodingView` 形参，由 `run()` 传入；回合中只 `last_view.panel = ...` 后发 | `+1 形参`（已 16 个），但通路上最短；`state_store` 不需要 —— 只换 `panel` 一字段 |
| F2-b | 事件臂发**只带 `panel` 的最小事件**，让 UI 侧 merge | 破 `Outbound::View` 的「整表替换」语义（`app.rs:274`），要改 `apply_outbound` |
| F2-c | 回合中改调 `build_view_with_loop` | 设计已否（读 `Instant`/`state_store` 进热路径）；且 `ctx.agent` 被借走，`&Agent` 给不出来 |

另需补 `todo_store` 的传递：它今天活在 `run()`（`:473`），`run_turn_chain` 要读它做投影 ⇒ 同样加形参（或塞进 `TurnCtx`）。**这两处形参设计文档一个都没提**，是 R2 的实际体量。

**F3 —— `truncate_to_width` 的可见性（R3，P1）｜✅ 已修**

`truncate_to_width` 是私有 `fn`、`display_width` 是 `pub(crate)` ⇒ `apps/coding-agent` 用不了。
**选定：显示列截断改在 UI 侧做**（`draw_sidebar` 画每行时调一次）；app 侧只封「条数」与「字符数」。
理由：「字符数」与「显示列」是两个不同的量（CJK 一字 = 2 列），而只有 UI 知道内区宽。

### 需讨论（需要团队决策）

**F4 —— `SIDE_WIDTH = 30` 是否该改成「屏宽的一定比例」**

设计已明确「静态大小」是需求决定，我认可不当场翻案。但要记一笔：30 这个数在 100–140 列区间是好用的，在 80 列会让 Chat 内宽掉到 46（接近可读下限），在 60 列以下基本不可用。§10 已承认这一点。

若将来要改，`side_width()` 是纯函数 ⇒ 只改函数体，不扩散 —— 这一点设计做对了。

**F5 —— G7/G8 的用例怎么在「无 `CodingView` 可复用」的前提下写**

F2 若选 F2-a，G7 可以直接对 `run_turn_chain` 的 `out_tx` 断言「至少一条 `View` 且其 `panel` 是新的」。若选别的方案，用例形态会不同。**测试设计依赖 F2 的决策**，不能先写用例。

### 架构级（影响面大，需要跨 phase 规划）

无需 —— 本设计明确不动 `ys-protocol`、不建 trait/hook，没有架构级欠债。

## 可删除 / 可简化项（按收益排序）

| 机制 | 删除依据 | 删除风险 | 建议 |
|---|---|---|---|
| `FrameAreas.side: Option<Rect>` | 可用 `side.width == 0` 表达「关闭」 | 低 | **保留** —— `Option` 让 `draw_sidebar` 的调用点无条件化，比查宽度更清晰。不删 |
| `PANEL_RUNNING_MAX = 8` | 单回合派发上限是 16，8 是拍脑袋 | 中（去掉则极端情况下 16 行 × 120 字符进入每帧） | **保留**，但 §4 的理由「16 的一半」不算论证。建议改为「侧栏内区高上限」（40 行屏 ⇒ 20 行/栏，扣标题与 `+N` ⇒ 18），让常量与几何挂钩而非与派发上限挂钩 |
| `MAX_TODO_CONTENT_CHARS = 96` / `MAX_DESCRIPTION_CHARS = 120` | 已有 `PANEL_*_MAX` 条数封顶；字符上限是第二重 | 低 | **保留** —— 防单条超长（`MAX_CONTENT_CHARS=240` CJK 是 720 B）。但两者语义重复处应合并说明：一个管「多少条」，一个管「每条多长」，是正交的两维，文档该写成一张二维表而不是平铺列表 |
| `HandleEntry` 结构体（vs 直接 `(Weak, Arc<str>)` 元组） | 只有 2 字段、1 个使用点 | 低 | **保留** —— 命名字段比元组更可读，且 `Tuple` 做 value 会让 `retain(\|_, w\| w.strong_count()>0)` 变成 `.0.strong_count()`。不删 |
| `side_width()` 独立函数（vs 内联进 `frame_areas`） | 只有一个调用点 | 低 | **保留** —— 它承载两条实测结论的注释（`Length` 会抢宽），值得一个名字 |
| §5 的 300ms 节流 | 需求没提；一个回合最多 16 次派发，不节流也就 16 次快照 | 中（G8 覆盖） | **需讨论**：`PartialEq` 变化检测已经过滤掉「无变化」，节流只过滤「高频变化」。todo 的 `revision` 在一次 `apply` 里可能连跳多次（批量改），此时节流有价值。**建议保留，但理由改为「批量 apply 的合并」而非「与 TICK 同阶」** |

**唯一建议真正删除的**：无。设计的裁剪已是干净的 —— 三个候选的核心机制全部被正确拒掉，且每个都只保留了「思想」而非机制本身。

## 关于方法本身的一个提醒

本报告的价值集中在 R1/R2 两条 **P0**。二者都不是「这个想法不好」，而是「文档说的与代码/文档自身说的是两回事」：

- **R1** 是设计文档 §3.1 的代码与其 §1.2 结论互相矛盾 —— 照抄代码会重新引入设计声称已消除的缺陷。
- **R2** 是对代码可达性的断言未核实 —— 「复用本请求已构造的 `CodingView`」这句话在 `run_turn_chain` 的作用域里没有对应物。

这两类错误在**看起来自洽的设计文档**里最难发现，因为文档整体是通顺的。建议把「每个新增数据通路都必须指定其物理载体（哪个函数的哪个形参）」作为写设计文档时的固定检查项。

## 总体评价

**整体健康度：🟡 中等偏上。**

设计的**取舍质量很高**：几何收敛、三处复算合一、砍掉三个候选的过度设计、`Weak` 化让生命周期自然、入口封顶有两维上界。实测驱动的部分（50/50 舍入、`Length` 抢宽）是本次最有价值的产出，直接否掉了两个手算假设。

**最大风险**已处理：R1/R2 两条 P0 在本次复核中当场修进 `design.md` 与 ADR-0075。
保留记录的理由是——这两类错误（文档自身矛盾、可达性断言未核实）在**看起来自洽的设计文档**里
最难发现，值得当作写设计时的固定检查项。

**剩余待办**：
1. `PANEL_RUNNING_MAX = 8` 的论证应从「派发上限的一半」改为与**侧栏内区高**挂钩（见「可删除/可简化」）；
2. 300ms 节流的理由应改为「批量 `apply` 的合并」而非「与 `TICK_INTERVAL` 同阶」；
3. 进 `prototype` 验几何 —— §10 把「切换后滚动 / 鼠标命中 / 选区对齐」标为唯一正确性风险，判断准确。

界面验收仍必须靠实物：28 列内区能显示多少字，只有看到才知道（§10 最后一条）。
