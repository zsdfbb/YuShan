## 2. 决定性发现：设计骨架已被 ADR-0041 删除

这是本次分析最重要的一条，它把可行性直接判红。

### 2.1 事实链

| 时间 | 事件 | 证据 |
|---|---|---|
| 2026-09-15 | design plan 写定，骨架 = `Request::Prompt` 臂内包 `while let Some(msg) = pending.take()` | `design-plans/2026-09-15-follow-up.md:55` |
| 2026-09-15 → 10-17 之间 | **同一个骨架真的实现过**：`apps/coding-agent/src/follow_up.rs`（`should_review` / `TurnKind` / `REVIEW_PROMPT` / `REVIEW_MIN_ROUNDS`） | `git show 466ab11~1:apps/coding-agent/src/follow_up.rs` |
| **2026-10-17** | **ADR-0041 删除该文件与整个 `pending.take()` 循环**，并把「每次用户输入恰好跑一个回合」升为不变量 | `docs/adr/0041-remove-completion-review-turn.md`；`app_loop.rs:54`（不变量 ④） |
| 2026-10-22 | ADR-0047 说「follow-up 缺协议格」 | `adr/0047:184` |
| 2026-11-06 | 本分析 | — |

### 2.2 为什么这是硬冲突而不是「改改就行」

ADR-0041 的决策原文包含两条：

1. **删 `apps/coding-agent/src/follow_up.rs`** —— 与 follow-up 设计计划的落点**同名**
   （计划的 §3.4 要求「新增小模块（如 `apps/coding-agent/src/follow_up.rs`）」）。
   即：**这个文件名曾经被占用、用来实现另一种语义的追问，然后被显式删掉。** 现在要重新建它，
   必须说明「为什么这次不一样」，否则后人读 ADR-0041 会以为这是回退。
2. **`Request::Prompt` 臂由 `pending.take()` 循环收成单回合** —— 计划的 §3.1 正是要把它加回去。

### 2.3 更关键：`while` 循环可能仍是必要条件

ADR-0041 不只要「一个请求一个回合」，它还要**`emit_view()` 每个请求只跑一次**：

```rust
match req { ... }      // 各臂
`emit_view();`           // :972，请求处理完刷一次
```

现在 `Request::Prompt` 臂只调用 `run_turn_chain`（`app_loop.rs:570`），**指令条块**，
所以 `emit_view()` 天然每请求一次。

若按计划在臂内包 `while`（两次 `run_turn_chain`），则 `emit_view()` 仍只跑一次 ——
**状态行会停在第一次回合之后的读数上**。现有代码里有一个反证：自动起回合的两臂
（`Wake::SubagentReturned` / `Wake::BackgroundReturned`）都**各自手动补了一次 `build_view` + `send_or_flush`**
再 `continue`（`app_loop.rs:446` / `:503`），注释明说：

> 「本臂 `continue`，走不到循环尾部那次刷新 —— 否则状态行会停在自动回合**之前**的读数上」

⇒ 两条路：
- **A**：照那两臂的形状做（不包 `while`，而是**递归/重复调用** `run_turn_chain` 并各自补 view）
- **B**：包 `while` 但手动补 view

**A 与现有三条调用点同构，明显更优。** 计划里的方案 A 前提（`run_turn_chain` 可重复调用）
仍然成立，但**骨架要按 A 改**。

### 2.4 未受影响的部分

计划的**判断**全部仍然成立：

| 计划中的判断 | 现状核实 |
|---|---|
| 落点 `app_loop` 而非 `BasicLoop` | ✅ 正确（`run_turn_chain` 已是三条调用点的共用实现，`:1291`） |
| 零依赖环，不碰 `ys-loop` / `ys-protocol` | ✅ 正确（`TurnOutcome` / `RunResult` 就在 `app_loop` 里） |
| 检测用 HEAD 前后对比，不解析命令参数 | ✅ 正确（理由仍然充分） |
| 三样护栏（防套娃计数 / 默认关 / 非 git 静默） | ✅ 正确，且比原计划更需要 |

### 3.2 可维护性 🟡

| # | 检查项 | 判断 | 说明 |

### 3.3 可理解性 🔴

这是本设计**最严重的实际问题**：同一件事有四处**互相矛盾**的说法，且两两互不引用。

| 文档 | 说法 | 行 |
|---|---|---|
| design plan | 「`Prompt` 臂包个 `while` 就行，不碰协议」 | `:49-67` |
| ADR-0014 | 「只做 follow-up，不建 hook」（决策层，不提骨架） | `:24` |
| ADR-0041 | 「删掉 `follow_up.rs`，`Prompt` 臂收成单回合」 | 决策段 |
| `TODO.md` §B | 「不是缺实现，**是缺协议格**」 | §B 段 |
| ADR-0047 | 「follow-up 缺协议格，`Delivery{origin:System}` 补上」 | `:184` |

**四种说法两两冲突：**

- plan vs ADR-0041：包循环 **vs** 收成单回合（直接对立）
- plan vs `TODO.md`/ADR-0047：不缺协议 **vs** 缺协议格

而 `TODO.md` §B、ADR-0041、ADR-0047 **都不提这个 design plan**。只有
`input-delivery-latency/context.md:242` 提了一句「评估 ADR-0014 的落地」，语气是**待评估**。

⇒ 一个新人按顺序读这五份文档，会得到结论：**先做，然后别做，然后缺协议，然后不缺。**
这是必须修的文档债，与是否实现无关。

### 3.4 错误传播与处理完整性 🟡

| # | 检查项 | 判断 | 说明 |
|---|---|---|---|
| 1 | 失败路径都有处理 | 🟡 | `git_head` 返回 `Option` 已考虑；**但漏了「回合本身失败」** |
| 2 | 错误传播链清晰 | 🟢 | `TurnOutcome` = `Result<RunResult, LoopError>`，可判 |
| 3 | partial failure 有降级 | 🟢 | HEAD 检测不可用 → 静默跳过 |
| 4 | 错误不致资源泄漏 | 🟢 | 无资源 |
| 5 | 错误上下文足够 | 🟡 | 计划未规定失败时是否记 debug |

**缺口 ①（必须补）**：计划 §5 的测试只覆盖「HEAD 变了 / 没变 / 开关关 / 非 git」，
**没有一条覆盖「本回合失败或非正常收场」**。而 `run_turn_chain` 返回 `Result<(), AppLoopError>`，
外层 `Err` = UI 收摊、应直接退出；内层失败在 `TurnOutcome` 里。

⇒ 必须规定：**`StopReason::{Cancelled, Truncated, MaxRounds}` 时不追问。**
理由与 ADR-0041 撤掉完工复核的三道门一致（那里第 2 道门就是「只在 `Completed` 之后」），
且「用户中止永远赢」是本仓既有原则。**计划完全没提这条。**

**缺口 ②**：`AppLoopError`（UI 收摊）时 `run_turn_chain` 用 `?` 直接返回 ⇒ 追问不会发生，
这是对的，但**计划未写明**，实现时容易被写成 `let _ = ...` 吞掉。

### 3.5 并发安全性 🟢

| # | 检查项 | 判断 | 说明 |
|---|---|---|---|
| 1 | 共享状态有保护 | 🟢 | 追问在主循环单线程内串行，无共享 |
| 2 | 锁粒度合理 | 🟢 | 无锁 |
| 3 | 无死锁 | 🟢 | 无锁 |
| 4 | 异步路径竞态已考虑 | 🟡 | 见下 |
| 5 | 有并发测试 | 🟢 | 本来就没有并发 |

**竞态（低风险但真实）**：追问期间用户可能敲字。`Request::Prompt` 会排在 `request_rx` 里，
追问结束后才被消费 ⇒ **不会丢**，但顺序变成「用户先说的话排在追问之后」。
现有 `PendingResults` 用 `notify_one` 存 permit 处理同类问题；本设计没有对应机制。
**建议**：在文档里明确「追问期间的输入排队到追问之后」，这是可接受语义，但要说出来。

### 3.6 资源管理 🟢

无资源分配、无 FD、无连接。追问轮次有硬上限（护栏 ①，默认 1）⇒ 无膨胀风险。

**但**：`§3.3 护栏 1` 说上限默认 **1**，而 `§5 测试` 说「恰好追问 1 轮」。
两处一致，但**上限为 1 时「防套娃计数」是多余的** —— 一个 `bool` 就够。
这不是缺陷，但 `u32` + 上限的写法暗示「将来可调大」，而调大就会真的套娃。
**建议**：默认 1 时用 `bool`，并在注释写明「要调大必须重新论证防套娃」。

## 4. 性能与可靠性

### 4.1 性能模型 🟡

| 项 | 判断 | 说明 |
|---|---|---|
| 关键路径 | 🟢 | 追问 = 一次完整回合（可能多轮工具），成本已知 |
| 延迟预算 | 🔴 | **见缺口 ③** |

**缺口 ③（必须补，且可能是设计级）**：`run_turn_chain` 在**入口**算一次
`deadline = request_started + config.max_turn_duration()`（`app_loop.rs:1322-1323`），
注释明说「`deadline` 覆盖整条链」。

⇒ 若追问复用同一条链（方案 A 的「重复调用」），**追问回合的预算只剩主回合的残值**。
主回合跑满预算 ⇒ 追问**立刻**撞 deadline。

这不是 bug，但是**必须显式决定的语义**：
- 追问共享预算（省钱、防超时）⇒ 主回合跑满时追问被跳过
- 追问独立预算（保证追问能跑）⇒ 单个请求的总墙钟可达 2×`max_turn_duration`

**计划完全没提这一条。** 这是本设计最容易被忽略、实现时才发现的设计级决策。

### 4.2 故障模式 🟡

| 场景 | 行为 | 判断 |
|---|---|---|
| git 命令失败 / 非 git 仓库 | 静默跳过 | 🟢 已设计 |
| HEAD 检测到变化但文档无需改 | 追问一轮，模型回「无需改」 | 🟢 可接受（一次模型调用） |
| 追问回合又提交 | 护栏 1 挡住 | 🟢 已设计 |
| UI 收摊 | `?` 提前返回 | 🟡 未写明 |
| 主回合失败 | **未定义** | 🔴 缺口 ① |
| 预算耗尽 | **未定义** | 🔴 缺口 ③ |

### 4.3 可观测性 🟡

计划 §5 有一条「追问轮的 `Envelope.turn` 递增（消费者可见）」—— 好。
但 §6 的「UI 表现」仍是**待定**：状态行回合数会跳一格，是否需要在 `Envelope` 加标记。

现有 as-built 的答案是：自动起回合用 **`Role::Harness` 占位消息**（`app_loop.rs:1429` /
`subagent.rs:1229`），注释明确「这条输入由 harness 产生、用户没说过 —— 区分来源」。
⇒ **计划应直接采用这个既有约定**，而不是留作待定。追问的输入也应是 `Role::Harness`。
