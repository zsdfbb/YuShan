## 0. 结论先行

**整体健康度：🟡 可实施，但有 1 个 P1 矛盾必须先修文档。**

`/goal` 的形状是健康的 —— 净删 400 行、零新 crate、零 `ys-loop` 改动，判据落点与全仓既有纪律一致。
四个候选的对比也做得扎实（两条论据被事后核倒并记录在案，这比“选中了就完事”更有价值）。

设计里最尖锐的问题是**风险表的缓解措施与实现事实不一致**：R2 / R3 两处都把
“`Ctrl+C` / `/goal clear`”当作已有出口，但只有一半成立：

- **`Ctrl+C` ✅ 真的可用**（已实证：`Boundary::Abort` 在回合内的 `select!` 里被消费，
  `app_loop.rs:2057`；且 `QueueBoundarySource` 每回合新建，`app_loop.rs:1959`）。
  取消后该回合以 `Cancelled` 收场，命中断据 1 ⇒ 追问循环 `break`。**200 回合也能停。**
- **`/goal clear` ❌ 送不进追问循环**。`Request::SetGoal` 的消费点在顶层
  `match requests.recv()`，而整个追问循环在 `Request::Prompt` 臂内同步跑到底
  （已实证：`app_loop.rs:812-895` 区间零 `recv()`）。循环期间新 `Request` **不会被求值**。

> **⚠️ 本节后半条（“clear 不可用”）已在二次修订中推翻，见 §2.4。**
> 依据成立（循环内确实零 `recv()`），但**推论错了**：`/goal clear` 从来不需要
> “把 `Request` 送进循环”—— 它是**组合动作**，打断走 `Boundary::Abort`（回合内可达），
> 清目标走 `Request::SetGoal`（循环退出后必达）。原判断的隐含前提
> “clear 是一条必须进循环的 `Request`”本身是错的。

所以实际不影响“能不能停下来”，但影响“能不能**换成另一个目标**”——
而设计 §7 把它写成了到达出口，属于**文档缺陷**，必须改（要么实现轮询，要么删掉这个说法）。

> ⚠️ **本段结论已在二次修订中推翻，见 §2.4**：无需轮询、也无需删掉该说法 ——
> `clear` 拆成两个信道上的两个动作即可。第 22–24 行的事实依据仍成立。

其余维度以 🟡 为主，集中在“成本模型未量化”与“若干事实性断言与代码不符”。

## 2. P1（**原判，已被 §2.4 推翻**）：`/goal clear` 在追问循环期间不可达

> ⚠️ **本节保留为记录，结论已被 §2.4 取代。** 依据（循环内零 `recv()`）成立，
> 但推论错在隐含前提：把 clear 当成“必须送进循环的 `Request`”。
> 阅读时请直接跳到 §2.4。

### 2.1 事实

`app_loop` 主循环是 `match requests.recv().await { Request::Prompt(msg) => { …整个追问循环… } }`。
追问循环体在 `app_loop.rs:812-895`，其内部**不读取 `requests`**：

```
$ awk 'NR>=812 && NR<=895' apps/coding-agent/src/app_loop.rs | grep -n "recv()\|requests\."
  → 无：循环内不轮询 requests
```

`Request::SetGoal` 若按 §4 的定义加进同一个 `Request` 枚举，它的消费点是 `match` 的另一个臂 ——
而那个 `match` 在追问循环跑完之前**根本不会再被求值**。结论：

- ~~**`/goal clear` 送不进去**~~ —— **推论错误**。TUI 侧并不需要把它送进循环：
  打断投 `Boundary::Abort`（回合内可达），清目标投 `Request::SetGoal{None}`
  （循环退出后必达）。详见 §2.4。
- **`Ctrl+C` 可用**。这不是推断，是实证：`Boundary::Abort` 在回合内的 `select!` 分支被消费
  （`app_loop.rs:2057`），取消后该回合以 `Cancelled` 收场，命中断据 1 ⇒ 追问循环 `break`；
  且 `QueueBoundarySource` **每回合新建**（`app_loop.rs:1959`，`Abort` 标志位随回合作废）。
  因此 200 个回合也能停下来。

### 2.2 设计文档的措辞与事实不符

§7 R3 的缓解栏原文：

> **必须把 `Ctrl+C` 与 `/goal clear` 写进 `/goal` 提示文案**

R2 的出口栏：

> 出口：`Ctrl+C` / `/goal clear`

两者并列，读者会以为功能等价。**不等价**：`Ctrl+C` 能停，`/goal clear` 不能。
一期的 git 追问最多 1 次（`git_follow_up_used`）、回合链最长 2 个回合，所以
“循环内不消费 `Request`”从来不是问题；`/goal` 把它拉长到 200 个回合后，
用户可能想“任务跑了 50 个回合，目标其实选错了，换一个” —— 这个动作不存在。

**这不影响“能不能停下来”（能），但影响“能不能换方向”（不能）。**
把 R3 的缓解从 P0 降为 P1：文档必须改，但是否要改代码取决于你是否需要“任务中途换目标”。

### 2.3 建议（需讨论，二选一）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 循环内轮询** | 追问循环每回合开始前 `requests.try_recv()`，`SetGoal{text:None}` ⇒ `Stop(Aborted)` | 约 20 行；需处理“非 clear 的其它 `Request` 怎么办”（延迟到链尾？丢弃？）；与 `wake_rx` 赛跑要理清 |
| **B. 承认现状，改文档** | 保留“循环内不消费 `Request`”，把 R2/R3 的出口改成**仅 `Ctrl+C`**，并明说“换目标需先停下” | 零代码；但用户得先 `Ctrl+C`（舍弃当前进展）再重设 |

**我倾向 B**：`Ctrl+C` 已能止损，而 A 会引入“追问循环内消费 `Request`”这个新模式
（迄今所有 `Request` 都在回合之间消费，这是个干净的不变量）。**但无论选哪个，§7 的缓解栏必须改** —— 现在它暗示了两个出口。

> ⚠️ **本段（A/B 对比与“倾向 B”）已被 §2.4 推翻**：两个方案都不需要。
> 保留它是因为“`Request` 只在回合之间消费”确实是值得守住的不变量 —— 而 §2.4 的方案恰好守住了它。

## 2.4 二次修订：上面的 A / B 两难不成立

**本节推翻 §2.2 与 §2.3 的结论。** 依据（循环内零 `recv()`）无误，错的是**隐含前提**：
把 `/goal clear` 当成“一条必须送进循环里的 `Request`”。它不是。

### 真正的形状：一条命令 = 两个信道上的两个动作

| 用户动作 | 发的消息 | 信道 | 何时消费 | 效果 |
|---|---|---|---|---|
| `Esc` | `Boundary::Abort` | ② | **回合内** `select!`（`app_loop.rs:2057`） | 回合 `Cancelled` → 判据 1 → 断循环；**目标保留** |
| `/goal clear` | `Abort` + `Request::SetGoal{None}` | ② + ① | Abort 同上一行；`SetGoal` 等循环退出后到达 | 断循环**并且**作废目标 |

两条路用的都是**既有机制**，不需要在循环里轮询 `Request`，也不破坏任何不变量。
代码里已有同形先例：`Request::Compact && app.is_turning ⇒ 改投 Boundary::Compact`
（`events.rs:928-939`）。

### 剩下的真实风险：竞态窗口（不是“不可达”）

`run_turn_once` 开头会排空并**丢弃**残留 `Abort`（`app_loop.rs:1899-1905`，
有 `stale_abort_queued_before_first_turn_is_discarded` 守着）—— 因为 `Abort` 标志永久置位，
不丢会污染下一回合。若 `clear` 的 `Abort` 恰好落在两个回合之间，它会被丢弃，
该回合不被取消。

但关键区别：**`SetGoal{None}` 走信道 ①，在回合之间必达 ⇒ 目标一定被清掉。**
所以最坏结果是「目标已作废、当前回合多跑一会儿」，绝不出现「以为清了实际没清」。
这比原文说的「完全不可达」轻了一级。

### `Esc` 与 `clear` 的语义分工

这两个动作**不得混为一谈**，因为对应用户两种不同意图：

- **`Esc`**：这一回合停下，**目标还在**。用户想继续，再发一句话即可重新进入追问。
- **`/goal clear`**：停下**并且**认定这个目标作废。

若只提供 `Esc`，用户想换目标就得先丢当前进展再重设；若只提供 `clear`，
就丢掉了「暂停但不放弃」这个常见意图。两者都要有。

## 2.5 二次修订：提示键应为 `Esc`，不是 `Ctrl+C`

原文（§2.2、R2、R3）都把 `Ctrl+C` 当作说明书上的停止键。**改成 `Esc`**：

| | `Esc` | `Ctrl+C` |
|---|---|---|
| 段数 | 一段式 | **两段式**：第一次取消，第二次**退出进程**（`events.rs:594-603`） |
| 误触后果 | 空闲时只清输入框 | 任务中按两下 = **进程退出**，会话与内存中的目标状态全丢 |
| 有选区时 | 无影响 | 先当**复制**（`events.rs:580-586`） |
| 取消能力 | 同一个 `Boundary::Abort`（`events.rs:1020`） | 同 |

两者取消能力**无差别**，但一个跑了几小时的任务，用户看到卡住本能按两下 ——
`Ctrl+C` 会让整个进程消失。`Esc` 是更安全的止损键，应写在提示文案里。
`Ctrl+C` 仍可用，只是不写在说明书上。

## 6. 总体评价

**设计方向正确，可以实施 —— 文档已按本文修订完毕（494 行）。**

选候选 A（清单清空 = 达成）是对的：三个候选的可靠达成判定本质都是模型自陈，选最便宜的那个
是正确的工程判断，且 ADR-0074 把“为什么不选另外两个”记清楚了。净删 400 行、零 `ys-loop` 改动、
判据落在纯函数里 —— 这些都符合本项目“最小核心 / 依赖单向”的既有纪律，落地风险低。

需要警惕的是一类**特定的错误**：把一期的“当时无害”当成二期的“现在也对”。
一期的追问链最多 2 个回合，所以“循环内不消费 `Request`”从没人觉得是问题。
**本文自己也犯了同一个错的变体**：把“循环内不消费 `Request`”直接推成“`/goal clear` 不可达”（§2.4 已推翻）。
真正的教训不是“要加轮询”，而是**先分清动作属哪个信道** —— 打断走 ②、清理走 ①，
两者都是既有机制，根本不需要新开一个“在循环里消费 `Request`”的模式。

成本模型则是另一个真问题：设计已识别“跑飞很贵”（R3/R4），但原稿错锚在两个过时数字上（“每 turn 数十轮”）
与一个无逐项假设的数（“78 万有效 token”）。**这两条加起来会让“最坏情况”低估一个量级** ——
已在 `design.md` §7.1 改为“总成本上界不存在”。
