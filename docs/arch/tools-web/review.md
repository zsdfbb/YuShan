## 各维度判断

| 维度 | 判断 | 关键发现 |
|---|---|---|
| 1.1 技术可实现性 | 🟡 | 主干有 CodeWhale 的成熟先例；但 **`htmd` 的 `skip_tags` 语义未验证**（唯一放行门槛），**golden fixture 的来源与体积未定** |
| 1.2 依赖成熟度 | 🟡 | `htmd` 是 **0.x**（无 SemVer 保证）+ 拉入 html5ever 树（编译时间）。已配隔离壳与 golden 对策，但**首次引入的代价是实付的** |
| 1.3 实现周期 | 🟡 | **测试面很可能大于生产面**（SSRF 表 / UTF-8 跨 chunk / 预算切片 / fixture 三态 / 假服务器护栏）；无 CI + 单人 |
| 2.1 模块边界 | 🟢 | `tools-web` 独立 crate，`tools-basic` 无网络由**编译器强制**；`net.rs` 是网络策略唯一出口 |
| 2.2 接口稳定性 | 🟡 | 契约测试化的思路对；但 **`Backend` 类型从未定义**（`TABLE: &[Row]` → `WebConfig.backends: Vec<Backend>` 之间缺一环） |
| 2.3 错误处理 | 🟢 | 双通道清晰（模型可见 → `is_error`；基础设施 → `Err`）；降级理由**聚合而非丢弃** |
| 2.4 并发安全 | 🔴 | **落盘 tmp 名不唯一**（跨进程同 URL 会写坏）；**清理可能在测试路径上删真实 `~/.yushan/fetched`** |
| 2.5 资源管理 | 🟡 | `Content-Length` 防放大 ✓、cap ✓；但**峰值内存估算不一致**（漏了 5 MiB 的 HTML buffer） |
| 3.1 概念一致性 | 🟡 | **`convert.rs` 残留流式方案的 `Converter`/`CappedWriter`**，与 `htmd`（整块输入）不匹配；**三个超时层次未写清** |
| 3.2 上手成本 | 🟢 | 文档齐（context/design/ADR/调研四件套），决策有据 |
| 4.1 性能模型 | 🟡 | **自适应切片与「调用链确定」有张力** —— 同一查询可能这次成功、下次超时 |
| 4.2 故障模式 | 🟢 | 链 + 启动期可见 + 逐条理由，是正确姿态 |
| 附：既有代码 | 🔴 | **发现两个既有 bug**（见 R1）——不属本设计引入，但本设计会**踩上它** |

## 改进建议

### 易修复（改设计文档即可，开工前）

1. **R1 —— 无 HOME 时不得落盘**：`fetched_dir` 解析失败（无 `HOME`/`USERPROFILE` 且无 `YUSHAN_FETCHED_DIR`）→ **`webfetch` 返回明确的 `is_error` 结果**（"web tools require a home directory"），**绝不退化为相对路径**。并把「落盘路径永远是绝对路径」写成一条**契约测试**。**顺带**：`sessions_dir()` 的同款回退（`main.rs:278`）是**既有 bug**，建议一并修（否则会话文件会落进用户仓库）。
2. **R2 —— 让清理难以被误用**：① `build_tools(workspace, web)` 里**不调**清理，改为 `main` 显式调 `web.cleanup_fetched()`（与「启动期探测一次」同在 main 的显式序列里）；② 或让 `cleanup_fetched` **只接受显式传入的目录**，`WebConfig` 不隐式使用。**并为 `toolset` 的测试明确要求传临时目录 config**。
3. **R3 —— tmp 名唯一**：`<slug>-<hash>.md.<pid>.<原子序号>.tmp`（照项目硬约定），rename 前再 `fs::rename`（同分区间原子）。
4. **R4 —— 删掉流式残留**：`convert.rs` 收敛为**一个函数** `fn html_to_markdown(&str) -> String` + 一个 8 MiB 后置 backstop；**删掉 `Converter` trait 与 `CappedWriter`**。在模块头写明「`htmd` 需要整块输入，故不流式；cap 靠下载侧 5 MiB 兜住」。
5. **R6 —— 把四个时间概念写成一张表**：`client 级`（兜底）/ `链预算`（搜索总）/ `单后端切片`（搜索单次）/ `fetch deadline`（抓取单次），各自的值、谁先触发、webfetch 用哪个。
6. **R7 —— 补 `Backend` 定义**：明确 `struct Backend { row: &'static Row, key: Option<String>, endpoint: String }`（启动期由 `TABLE` 解析、冻结），并说明「未配 key 的行在此步被剔除」。
7. **R8 —— 修正内存估算**：峰值 ≈ `5 MiB(body) + ~2.5 MiB(htmd 开销) + 50KB(head)` ≈ **7.5 MiB**；并在 cap 常量处注明「cap 与峰值线性相关」。
8. **R10 —— 列一张常量表**：名字、值、是否可 env 覆盖、改动是否影响测试时长。

### 需讨论（需要你定）

9. **R5 —— 自适应切片要不要换成固定切片**？「调用链确定」的严格版本要求**每后端拿到的预算是常量**（如各 8s），代价是慢后端会吃掉后面后端的预算（可能需要 4×8=32s > 30s 的预算，或允许个别后端**本次不试**）。
   - **方案 A（自适应，现设计）**：总耗时上界确定（≤30s），但**单次成功与否不确定**。
   - **方案 B（固定切片）**：每后端预算恒定、行为最可预测；但总预算可能不够 4 家分。
   - **方案 C（自适应 + 下限）**：`max(MIN_SLICE, remaining/left)` 的下限调大（如 8s），接近 B 但保留弹性。
   - **我倾向 C**：它在「行为可预测」与「不浪费预算」之间取中，且有确定的**下界**可写进文档。
10. **R9 —— golden fixture 怎么取、允许多大**：建议 5 份各截到 **≤200KB**（保留结构与正文开头），并在 fixture README 记来源与截断说明。

### 架构级（跨 phase）

11. **「契约测试化」需要一个落点**：设计 §1.5② 列了 6 类契约，但没说它们住在哪个测试文件、由谁在所有切片里保持一致。建议在 `tools-web` 里立一个 `tests/contracts.rs`，并把它写进 exec-plan 的固定任务（**每次改动都必须过它**）。
12. **测试面 > 生产面**是真实风险（无 CI、单人）。建议 exec-plan 里**给测试任务预留与实现相当的预算**，而不是当成实现的附带品。

## 总体评价

**整体健康度：中上，但有两处必须开工前修。**

设计的主干是扎实的——crate 边界强制隔离、`net.rs` 单一出口、错误双通道、降级可见、以及**把「稳定」拆成契约测试 + 依赖隔离 + 确定链**这一组动作，都对着正确的问题。

**最大风险是两个"会真的造成损害"的：**

- **R1（无 HOME → 写进仓库）**：它同时**违反了本设计的头号铁律**，又暴露出**既有的同类 bug**（`sessions_dir`）。这类问题不会在测试里显形（测试总有 HOME），**只会在真实用户的机器上发生**。
- **R2（清理删真实文件）**：方向相反但同样是"数据损害"——**测试副作用越出沙箱**。它极易发生（`toolset` 既有测试就在调 `build_tools`）。

**另一处直接对着你诉求的是 R5**：你说「调用链确定」，而当前的**自适应切片**让「每个后端分到多少时间」依赖前面几个的耗时 —— **顺序确定，但结果不确定**。这条需要你拍板（我推荐方案 C）。

**另一个结构性问题**：设计里还残留着**被否决方案的零件**（`Converter`/`CappedWriter` 来自流式方案），而它与 `htmd` 的能力**不匹配**。这类残留比缺漏更危险——实现者会照着它去做一件做不到的事。

**推荐下一步**：先修 R1–R4、R6–R8（都是文档级，含两个真 bug 的处置），再定 R5，然后进 `sequential-workflow`。
