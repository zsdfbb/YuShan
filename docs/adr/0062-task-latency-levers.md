# 0062 — 任务延迟优化：先度量，再改提醒与窗口，结构性批处理放第二刀

把「完成同一任务更慢」拆成可验收的杠杆：第一刀只做**低风险、可回滚**的度量 / 提醒 / 窗口上限；
第二刀的 `batch`（受限 JSON DAG）必须先过 pilot 门禁才允许合并。**默认不引入新的跨 crate 抽象。**

## Status

proposed（2026-10-29）；A3 / A4 于 2026-10-30 按实测返工（见「实测后的修订」）。
设计见 `docs/arch/task-latency-optimization/design.md`。

## 背景

- 会话 `1793181762`：555 轮 / 626 次工具调用 / 主循环模型 54.0 min / 工具 15.2 min；
  每轮中位 4.49 s，其中 TTFT 2.23 s。
- 每轮工具调用 1.13，但**每条 `bash` 平均 4.17 个 shell 步骤** ⇒ 模型已在 bash 内批处理，
  「外层调用数」不是完整口径；真正稀缺的是**跨轮依赖层**。
- TTFT 在 20k–300k 输入之间几乎平坦（2.22→2.46 s），仅 >300k 跳到 3.20 s。
- 跨 harness 对照：codex 128 s / ≈6 轮 vs 本仓 291 s / 33 轮；同模型另一 harness
  90.4 s / 13 轮 vs 440.2 s / 21 轮（`docs/arch/explore-speed/cost-model.md:205-220`、
  `docs/arch/execution-efficiency/context.md:122-132`）。
- 同类调研：三家的压缩触发都带绝对约束；Codewhale 有轮数 soft landing；
  **三家都没有 bash 查看器检测，也没有验证结果复用**。
- 本仓 ADR-0039 的冗余 `cd` 回显最终被 `f6885fa`「执行前剥离」取代 ——
  提示/回显改变行为的证据是负面的。

## 决策

### 1. 度量先行（A1），其余每项都以它验收

`RoundClock`（`apps/coding-agent/src/round_clock.rs`）已接收全部事件，扩展 `TurnTotals`
并输出定形一行；`-p` 写 stderr、TUI 走 `Outbound::Output`、debug 落 `run_reading`、
`e2e_bench` 落 JSON。**没有这一项，后续任何改动都无法判断好坏。**

### 2. 提醒走 loop 内既有通道，**不建 `TurnAdvisor` trait**

候选乙提出在 `ys-component` 新增第 5 个可选挂载点。**否决**：

- 两个消费者（批处理提醒、轮数软提醒）都在 `BasicLoop` 内部，判据只读本回合状态；
- 现有 `narration_nudge`（`basic.rs:452-464`、`:635-650`）已经是「纯常量、仅本请求、
  不落 session」的成熟形状，直接复用即可；
- ADR-0014 / ADR-0021：今天只有 1 个消费面（loop 自己），跨 crate trait 是零消费者抽象。

**升级路径**：出现第三个消费者且需要接线器持有状态（如跨会话统计）时，再提为 trait；
届时把三条提醒一起收编。

### 3. 上下文上限用「有效窗口」，不给 `CompactPolicy` 加 `trigger_cap`

`Config::effective_context_window() = min(声明窗口, context_cap_tokens)`，默认 200k；
`CompactPolicy` 的算法与不变量一行不改。理由：`trigger_at` / `keep_budget` / 回合工具预算
三处都从同一窗口派生，一个 `min()` 同时对齐三者；而给策略加 `trigger_cap` 会出现
「触发点改了、保留量没改」的半对齐状态。库默认 `0`（不封顶）⇒ 老调用方逐字节不变。

**200k 而非 128k 或 1M**：1M 是当前模型的标配窗口（用户 2026-10-29 确认），但实测 TTFT
在 20k–300k 平坦、300k 后才跳升，喂满 1M 不会更快只会更贵。128k 又太激进：保留量按窗口
10% 缩放只剩 12.8k，而本会话每回合工具输出增长约 17k，压缩会退化成每回合一次、
每次 25–45 s，净收益为负。200k 是「至少 200k」这一约束下的默认；300k 是观察到重读后的备选。

### 4. 压缩收益按本机实测斜率计，不沿用 9 min

`docs/arch/session-latency` 的 76.7 ms/1k 来自单会话、12k–96k 输入、缓存命中较低的场景；
本机 4,972 轮拟合 7.08 ms/1k，长会话分桶中位约 3.4 ms/1k，且 20k–300k 近乎平坦。
压缩项净收益 **1.5–2.5 min**，主要价值在 token（−40%~−50%）与 >300k 的尾部。

### 5. `batch` 放第二刀，且必须过 pilot 门禁

- **不做代码执行**：本仓不做沙箱（项目定位）；`bash` 已能执行任意命令，通用解释器会新增
  能力面、破坏 `tool_call_id` 配对、在事件模型之外开洞。
- **`batch` 是受限 JSON DAG**：只调度 `read`/`grep`/`find`/`ls` 四个已声明并发安全的工具；
  1–6 步；引用只许指向更早步骤；无引用步并发（≤4）。
- **净收益 3.5–7.6 min**（毛 8.8–15.0 min，扣 plan 生成的 0.9–1.3 s/次）。
- **门禁**：第一刀后用 `fact/1` / `exp/t1` / `daily/2` 各 ≥3 次；若
  `tools_per_round < 1.5`、单调用轮 > 50%、轮数降幅 < 15%、质量位保持，
  才启动 `batch`。`batch` 上线后覆盖率 < 30% 的查看器轮 ⇒ 回滚。

### 6. 不做 bash 查看器运行时检测

三家同类都没有；本仓 ADR-0039 的注记实验最终被「执行前剥离」取代。
「让模型换工具」只保留提示词与批处理提醒（A4）两种低成本形态；**不新增命令分类器与频次状态机**。

### 7. 重复验证用「三层防止」，不做结果缓存

缓存（同命令同树 ⇒ 回放旧输出）**否决**：它仍要花一轮模型往返，且把「模型为什么想重跑」
这个根因掩盖掉。改为三层防止：

1. **规则**（A7 任务边界）；
2. **保留证据**（核心）：让「刚测过」这条事实在**压缩**后仍然可见。
   回合级降级只作用于 >2 KiB / 40 行的大结果（`turn_budget.rs:44-52`），
   验证结果本来就不会被降级；真正的风险是压缩。**用摘要 prompt 新增 `## Verification` 节**
   （v1，不改数据结构）；若摘要漏项，再改为压缩后追加一条独立消息（v2）。
   ⚠️ 不能写成「keep 区间优先包含」——`CompactPlan` 只有两个**连续**区间
   （`compact.rs:44-57`），历史中段的料条无法单独保留。
3. **硬拦截**（兜底）：同命令 + 树指纹未变 + 上次成功 ⇒ **拒绝执行**，只返回一行事实，
   不回放旧输出。

⚠️ 第 3 层与 ADR-0039「命令照原样执行，不剥离、不拒绝」**方向相反**。这里只在
「幂等的验证命令 + 树未变 + 上次成功」这一窄类上反转，理由是重复执行没有信息增量；
其他命令仍一律照原样执行。此边界必须写进实现注释。

### 8. 不改 `Tool::is_concurrency_safe` 的准入规则

现规则明确「`bash`/`write`/`edit` 永远不行」（`crates/ys-tool/src/lib.rs:46-55`）。
让只读 bash 可并发需要先改设计文档，且方向与「少用 bash」相反；本期不做。
⚠️ 推论：`batch` v1 也声明 `is_concurrency_safe = false`，避免「外层 4 路 × 内层 4 路」
的 16 进程尖峰。

### 9. 任务边界写进系统提示，且「多余动作先提议」

用户观察到的症状（要 `commit+push` 却先重跑测试）本质是任务边界失守，
把实现阶段的收尾仪式带进了纯 git 操作。A7 因此扩展为一条边界规则：

- **免问的必要步骤**：为理解任务而读/搜、对**自己改过的代码**跑检查、修自己造成的编译错误；
- **其余一律先提议**：无关重构、新文件/新文档、依赖变更、大范围格式化、额外测试套件、
  **未被要求的** commit/push——一行说明后等待用户回答；
  （用户明确要求 commit/push 时，它就是任务本身，只做它，不附带重跑验证。）
- **不能问时**（`-p` / `--json` / CI）：只做被要求的部分，把多余项列为未做。

代价：交互模式下「提议」结束当前回合，用户回复是新回合，多一次往返；换来的是不跑偏。
`-p` 模式禁止提问（没有用户可答），由文案的第三句兜底。
这条是纯行为约束，ADR-0039 说明提示不保证生效，必须用 A1 的「未请求写操作占比」验收。

### A6 反转 ADR-0027 的「软警告本轮不做」

**被反转的条目**：ADR-0027 在
`docs/adr/0027-completion-check-and-round-budget.md:116` 写下
「**软警告本轮不做**（超范围，记账）」。

**语境已变**：

- `max_rounds` 今天默认 `u32::MAX`（`apps/coding-agent/src/config.rs:415-421` 的
  `max_rounds()` 访问器；`RawUserConfig` 缺省回落 `u32::MAX`）⇒ 轮数硬上限事实上不设；
- ADR-0041 已删掉完工复核回合 ⇒ 回合末不再有「再检查一遍」的收敛点；
- 于是回合内唯一兜底只剩 48h wall-clock，且它对「小输出空转」很粗（可空转数小时才到点）
  ⇒ **软提醒的缺口成立**。

**边界（不重新引入硬上限）**：

- 只注入**一条瞬时 `Role::User` 常量**，仅作用于本次请求；
- **不落 session**、**不中断回合**、不产生事件、不碰 system/tools；
- 阈值 `soft_round_advice_at` 默认 **60**，触发后翻倍：**60 → 120 → 240**；
  每回合重置；
- `soft_round_advice_at = 0` 可关闭；
- 它**不是**重新引入 `max_rounds` 硬上限：没有「到点强制终止」，只有「到点提示收敛」。
  硬上限仍由 `max_rounds` 独立承担（默认不设）。

## 实测后的修订（2026-10-30）

首轮三臂基准（原始基线 / 本期改动 + 旧提示词 / 本期改动 + 新脚本指引，各提示 3 次）推翻了两项
设计假设，完整数据见
[`docs/reports/2026-10-30-task-latency-first-knife-report.md`](../reports/2026-10-30-task-latency-first-knife-report.md)。

### A4 原判据实测无效 ⇒ 改为累计 + `tpr` 过滤

- **原判据**：连续 N 轮只有 1 个工具调用，阈值 4，到阈值即触发。
- **实测**：10 次运行只触发 4 次，其中 3 次落在回合最后 1–2 轮；单调用轮占比 49% → 51%，
  **未变**。根因是「连续」计数会被中间任一多调用轮清零（轮序列形如
  `1 1 2 1 1 1 1 1 1 0`）。
- **新判据**（`advance_batch_nudge`，`crates/ys-loop/src/basic.rs:90-108`）：回合内**累计**
  工具调用数（单调、永不重置），阈值 **12**，且仅当 `tpr < 1.5` 才触发并翻倍（12 → 24 → 48）；
  `tpr >= 1.5`（模型已在批处理）⇒ 不触发、也不推进阈值。新判据在 6 次运行中只触发 1 次，
  其余被 `tpr` 过滤正确抑制 —— **逻辑正确，但基准任务上仍几乎没有触发空间**。

### A3 由「禁止 bash 搜索」反转为「探索用一条命令聚合」

- **原方向**：用结构化 `read`/`grep`/`find`/`ls` 代替 `bash` 搜索，删掉 shell loop 逃生口，
  要求一条消息发多个独立调用。
- **实测**：这类逐工具禁令把本可聚合的检索拆成逐个结构化调用，反而抬高轮数。新指引改为
  「**写一条命令一次吐全**」（`for` 循环 / `rg -n --context` / `awk`），并删除四条逐工具禁令；
  写入侧保持 `edit`/`write`、禁止脚本化写入（绕过 `oldText` 精确匹配），但**允许拆成多次调用**。
- **读数**：`fact/1` 三次运行的 `read`+`grep` 合计仅 2 次，其余几乎全是 `bash` + `rg`/`for`/`sed`
  的聚合命令；`daily/2` 轮数中位 10 → 6。这是本期**唯一测出机制性改变**的杠杆。

### A5 / A6 无证据

两项在本次基准里**从未触发**：压缩事件 0 次（输入中位 20–33k，触发点 170k）；最长回合 24 轮
（软提醒阈值 60）。因此**对它们的有效性没有任何证据**，既未证明有效也未证明无效。A5 的主要
收益是 token，而基准不测 token。门禁（决策 5）所依赖的读数因此无法由该基准判定，需长程提示
或真实长会话的 `run_reading` 跨会话对比。

## Considered Options

- **候选甲（最小复杂度）**：全部采纳为第一刀的骨架，但把它的批处理收益从 10–18 min
  下调到 3–6 min（模型已在 bash 内批处理）。
- **候选乙（机制优先）**：采纳 `read` schema 修正、有效窗口、度量；**否决** `TurnAdvisor`
  trait（见决策 2）、bash 查看器纠正（见决策 6）、`EvidenceLog` 在结果内附 notice
  （无先例 + 负面先例）；其 `read glob` 暂缓（`cat`/`ls` 仅占 4.5%）。
- **候选丙（性能优先）**：采纳 `batch` 作为第二刀、pilot 门禁与「依赖层」口径；
  **否决**子 agent 不等（改 ADR-0055 语义，需独立 ADR）、写时封顶替代 Step 11
  （改动面大、先看第一刀读数）、请求侧改动（命中已 99.3%）。
- **直接改主轮思考强度**：`daily/2` 实测 −37%，但 `fact/1` 有质量退化读数（ADR-0060 决策 7）；
  不在本 ADR 的默认改动内。

## Consequences

- **正面**：第一刀约 5–13 min（中位 ~8 min）；两刀合计 9–21 min（中位 ~13 min，约 24%）。
  每一项独立开关、可单独回滚。
- **负面 / 如实记账**：
  1. **第一刀的真实下界是 ~2 min**（只有 A5 几乎确定）；A3/A4/A6/A7 全靠模型响应提醒，
     **可能全部为 0**。中位 ~8 min（两刀中位 ~13 min）**不是期望值**，是「行为杠杆部分生效」
     的情形。**不是「2–5 倍」方案**；即使两刀做完，轮数仍在 ~400 量级。
  2. A2/A3 会平移一次工具表与系统提示前缀 ⇒ 所有用户一次冷启动。
  3. A5 让压缩更频繁（24 回合约 2–3 次），每次 25–45 s，已计入收益。
  4. `batch` 的采纳率是真实风险，必须以 pilot 门禁兜底。
  5. 第一刀的收益主要来自行为改变（提醒/文案），证据方向偏弱；若读数不动，
     应直接进入第二刀而不是继续调文案。
- **不受影响**：`ys-core` / `ys-event` / `ys-protocol` 零改动；`ys-tui-coding` 不新增依赖；
  `ModelEventSink` 保持同步 `fn`；`RunLimits` 新字段全部默认关闭。
