# tools-align-pi — 架构质量分析报告

## 分析范围

- **对象**：设计方案（`docs/arch/tools-align-pi/design.md`，融合方案）
- **维度**：全量（可行性 / 可维护性 / 可理解性 / 性能与可靠性）
- **来源**：`design.md` + `context.md` + 三份候选原始输出 + 直接读码复核
- **日期**：2026-09-16

> 立场：本报告对 `design.md` 做**对抗式**审查。凡标 **🔴/P0** 者，建议在开工前改设计文档，而非留到实现期发现。

## 各维度判断

| 维度 | 判断 | 关键发现 |
|---|---|---|
| 1.1 技术可实现性 | 🟡 | 主干有 Pi 的已知实现路径；但**三处关键假设未验证**（`rg --json` 的 context 事件、HTML→MD crate 的 skip-tags / Write-中止、`--hidden` 取舍） |
| 1.2 依赖成熟度 | 🟡 | `reqwest` 成熟（已在 workspace）；**HTML→MD crate 未二选一定案**，且候选带 html5ever 系编译成本；**未提 TLS 栈必须与 `model-openai-compatible` 一致**（两套 TLS 会双份链接） |
| 1.3 实现周期 | 🟢 | 增量路径清晰（B1 → truncate → exec → grep → find/ls → 提示词），里程碑可独立验证 |
| 2.1 模块边界 | 🟢 | 方向正确：`tools-web` 不依赖 `tools-basic`，二者只共享 `ys-tool`；依赖无环 |
| 2.2 接口稳定性 | 🟡 | **`ToolSpec` 是否加字段未定**（决定 prompt 用 `description` 还是独立 snippet）；`build_system_prompt` 改签名（破坏性，调用点须同步）；`ToolRegistry::build` 保序是**行为变更** |
| 2.3 错误处理 | 🔴 | **「我们自己杀的子进程」未被退出码表覆盖** —— 极可能把正常的结果当失败（见 R1）；错误上下文（stderr）上限未写死 |
| 2.4 并发安全 | 🟡 | 注入式 `SearchBackends`（无全局可变状态）✓；但 stderr 排空任务 × 早杀 × `wait()` 的收敛顺序未写清；**无并发测试要求** |
| 2.5 资源管理 | 🟡 | B3（`kill_on_drop`）已纳入 ✓；**`ls` 的 `read_dir` 无条目上限** → 超大目录无界读（见 R2） |
| 3.1 概念一致性 | 🟡 | **三个上限（`limit` 100 条 / `byte_cap` 1MiB / `truncate` 50KB）混用且关系未说明**；**`--hidden` 取舍丢失**（见 R3/R4） |
| 3.2 上手成本 | 🟢 | design.md 结构清楚，ADR-0015 解释了「为什么 shell out」 |
| 4.1 性能模型 | 🟢 | 关键路径已识别（输出有界 = 正确性、rg 原生 30×、达上限早杀），有 back-of-envelope |
| 4.2 故障模式 | 🟡 | 降级路径定义 ✓；但**缺 SSRF / 网页提示注入**两条安全风险条目（见 R8）；HTML 解析失败无降级定义 |
| 附：与既有文档一致性 | 🟡 | `extension-points.md` / ADR-0015 与之一致 ✓；**但 design.md 未映射 `docs/design.md` §12 测试矩阵，也无测试计划**（项目硬规矩，见 R7） |

## 风险排序

| # | 风险 | 影响 | 可能性 | 优先级 |
|---|---|---|---|---|
| **R1** | **「我们杀的子进程」被当错误**：`Stop::Cap/Aborted/TimedOut` 时进程被信号杀死，`status.code()` 为 `None`；设计的退出码表只列了 0/1/2，**没写「`stop != Eof` 时先忽略 code」**。实现时极易把「数够 100 条主动停」当成失败 | 高 | **高** | **P0** |
| **R2** | **`ls` 的 `read_dir` 无条目上限**：超大目录（数十万条）会先全部读进内存再排序 → 卡顿/内存峰值。候选 C 原有「扫描上限 20000 条」，**融合时丢失** | 中 | 中 | **P0** |
| **R3** | **三个上限语义未理清**：`limit`（100 条命中）／`byte_cap`（1MiB 读）／`truncate::head`（50KB 输出）三者单位不同、关系未说明。带 `-C N` 时字节闸先于条数闸触发，用户看到「limit 100 却只出 12 条」 | 中 | **高** | **P0** |
| **R4** | **`--hidden` 取舍丢失**：候选 A 主张**不加**（避免搜进 `.git`）、候选 C 主张**加**（否则 `.github/workflows/*.yml` 搜不到）。融合版 argv 里没有 `--hidden` → **静默选了 A 且未记录理由** | 中 | 中 | P1 |
| **R5** | **`ToolSpec` 接口未定**：prompt 清单「从 spec 派生」——是用 `description`（面向 API 的完整长句，每轮进 prompt 浪费 token），还是给 `ToolSpec` 加 `prompt` 片段字段（改核心接口）？两条路代价不同，**设计未选** | 中 | **高** | P1 |
| **R6** | **HTML→MD crate 未定且 API 未验证**：`html2text` vs `htmd` 二选一未决；且「跳 boilerplate + 写入字节计数 `Write` 即中止」两个前提**都没验证**。另外「流式」表述**不准确**——HTML 解析器需要完整输入，只有输出是流的，内存下界仍是 5MiB | 中 | 中 | P1 |
| **R7** | **无测试计划、未映射 §12 测试矩阵**：项目硬规矩要求「新模块接口改动须对应 §12 条目」+「关键逻辑做变异测试」。design.md 只在风险区提了 4 个变异点，**没有测试章节** | 中 | **高** | P1 |
| **R8** | **缺两条安全风险条目**：`webfetch` 的 **SSRF**（`http://127.0.0.1`、云元数据 `169.254.169.254` 全可达）与**网页内容即提示注入**（抓回的页面进上下文）。候选 C 明确标为「最大安全悬空项」，**融合版未写入** | 高 | 低 | P1 |
| **R9** | `ys-tool` 不再纯 trait crate（truncate 进驻）：可接受，但属**核心 crate 边界判断**，应记录（现仅在 design §1.1 一句） | 低 | 高 | P2 |
| **R10** | `ToolRegistry::build` 保序是行为变更，可能撞既有断言（如 `view.rs` 的工具列表断言） | 低 | 中 | P2 |
| **R11** | 默认搜索 provider 未定（Brave / Tavily / 国内一家） | 中 | — | P2（已列待决） |
| **R12** | 老版本 `rg`（无 `--json`）会运行期 exit 2 → 错误结果。设计「不探版本」的理由成立，但**未说明该故障形态** | 低 | 低 | P2 |

## 改进建议

### 易修复（低风险，改设计文档即可）

1. **R1 —— 补进退出码表**：明确「`stop != Eof`（我们杀的）→ **忽略 `code`**，按已有结果渲染 + notice」，并列为**变异测试首选目标**（「删掉该判断 → 测试必须变红」）。
2. **R2 —— `ls` 加扫描上限**（如 20000 条）再排序取 `limit`，与 `ModelRequest` 的工具输出纪律一致。
3. **R3 —— 用一张表写清三个上限**的单位、触发条件、各自 notice 文案；明确「字节闸先触发时也要报出来」。
4. **R7 —— 补「测试计划」章节**：① 映射到 `docs/design.md` §12；② 列出变异测试点（R1 的杀进程判定、无命中≠错误、降级漏排 `node_modules`、stderr 不排空必死锁、`kill_on_drop` 移除即泄漏）；③ 降级路径用 `posix_only()` 注入确定性复现；④ 网页层用本地 `TcpListener` 假服务器，不打外网。
5. **R8 —— 把 SSRF 与提示注入写进「已知风险」**（范围外但要留痕），并在 webfetch 输出加 `[fetched from <url>]` 标注。
6. **R5 —— 补一句定论**：**推荐不改 `ToolSpec`** —— 工具清单与一句话描述留在 `prompt.rs` 的 snippet 表（按 name），外加一个「每个已注册工具都必须有 snippet」的**漂移测试**。理由：给 `ToolSpec` 加 `prompt` 字段等于把产品级提示措辞塞进核心 crate `ys-tool`，与既定的「提示词是产品层知识」相悖；用测试锁漂移比改核心接口便宜。

### 需讨论（需要判定）

7. **R4** —— `--hidden` 拍板。推荐**不加**（`--hidden` 会把 `.git/` 内容也纳入扫描，token 灾难）；代价是搜不到 `.github/workflows/*.yml`，记为已知取舍。
8. **R6** —— 先做 **prototype** 验证 HTML→MD 的两个前提再定 crate；并把「内存下界 = 输入全文」写清（别再说「流式」）。
9. **R11** —— 定默认 provider（考虑国内可用性；如需国内 API，Brave 默认值要换）。

### 架构级（影响面大，跨 phase）

10. **两切片的验收标准应各自独立**：切片一（离线、零新依赖）可先落地并验收；切片二依赖 provider/crate 两个待决项。建议 design.md 明确「切片一完成 = 可独立 merge」，避免被切片二拖住。
11. **`spec.description` 升格为模型可见主文案**是全局影响（9 个工具描述需重写，写砸了模型变笨）。建议在实现前先出一版 description 草稿并评审，而非实现时顺手写。
12. **工具数 4 → 9 的 token 成本**（≈40–80 token/轮）是净负外部性。若将来需要按意图裁剪工具子集，应作为独立话题规划，别在本切片临时加开关。

## 总体评价

**整体健康度：中上。** 主干扎实——两切片切分正确、依赖方向无环、把「输出有界」识别为正确性问题而非优化（这点很关键）、三候选的**独立发现**（B1 保序 / B2 无 boundary / B3 泄漏）被有效吸收，ADR-0015 也把「为什么 shell out」留了痕。

**最大风险点有两个**：

- **R1（把自己杀的进程当失败）** —— 这是实现期最可能踩、且最伤模型体验的一处；好在**极易预防**（一句话写进退出码表 + 一个变异测试）。
- **R3（三个上限未理清）** —— 它不致命，但会让实现者对「该在哪儿截断」产生分歧，并让模型看到的行为飘忽。

**另一个结构性问题**：design.md 是一份**好设计**，但**缺测试计划与 §12 映射**（R7）——按本项目过去的惯例，这会在 review 时被判「不完整」。

**推荐下一步**：先把 P0 三条（R1/R2/R3）+ R7/R8 补进 design.md（都是文档级改动），再定 R4/R6/R11 三个待决项，然后按「切片一先落地」开工。**切片二在 R6 得到 prototype 验证前不要动。**
