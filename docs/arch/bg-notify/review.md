## 0. 结论

**黄。** 方向正确、证据扎实、边界克制，但有 **1 个 P0**（锁内阻塞 + 新竞态）、
**3 个 P1**（超时转后台的语义倒退、滞留项占名额、渲染失败丢数据）、若干 P2。

设计能落地，但**按现文实现会引入一个比现状更严重的卡顿**。修完 P0/P1 再动手。

## 1. 可行性 — 绿

| 检查项 | 判断 | 依据 |
|---|---|---|
| 核心机制有已知实现路径 | ✅ | `Boundary::Deferred` + `drain_boundary` + `DeferredResult` **全部已存在**；subagent 已在生产使用同一路径 |
| 依赖的底层能力可用 | ✅ | 仅用 `std::sync::Mutex` + 既有 tokio sweeper，无新依赖 |
| 无「黑科技」或未验证假设 | ✅ | 六条关键断言逐条核实通过（见 §6） |
| 关键选型有历史经验 | ✅ | 照搬 `SubagentRunner::result_sink` 的既有形态 |

**实测证据充分**：68 次 poll / 54 次空转 / 1243 s 等待，需求不是臆想。
这是本次设计最强的部分 —— **问题被量化了，而且量化方式可复现**（会话 JSONL 可复查）。

## 2. 可维护性 — 黄

### 2.1 模块边界 — 绿

职责清晰（注册表承投放点、`bg_output` 承渲染、`app_loop` 承绑定），依赖方向不变，
5 个 crate 零改动。改动集中在 `adapters/tools-basic` + app 侧接线，符合「新增功能影响 1–2 个模块」。

### 2.2 接口稳定性 — 黄

`BackgroundTasks` 新增 3 个 pub 方法（`bind_deferred` / `take_completions` / `adopt`），
且**语义在其内部收敛**（`notified` 一位两用）。风险在于：`advance_consumed` 要删，
而它是 `pub` 方法 —— 外部若有调用点会破。需确认调用面（当前看只有 `bg_tools.rs` 用）。

### 2.3 测试难度 — 黄

设计给的测试矩阵质量高（每条都带**变异描述**，符合本仓纪律）。但：

- **R6 竞态（100ms 窗口）无法用单元测试稳定复现**。设计的缓解依赖「`mark_notified` 在
  `push` 之后」这一顺序不变量，而顺序错了只在竞态下暴露。**建议**：把
  「取候选 → 渲染 → push → mark」抽成纯函数，用一个可注入的 `push` 失败/延迟钩子测，
  否则这条只能靠 code review 守。

### 2.4 ⚡ 并发安全 — **红**（P0）

**问题 P0-1：`sweep()` 持有注册表锁期间，会同步执行 `sh -c "kill -9 -{pid}"`。**

证据（既有代码，非设计臆造）：

```
background.rs:530  pub fn sweep(&self) {
background.rs:531      let mut inner = self.lock();      ← 持锁
background.rs:534      self.enforce_output_cap(&mut inner);
background.rs:535      self.reap(&mut inner);
                       ...
background.rs:620-ish  fn kill_entry(entry) { kill_group(entry.pid); }   ← 锁内
proc_group.rs:26   pub(crate) fn kill_group(pid) {
proc_group.rs:27       let _ = Command::new("sh").arg("-c").arg("kill -9 -{pid}")
proc_group.rs:33           .status();                     ← 同步 fork+exec+wait
```

即：**当前就已经每 100ms 可能在锁内 fork/exec/join 一个 `sh`**。进程启动慢时（低端
Android/Termux、系统负载高），这是**锁内阻塞**，而同一把锁是 `snapshot()`、
`take_completions()`、`spawn()` 的必经之路 ⇒ 工具调用会跟着卡。

设计把 push 放进 `sweep()` 会让它**更糟**：`sweep` 从「偶尔做重活」变成「每条完成命令
都要渲染正文 + push」，而渲染要读输出文件（**锁内 IO**）。设计 §2.4 明确要求
`take_completions` 渲染 message —— 若在锁内做，就是**锁内文件读**。

**这是既有技术债被新设计放大，不是新引入。但设计没识别它。**

**必须修**（三选一）：
1. `sweep()` 拆成「锁内收集 → 释放锁 → 锁外渲染 + push → 重新加锁 mark」（推荐）；
2. 把 `kill_group` 改成非阻塞投递（`kill_group_async` 已存在，但 `sweep` 是同步 fn）；
3. 至少把渲染挪到锁外。

**问题 P0-2：新竞态窗口比设计承认的更宽。**
设计 §R6 说窗口「≤ 一次 tick（100ms）+ 一次 push」。若实现成
「锁内取候选 + mark，锁外 push」，则窗口 = **两次取锁之间**（包含渲染读文件的时间，
可能是毫秒到数十毫秒），且**失序风险**：条目已 mark 但 push 尚未发生，此时回合切换 ⇒
下回合补投取不到它 ⇒ **静默丢失**（正是设计想避免的）。设计的三道缓解里第 1 条
（`mark` 在 `push` 之后）正好与此冲突 —— **必须明确「push 成功后才 mark」，且 push
必须在同一临界区内完成，否则要引入「投递中」第三态**。

### 2.5 ⚡ 错误处理 — 黄

- **P1-3 渲染失败丢数据**：设计 §R3 已诚实承认（输出文件被 `/new` 或淘汰删掉 ⇒
  该条丢失）。缓解是「退回路径指针」，但**没定义触发条件与正文形态**。建议：把
  `BgState` 的终态 + 文件缺失组合明确成 `BgCompletion::Unreadable { path }`，
  正文写「输出已不可读（命令已结束，退出码 N）」—— 让模型知道「有结果但内容没了」，
  而不是以为「没结果」。
- **错误传播链**：`Boundary::Deferred` 的 push 无返回值（`QueueBoundarySource::push`
  返回 `()`）。落点若已 drop，push 无声失败。设计靠 `notified` 位兜底，可接受，
  但**应加一条 debug 日志**（本仓 `YUSHAN_DEBUG` 默认开启）。

### 2.6 ⚡ 资源管理 — 黄

- **P1-2 滞留项占名额**：设计 §R5 承认。句柄表上限 8，滞留项与在跑项**共用**名额 ⇒
  用户开 4 个后台命令后结束回合（受 `max_running=4`），下回合前若又开 4 个，
  滞留的 4 条会被 `evict_oldest_completed` 淘汰 ⇒ **结果被静默丢弃**。
  设计说「极端情况」，但**这是用户的正常用法**（启动构建 → 回合结束 → 下回合再启动）。
  **建议**：滞留项与在跑项**分开计数**，或滞留项不参与 `max_entries` 淘汰（只受时间/总量约束）。
- **FD 账**：设计声称稳态 0 / 轮询瞬时 +1，与既有实现一致 ✅。但 `adopt` 新增
  「收养者持有 `Child`」—— 每个收养者 = 1 个 fd（既有 `BgEntry` 也是如此），
  设计未重算 fd 上限 ⇒ 需补一行。

## 3. 可理解性 — 绿

- **概念一致性**：`notified` 一位两用（「还没投」+「已投过」）虽然省，但与
  `BgState` 构成**两个正交状态机**。建议在 `background.rs` 类型定义旁写明不变量
  「`notified == true` ⇒ 该条目即将/已被淘汰」，否则后人会想加第三个态。
- **文档完整度**：**优**。六个 crate 零改动、候选对比、被否理由、诚实缺口清单都在。
  `R1`–`R8` 的风险编号可直接对应测试用例，这是本仓少见的成熟度。
- **新人上手**：§2.2 的「进程级 vs 每回合」图解把最容易踩的坑讲清楚了 ✅。

## 4. 性能与可靠性 — 黄

### 4.1 性能

- **收益实打实**：省 ~54 次模型往返 / ~15 分钟。这是**数量级改善**，非边际优化。
- **成本被低估**：设计未给「渲染正文」的开销。每条完成命令要读最多 50 KiB +
  `head_tail` 裁剪。若在锁内做（见 P0-1）⇒ 每 100ms tick 持锁读文件。
- **token 成本**：设计给 50 KiB 上限 ✅，但未算**滞留补投**场景：一次补投 4 条
  × 50 KiB = 200 KiB 进上下文，可能直接触发压缩。**建议**补投时分条限流（每回合最多
  补 2 条，其余留到下回合）。

### 4.2 故障模式

- **P1-1 超时转后台的语义倒退**（设计 §R4 提到测试要改，但**没把这当成架构风险**）：
  今天 `bash` 超时 ⇒ 杀进程组 + `is_error: true`，用户看到明确失败。
  改后 ⇒ 进程转后台 + `is_error: false`。
  **后果**：`yushan -p`（Print 模式）没有后台能力也没人消费 `Deferred`（无 UI 循环），
  超时的命令会变成**静默转后台然后结果无人接收** —— 比今天的「明确超时失败」更差。
  **设计未提 Print/JSON 模式**。这是**范围漏洞**：`-p` / `--json` 的
  `Boundary` 消费路径与 TUI 不同，必须显式说明「无后台能力时保持现状」。
- **单点**：sweeper 是唯一检测者。若它有 bug 或未启动（`BG_SWEEPERS` 静态表），
  所有通知停止且**无告警**。建议：`take_completions` 返回滞留条目的 age，超阈值记日志。

## 7. 改进建议（分层）

### 易修复（动手前改设计文档即可）

1. **写清 Print/JSON 模式的行为**：无后台能力时 `bash` 超时**保持现状**（杀 + `Err`）。
   这是 P1-1 的修法，且实现上就是「`backgrounds.is_none()` 时走原路径」——
   设计 §R8 已提子 agent 受限，把父进程的 `-p` 模式一并写进去。
2. **补 `Unreadable` 终态**（P1-3）。
3. **补 fd 账**：`adopt` 新增的持有者。
4. **写 `notified` 不变量**（P2-3）。

### 需讨论

5. **滞留项是否与在跑项共用名额**（P1-2）。建议分开，否则正常用法会丢结果。
6. **补投限流**（P2-1）：每回合最多补 N 条。
7. **`sweep` 的重构范围**（P0-1）：只挪渲染，还是连同 `kill_group` 一起异步化？
   后者会改 `sweep` 的同步签名，影响面更大。建议本次只做「锁内收集 → 锁外处理」，
   `kill_group` 的既有问题单独记一条 TODO。

### 架构级

8. **投递的恰好一次语义**（P0-2）。当前设计靠「顺序不变量 + 下回合重投」降级，
   但重投意味着**可能投两次**。若模型据此重复触发动作（如重复删文件），代价不小。
   更稳的形态是给条目加 `Delivered` 第三态（投出后置，淘汰时才删）。
   **这需要设计明确表态**：接受「可能重复」，还是引入第三态。
9. **sweeper 单点无告警**（§4.2）。可推迟，但应记入已知缺口。
