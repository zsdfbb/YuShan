# 0057 — 输入框选区与「复制落到系统剪贴板」

两件事，同一条根因链：**应用接管鼠标后，剪贴板只有一条不保证存在的通路**。
① 复制改走「本机工具 + OSC 52 双发」；② 输入框获得全选/扩选/复制，`↑↓` 改归输入光标。

## Status

accepted（2026-10-26）—— 已实施。

落点：`crates/ys-tui-coding/src/run.rs`（`write_clipboard` / `write_system_clipboard` /
`clipboard_writers` / `spawn_writer`）、`input.rs`（选区原语 + 视觉行移动）、
`events.rs`（键位分派）、`draw.rs`（`input_selection_cells` + `wrap_width` 写回）、
`commands.rs`（`KEY_HELP` 与 `/copy` 提示文案）。

## 背景

### 1. 「拷贝不好用」不是选区的问题，是**出口**的问题

ADR-0051 让裸左键拖选 → 松手 → 提取屏幕字形 → 写剪贴板。提取链路是好的；写出去的那一步只有
**OSC 52** 一条通路（`run.rs::write_clipboard` 只发 `ESC ] 52 ; c ; <b64> BEL`）。

OSC 52 的覆盖面比它看起来窄：

- **VS Code 集成终端不实现它**（xterm.js 至今没有写剪贴板的实现）。本仓的主要使用场景正是它
  —— ADR-0051 的整个动机就是「VS Code + macOS 上连 `⇧`+拖选都没有」。
- 不少独立终端默认**关掉**它（防恶意程序写剪贴板），且失败**完全静默**：写入是单向的，没有应答可等。

于是同一份代码在三类环境里的表现是：能粘 / 粘不出来 / 不知道有没有成功。用户看到的就是
「拷贝不好用」。

### 2. 输入框没有任何选区概念

`InputBuffer` 只有 `text` + `cursor`，编辑原语（`backspace` / `delete_forward` / `insert_char`）
都只作用于一个 char。要「选中全部再删掉」只能按住退格 —— 长草稿上这是纯粹的浪费。

## 决策

### 1. 剪贴板写入**双发**：本机工具 + OSC 52

`write_clipboard` 变成两个动作的组合：

1. `write_system_clipboard`：按序试 `wl-copy`（仅 `WAYLAND_DISPLAY` 非空时置顶）/ `xsel` /
   `xclip` / `pbcopy` / `wl-copy` / `clip.exe`，**命中即返回**，把文本写进子进程 stdin 后立即关掉。
2. 仍然发 OSC 52（保留给 SSH / 容器 / tmux 这类没有本机工具的环境）。

**为什么不是二选一**：两条路的失败都是静默的，而「终端到底支不支持 OSC 52」这个信息**拿不到**
（无应答可等）。分头探测做不到，只能都发 —— 成功的那个生效，失败的无声无息。这不是兜底，
是**两个正交的投递目标**：本机工具写的是操作系统剪贴板（任何 app 都能粘），OSC 52 写的是
**终端自己**的剪贴板（能穿过 SSH）。

**为什么用命令行工具而不是剪贴板 crate**：要多一个 crate 换取 5 个平台各一份实现，而本节新增的
全部代码是 3 个函数、约 60 行、零依赖。子进程的启动成本落在**复制**这个低频动作上，不在帧路径。

**`xsel` 的特殊性**：X11 的 selection 语义要求**拥有者是个活进程**。`xsel` 写完 stdin 之后不会
自己退出（它要一直持有 selection），故这里**不 wait、不 kill** —— 让它后台挂着，下一次复制时新的
`xsel` 接管 selection，旧的自动退出。反过来，**stdin 必须关**（drop），否则它永远等不到 EOF。

### 2. 输入框有选区，且 `anchor` 和 `cursor` 平级

`InputBuffer` 新增 `anchor: Option<usize>`（char 索引，与 `cursor` 同不动点）。选 **两个端点 +
用时归一化**，不存 `head`/`tail`：与 `selection.rs` 的 Chat 选区同口径，且反向选区（锚点在右）
自动正确 —— 右移会缩小它。

**承重的约束**：`anchor.is_some()` ⇔ 有选区。端点相等时 `anchor = None`（`settle()` 的唯一职责），
不留「零宽选区」这个第三态 —— 否则每个编辑原语都要多一个分支，而那个状态没有任何可观测含义。

**所有删文本/整体改写的原语先 `take_selection()`**：`backspace` / `delete_forward` /
`insert_char` / `insert_str` / `complete_leading_token` / `clear` / `take`。这条是硬约束，
变异测试逐个注入过（漏一个 ⇒ 退格会删掉用户没在看着的内容）。

### 3. 键位：`Ctrl+Shift+A` 全选，**不动** `Ctrl+A`

| 键 | 行为 |
|---|---|
| `Ctrl+Shift+A` | 全选输入框 |
| `Ctrl+A` / `Ctrl+E` | 行首 / 行尾（readline 语义**保持不变**） |
| `Shift` + `←→↑↓ Home End` | 扩选（锚点钉在移动前的位置，连按不漂移） |
| `Ctrl+C` | **有选区 ⇒ 复制**；无选区 ⇒ 原两段式「取消回合 / 退出」 |
| `Backspace` / `Delete` / 打字、粘贴 | 有选区 ⇒ 替换整段 |

**为什么全选不占 `Ctrl+A`**：`Ctrl+A` 在终端里是 readline 的 `beginning-of-line`，绑了二十多年；
把它改义会让「跳到行首」这个高频操作凭空消失，而全选是低频操作。`Ctrl+Shift+A` 是有代价的
——**多数终端把 `Ctrl+Shift+字母` 发成同一个控制字符**，此时它退化成与 `Ctrl+A` 同义（行首），
全选按不出来。本仓开了 `DISAMBIGUATE_ESCAPE_CODES`，支持的终端会发 `CSI 97;6u`，**能区分**。
两档行为都自洽：退化时只是「这个键没有新功能」，不是「按错」。

**为什么 `Ctrl+C` 要看有没有选区**：GUI 输入框的肌肉记忆是「选中 → Ctrl+C 复制」。在有选区的
时候直接退出/取消，一次手滑就丢掉半屏输出。无选区时行为**完全不变**（取消 / 两段式退出），
所以退出路径没变弱：`Ctrl+D`、`Esc`、再按一次 `Ctrl+C`（回合中）都还在。

### 4. `↑` / `↓` 先归输入光标，到边界才回落

裸 `↑` 现在的顺序是：**输入框按视觉行上移 → （到首行）输入历史 → （历史空）聊天滚动**。
`↓` 对称：**输入框下移 → （浏览态内）下一条历史 → （到底）聊天滚动**。

**为什么反转 ADR-0045 的 `↑` 归历史**：输入框会**软换行**（`wrap_input`，长草稿折成多行），
此时 `↑` 是编辑操作 —— 用户想回到上一行改字，而拿到的却是「上一整条消息替换掉草稿」。
「多行输入框里 ↑ 跳历史」是单行输入框时代的约定，软换行让它变成陷阱。

**代价（明确接受）**：`↑` 不再是无条件的「取回历史」。历史仍在，只是要多按几下（到首行之后）。
`PageUp` / `PageDown` / `Ctrl+↑` / `Ctrl+↓` 都不受影响。

**宽度从哪来**：缓冲层**不猜**折行宽度（那是 UI 属性，随 resize 变）。`ui_with` 每帧把
`input_inner_width` 写进 `InputBuffer::wrap_width`；宽度未知时 `up()` / `down()` 返回 `false`
⇒ 直接回落历史/滚动。**猜错一次就是「按 ↑ 跳到错误位置」**，比明确不动更坏。

### 5. 键位表结构化，新增 `/keybind`

键位原先只是 `commands.rs` 里的一个字符串常量 `KEY_HELP`，只经 `/help` 露出。两个后果：

1. **它必然漂移**。本轮把 `End` 改成输入行尾、`↑` 改成先归输入光标，而那段字符串不在
   任何编译期或测试期的约束里 —— 改了实现、文案照旧，用户看到的是错的手册。
2. **它无处安放**。二十条键位塞进 `/help` 会把「要查哪条命令」挤出屏幕；而键位是
   「试不出来就等于没有」的信息，需要一个能整屏读完的出口。

于是：键位改成结构化数据 `KeyBinding { keys, action, group, note }`，真源唯一
（`all_keybindings()`），两个出口从它**派生**：

- **`/keybind`**：完整表，按 `KeyGroup` 分段（输入编辑 / 提交与退出 / 滚动与跳转 /
  剪贴板 / 鼠标），键列按**显示宽度**对齐（CJK 占 2 列），注意事项单独续行。
- **`/help`**：命令索引 + 一段高频摘要（`KEY_HELP_BRIEF`），结尾指向 `/keybind`。

**为什么保留摘要而不是让 `/help` 只指向 `/keybind`**：`/help` 是发现入口，用户不知道
有 `Esc` / `Tab` 这类键时不会去查表；摘要覆盖「不知道就卡住」的那几条。

`note` 字段的存在理由是**别把「终端做不到」写成「本仓不支持」**：`Ctrl+Shift+A`
在多数终端被压成 `Ctrl+A`，那是终端行为而非设计缺陷，必须写在旁边。

### 6. 裸 `End` 归输入行尾（与 `Home` 对称）

ADR-0045 把 `End` 留给「跳到最新消息」，`Home` 给输入行首 —— 这一对**刻意不对称**。实际用起来
不对称本身就是成本：`Home` / `End` 是同一组肌肉记忆，一个改输入、一个滚聊天，每次都要想。
现在两者都归输入框，聊天导航统一走 `Ctrl` 修饰的那组（`Ctrl+End` / `Ctrl+↓`）——
同一载荷、键更明确，且「跳到最新」本来就是「回合结束后回到现场」的高频动作，值得一个不会被
误触的组合键。

## 代价

- **`Ctrl+Shift+A` 在部分终端不可用**（退化成 `Ctrl+A`）。`Shift+↑↓` 与 `Ctrl+End` 是替代路径。
- **`↑` 取历史的路径变长**：输入框多行/软折行时要先回到首行。
- **`End` 改义**：ADR-0045 的键位表与 `/help` 那段需要重写（本次一并做了）。
- **多进程**：每次复制起一个短命子进程；`xsel` 会**留着不退**（X11 selection 语义决定的，
  不是泄漏 —— 下次复制接管后自己退出）。
- **选区只覆盖输入框与 Chat 两个独立的层**：两者不能跨选（输入框与对话是不同的 buffer），
  也没有双击选词 / 三击选行（同 ADR-0051 的口径）。

## Considered Options

### A. 只加本机工具，删掉 OSC 52

- 否决理由：SSH / 容器 / tmux 里**没有本机工具**，那正是 OSC 52 唯一覆盖而工具覆盖不到的场景。
  删掉等于把「远程能用」换成「本地更可靠」，是交换不是改进。

### B. 探测一次终端能力（`DA1` / `XTGETTCAP`）再决定发不发

- 否决理由：写剪贴板**没有应答**，这些查询问的是「终端名/能力」，返回里没有「支持 OSC 52 写」
  这一项；而 xterm.js 这类终端**会声称支持**却什么都不做。探测带来的是新的失败面（终端不答 ⇒
  卡在超时），收益为零。

### C. `Ctrl+A` 改义为全选（macOS 习惯）

- 否决理由：丢 readline 的 `beginning-of-line`。而且本仓已有 `Ctrl+E`（行尾）与它配对，
  拆掉这一对会让 `Ctrl+A/E` 的对称性消失。

### D. 输入框选区存 `(head, tail)`（归一化后）

- 否决理由：`cursor` 本来就是光标唯一真值；再存一个归一化的 `head` 就要求两者在**所有**编辑原语里
  同步，而反向选区（锚点在右、光标左移）每次都要重算。存两个端点 + `selection()` 归一化，
  便宜且没有第二份真值。

### E. `↑` 保持不变（无条件取历史），另给一个「多行输入里上移」的键

- 否决理由：多一个键去避开已有键的歧义，是把复杂度推给用户。软换行下 `↑` 的自然含义就是
  「上一行」；历史动作还有 `PageUp` / `Ctrl+↑` 两条路。

| 渲染（高亮落在正确格、无选区零高亮、每帧写回 `wrap_width`） | `draw.rs` 单测 3 条 |
