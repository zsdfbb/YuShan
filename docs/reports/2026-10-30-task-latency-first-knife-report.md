# 任务延迟第一刀（A1–A7）实测报告：轮数、工具形态与失效的判据

- **日期**：2026-10-30
- **性质**：**实测记录**。本文只报告读数与归因，不改代码、不改配置。
- **被测**：第一刀 A1–A7（含 A3 / A4 的返工形态），代码见
  `apps/coding-agent/src/prompt.rs`、`crates/ys-loop/src/basic.rs`、
  `crates/ys-component/src/limits.rs`；设计口径见
  [`docs/design-final/task-latency-levers.md`](../design-final/task-latency-levers.md)。
- **样本限制**：每条提示 3 次 repeat，单次运行方差极大（见结论 6）。下文所有墙钟数字
  只作方向参考，**不作统计结论**。

---

## 0. 结论

1. **质量位全程无回退**：18 次运行全部保持基线水平。
2. **A5 与 A6 在本次基准里从未触发** ⇒ 对它们的有效性**没有任何证据**。
3. **A4 旧判据实测无效**：触发少、且多落在回合末尾；单调用轮占比未变。
4. **A4 新判据逻辑正确，但仍几乎没有触发空间**。
5. **A3 是唯一测出机制性改变的杠杆**：工具形态从逐个检索变为 `bash` 聚合命令，轮数下降。
6. **墙钟 −6% 不可作为结论**：3 次 repeat 分辨不了 ±50% 的单次方差。
7. **`daily/2` 的 cache 下降与 `fact/1` 上升方向不一致**，需单独排查。
8. **门禁（design §5）无法由该基准判定**：它依赖的 A5/A6 不触发，A4 几乎不触发。

## 3. 逐项结论

### 3.1 质量位无回退

18 次运行全部保持基线水平：`daily/2` 与 `fact/1` 在三条臂上均为 **Q+ ×3**；
`exp/t1` 两侧同为 **Q? ×3**（该提示本身没有可判定的完成标准，`Q?` 是基线形态）。
**没有任何一次质量退化。**

### 3.2 A5 与 A6 从未触发

| 项 | 阈值 | 实测 |
|---|---|---|
| A5 压缩 | 170k 输入 | 压缩事件 **0 次**；输入中位 20–33k |
| A6 轮数软提醒 | 60 轮 | 最长回合 **24 轮** |

**因此对这两项的有效性没有任何证据**，既未证明有效也未证明无效。A5 的主要收益是 token，
而本基准不测 token（只看轮数 / 墙钟 / cache）。A6 的触发条件在短任务上根本达不到。

### 3.3 A4 旧判据实测无效

旧判据是「连续 N 轮只有 1 个工具调用」，阈值 4，到阈值即触发。

- 10 次运行中只触发 **4 次**，其中 **3 次落在回合最后 1–2 轮**（此时提醒改变不了任何东西）；
- 单调用轮占比 **49% → 51%**，未变；
- 根因：**「连续」计数会被中间任一多调用轮清零**。实测轮序列形如
  `1 1 2 1 1 1 1 1 1 0` —— 一个 2 调用轮就把前面的积累全部作废。

### 3.4 A4 新判据逻辑正确但仍无空间

新判据（`advance_batch_nudge`，`crates/ys-loop/src/basic.rs:90-108`）：回合内**累计**调用数、
阈值 **12**，且仅当 `tpr < 1.5` 才触发并翻倍。

- 6 次运行只触发 **1 次**（第 12 轮 / 共 14 轮）；
- 其余被 `tpr >= 1.5` 正确抑制（`fact/1` 的 tpr 为 1.60 / 1.69），或累计不足 12
  （`daily/2` 仅 3–7 次调用）。

判据本身工作正常，但**基准任务的回合太短**，A4 没有发挥空间。

### 3.5 A3 是唯一测出机制性改变的杠杆

工具形态发生了可观察的转变：

- 从 `grep → grep → read/read → bash ×N` 的逐个检索，变为**几乎全是 `bash` + `rg`/`for`/`sed`
  的聚合命令**；
- `fact/1` 三次运行分别 16 / 13 / 20 次调用，其中 `read` + `grep` 合计**仅出现 2 次**；
- `daily/2` 轮数中位 **10 → 6**。

这与 A3 的意图一致：把多轮取数压成一条命令，减少模型往返。**这是本期唯一测出机制性改变的
杠杆。**

### 3.6 墙钟 −6% 不可作为结论

单次运行方差达 **±50%**：

- `fact/1` 基线 86–226 s；
- `daily/2` 轮数 6–24。

3 次 repeat 无法分辨该量级的差异。**可信的是轮数与工具形态，不是墙钟。**

### 3.7 cache 方向不一致

- `daily/2` 从 88% 降到 78%；
- `fact/1` 反而从 84% 升到 91%。

两个提示方向相反，不能归因于同一改动，需后续单独排查（可能与聚合命令一次性读入更多上下文、
以及不同回合长度下的缓存命中结构有关，但本报告不作断言）。

### 3.8 门禁无法判定

design §5 的门禁判据依赖 A5/A6 的触发与 A4 的覆盖，而：

- A5/A6 在基准任务上**不触发**；
- A4 几乎不触发。

**该基准测不了这三项。** 需要长程提示，或按 design §9.2 用真实长会话的 `run_reading`
做跨会话对比。

## 4. grep 截断提示修复

### 4.1 现象

`e2e_bench` 的 `daily/2` 实测中，模型这样用 grep：

```text
[r1] grep {"pattern": "is_concurrency_safe"}
[r2] grep {"pattern": "is_concurrency_safe", "limit": 200}
```

`r2` 相对 `r1` 只改了 `limit`，是一次**白烧的往返**：`r1` 已触达字节上限，
`r2` 一条也多拿不到。

### 4.2 根因数据

| 项 | 值 | 出处 |
|---|---|---|
| 命中总数 | 129 条 | 全仓 `is_concurrency_safe` |
| 命中总字节 | 26,292 字节 | `rg --json` 渲染形态 |
| 单条结果字节预算 | `16 * 1024`（16 KiB） | `GREP_MAX_RESULT_BYTES`，`adapters/tools-basic/src/grep.rs:55` |
| 预算用尽位置 | 第 77 条命中 | `Truncated 52 lines, showing first 77`（129 − 77 = 52） |
| 默认条数上限 | 100 | `DEFAULT_LIMIT`，`grep.rs:46` |

16 KiB 预算**先于** `limit=100` 用尽：`limit=100` 已超过预算能装下的条数，
`limit=200` 不会多返回任何内容。旧实现在字节截断时仍走 `limit_reached` 分支，
于是同时输出两条互相矛盾的 notice。

### 4.3 notice 文本对照（逐字）

旧（字节截断时两条并存，第一条是错误建议）：

```text
100 matches limit reached. Use limit=200 for more
Truncated 52 lines, showing first 77. Narrow the search (smaller context, tighter pattern/path, or add a `glob`) to see the rest
```

新（字节截断时不再出现 `Use limit=…`，合并为一条报总数 + 收窄指引；
`Truncated …` 收窄 notice 仍同向保留）：

```text
129 matches found; showing the first 77 lines (output capped at 16 KiB). Raising `limit` will not return more — narrow with `glob`, `path`, or a tighter `pattern`.
Truncated 52 lines, showing first 77. Narrow the search (smaller context, tighter pattern/path, or add a `glob`) to see the rest
```

仅 limit 触发（总字节远小于 16 KiB）时，加大 limit 是**正确**建议，保留并前置总数
（`build_result` 的 `else if limit_reached` 分支，`grep.rs:325-331`；示意取自回归用例）：

```text
3 matches found; showing 2. Use limit=4 for more
```

总数由 `render_entries`（`grep.rs:591-649`）在丢弃 limit 之外的命中**之前**统计
（`:596`），故两种形态都能报出真实总数。

### 4.4 为什么不调大默认 limit

- 瓶颈是 `GREP_MAX_RESULT_BYTES`（16 KiB），不是条数：129 条 / 26,292 字节的命中在
  第 77 条处已把预算用尽；
- `limit=100` 已经大于能装下的条数，调到 200 不会多返回一个字节；
- 调大默认值只会让每次 grep 的**上限**更高，在真正触发 limit 的小结果上增加 token，
  对这里的大结果没有任何收益。

正确的降载手段是收窄搜索面（`glob` / `path` / 更紧的 `pattern`），这也正是新合并
notice 给出的唯一建议。

### 4.5 效果可测性

**该修复在当前基准上的效果不可测。** 新提示词（A3）让模型改用 `bash` + `rg`：
3 次 `daily/2` 运行里 grep 工具只出现 **1 次**，结构化 grep 已不是主通道。因此本基准
无法给出「修复前后轮数差」的读数；该修复的收益应记为**消除一个已观测到的错误建议**，
而不是可量化的墙钟或轮数改进。
