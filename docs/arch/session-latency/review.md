## R2 详析 —— B2 的因果假设被实测推翻

**设计假设**：「压缩后回弹的主因是**保留段构成**（`kept` 4 vs 40 差异明显）⇒ 需 B2 可观测来定位」。

**实测（压缩后首轮的实际 `input_tokens` vs 事件里的 `estimated_tokens_after`）**：

| 回合 | `est_after` | **实际 input** | 差值 |
|---:|---:|---:|---:|
| 7 | 8,389 | 18,314 | **+9,925** |
| 11 | 12,657 | 21,442 | **+8,785** |
| 12 | 11,410 | 20,971 | **+9,561** |
| 15 | 12,723 | 22,557 | **+9,834** |
| 16 | 10,439 | 20,766 | **+10,327** |
| 16 | 12,016 | 22,392 | **+10,376** |
| 19 | 12,138 | 23,796 | **+11,658** |
| 21 | 15,363 | 26,485 | **+11,122** |

⇒ **8 次压缩的低估量高度一致：+8,785 ~ +11,658**（均值约 **+10,260**）。
这**不是**「保留段构成」的问题 —— 是**每次请求都要重发、却既不在会话里也不参与压缩的那部分**
（system prompt + 工具表 + skill 目录）。

**关键**：这个量**已经在代码里存在**（`RunLimits.fixed_prompt_tokens`），且**已经参与触发判定**
（`basic.rs:226`）⇒ **压缩的「该不该触发」判对了，但「压完还剩多少」的口径没算固定开销**
⇒ `ContextCompacted.estimated_tokens_after` **系统性低估约 10k**。

⇒ **这才是回弹的真实机理**：
```
压缩后真实占用 = estimated_tokens_after + fixed(≈10k) = 20k~26k
    ↓ 但保留预算 keep_budget(128k × 0.10) = 12,800
保留段按 12.8k 切 ⇒ 加上固定开销后真实占用 ~23k
    ↓ 之后每轮回涨 ⇒ 40 轮后回到 90k
```

⇒ **B2 应改为**：
1. `estimated_tokens_after`（及 `before`）**计入 `fixed_prompt_tokens`** ⇒ 事件数字与真实占用同口径；
2. `keep_budget` 的切分**是否该把固定开销算在预算内**（当前**不算** ⇒ 压完真实占用必然超预算）——
   这是**算法口径问题**，需设计决策；
3. 保留段构成仍值得观测（B2 原意），但它是**次要**因素，**不是主因**。

## 改进建议

### 易修复（低风险快速改进）

1. **修正 B1**：从「补 `TokenLedger`」改为「**`estimated_tokens_before/after` 计入 `fixed_prompt_tokens`**」。
   改动面：`crates/ys-loop/src/compact.rs:231,259`（两行）+ `crates/ys-event/src/event.rs:83-92` 的 doc 注释。
   **收益实测**：让压缩后的数字与真实占用同口径 ⇒ 可直接看出「压完还剩多少」。
2. **修正 B2**：把「保留段构成可观测」降为**次要**，主项改为「`keep_budget` 是否含固定开销」的算法口径决策。
3. **修正 C3**：复用 `bash.rs:213` 的 `redundant_root_cd()`，**只加剥离动作**，不重写判定。
4. **修正 C4**：`bash_bg` 已存在 ⇒ C4 降级为「**guideline 引导**」（`prompt.rs` 提示构建/测试用 `bash_bg`），
   代码工作量 ≈ 0。
5. **修正文档**：`docs/design-final/compaction.md` §已知遗留 1 说「估算器未与真实 usage 对账，
   且不计 system prompt / 工具表（系统性低估）」⇒ **前半句已过时**（`fixed_prompt_tokens` 已落地并接入判定），
   **后半句只对「事件口径」成立**。该文件带 `[已关闭]` 标记约定，需按规范更新。
6. **修正收益估算**：§4.2 的 −2.0 h 中 **B1 的 −10~20 min 不成立** ⇒ 调整到 **−1.7 h**；
   且 G1「降 30%+」的达成**从「单靠 B1」改为「靠 D1+C4+B3 合计」**（见下）。

### 需讨论（需要决策）

7. **`keep_budget` 是否含固定开销**（R2 的算法口径问题）：
   - 方案 i：不含（现状）⇒ 压完真实占用 = keep + fixed，**必然超预算**；
   - 方案 ii：含 ⇒ 切分时先扣掉 fixed，保留段更小 ⇒ 压完真实占用 ≈ keep_budget。
   ⇒ **这是设计决策，不是实现细节**，需明确后写进 ADR。
8. **D1 的形态**（R4）：`bash_bg` 与 subagent **不同构**（进程组 vs 独立 Agent）⇒
   需定：`SubagentHandle` 的存储（进程内 `Arc<Mutex>` vs 落盘）、失败/取消/泄漏三条路径、
   以及「父回合继续做什么」的语义。
9. **C1/C2 与 guideline 的同批改动**（R7）：`cost-model.md` §8.3 已证**只改一处反而更糟**
   （11→15 轮）⇒ C1/C2 必须与 `prompt.rs` 的 guideline **同批改**，不能分两次发布。
10. **第三期的拆分**（R5）：建议 C1+C2+C3 一批（工具形态 + guideline），
    C4+C5+D1 一批（异步化）。理由：C5 依赖 C1/C2（只读工具变多才有分段的意义），
    C4 与 D1 都是「让重活不占回合」，同一批可共用验收口径。

### 架构级（影响面大，需跨 phase 规划）

11. **D2（subagent 工具表约束）**：本轮已记入 `docs/TODO.md`，需独立 `arch-design`。
    涉及 D20（缓存相干性）+ 前缀指纹锚 + D15（提示词不可见 + 执行时拒绝）双实现。
12. **PTC**：已记入 `docs/TODO.md`，**触发条件**已写明（上层给出执行边界）。
13. **轮数差距的正面处理**：`cost-model.md` §7 的 codex 对照（6 轮 vs 33 轮）是本设计**未覆盖**的最大差距。
    本设计的 13 条措施**全部不直接针对它**（它们降的是「每轮成本」和「工具形态」）⇒
    ⇒ **诚实的结论**：本设计能显著降低「每轮成本」，但**不能把轮数降到 codex 水平**。
    ⇒ 若 G1 达成不了，**下一个战场是 PTC 或 guidance 层的轮数控制**，
    不在本设计范围内。这点应写进 ADR 的「未决」。

## 总体评价

**整体健康度：中上。设计方向正确，但存在 3 处「把已实现的东西当待做」的事实错误**——
这些不是笔误，而是**文档与代码脱节**的产物：`design-final/compaction.md` 的「遗留 1」未随
`fixed_prompt_tokens` 落地而更新，导致本设计基于一份过时文档立项。

**最大风险**：R2（回弹主因判断错）与 R3（`ToolSpec` 扩展破前缀指纹锚）。
前者会让第二期做无用功，后者会破坏已建立的缓存相干性（D20 指出 DeepSeek 缓存 TTL 数小时~数天，
破坏前缀 = 每 72 小时重付 18.1k token）。

**可执行的部分**：13 条中 **8 条成立**（A1/A2/B3/B4/C1/C2/C5/O1），
**3 条需改口径**（B1/B2/C3），**2 条降级为引导或需重新定形态**（C4/D1）。
⇒ **修订后仍是一个可执行的计划**，且**第一期与第二期的绝大部分不受影响**。

**推荐下一步**：
1. **先修订设计**（P0 项：R1/R2/R3 + 文档过时条目）—— **半天内可完成**；
2. **第一期照原样执行**（A1 + A2 + O1）—— 零代码风险，且 A2 的离线验证**零成本**；
3. **第二期开跑前**先定「`keep_budget` 是否含固定开销」（R2 的设计决策），
   否则 B2/B3 的验收口径会写错；
4. **第三期先做 C1+C2+C3 一批**（含 guideline 同步改），D1 单独走一轮设计（生命周期复杂度最高）。

**一句话**：**方向对、依据实，但落地清单有 5 处需先修**；
修完即可按三期执行，第一期可立即开始。
