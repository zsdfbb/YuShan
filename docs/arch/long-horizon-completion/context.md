## 概述

一句话：在 YuShan 里，**「任务完成」不是一个概念——只有「回合完成」**。而回合完成的默认含义是
「模型这一轮没再调工具」（`basic.rs:408`）。本文探索：这个判据在长程任务上为什么失效，以及要补的是什么。

---

## 1. 关键发现（先行）

### 1.1 「完成」今天只有一个判据：模型自己停止调工具

`StopReason` 共四态（`crates/ys-core/src/stop.rs`）：`Completed` / `MaxRounds` / `Cancelled` / `Truncated`。
其中**只有 `Completed` 表示「到达完成」**，它只在 `BasicLoop` 拿到「模型本轮无 tool call」时发出（`crates/ys-loop/src/basic.rs:408-416`）。

> ⇒ 这是**唯一**的完成信号，且是**模型自觉**，**零验证**。其余三态全是「**没到达完成**」。

### 1.2 回合边界是一堵死墙（`app_loop`）

- `app_loop` 的 `Request::Prompt` 臂**恰好一个回合**（`apps/coding-agent/src/app_loop.rs:114`）。
- 回合结果的 `match` **不看 `stop_reason`**（`app_loop.rs:186-196`）：`Ok` ⇒ 记 usage；`Err` ⇒ 落日志。
  **撞 `MaxRounds` 与正常 `Completed` 走同一条路**，随后回到 `request_rx.recv().await` 等用户下一条输入。
- ⇒ 无论回合是「完成」还是「撞墙」，`app_loop` 之后的行为**完全一样：等下一条输入**。
  边界不是闸门（有判据可开），是**墙**（一律终止）。

### 1.3 单回合预算写死 10，不可配

- `crates/ys-component/src/limits.rs:39` — `max_rounds: 10`，判定在 `basic.rs:115`，撞顶时
  `RunResult { stop_reason: MaxRounds, final_message: None, .. }`（`basic.rs:126-131`）——**无收尾机会**。
- **在 coding-agent 无任何覆盖路径**：`resolve_limits()`（`apps/coding-agent/src/main.rs:361`）只写
  `context_window` 与 `compaction`；`config.json` 无 `max_rounds` 段；无环境变量、无 CLI flag（全仓确认）。
- ⇒ 例子里的「⚠ 10 rounds」是**够不到**的硬天花板。

### 1.4 一次性入口根本没有多回合

`-p` / `--json` 走 `run_single_turn`（`main.rs:714-724`）：`begin_turn(1)` + **一次** `run_turn`，随后退出。
⇒ 长程任务在 `-p` 下 **100% 烂尾**，连「手动再发一条」都没有。

### 1.5 ⚠️ ADR-0024 的闭环**盖不住这个例子**（本轮最重要的新发现）

- ADR-0024 决策 3 明确：追问的触发前提是**计划的有无**——
  > 「本设计的触发前提是用户自己的计划——模型不写计划 ⇒ `NoPlan` ⇒ **永不追问**。」
- 而例子里的 `/arch-explore` 是**探索型任务**：全程**没有写 todo**。
  ⇒ **即使 ADR-0024 全部落地，该回合依然在 10 轮处切断、依然不追问、依然烂尾。**

> ⇒ **todo 型闭环（0024）解的是「有明确清单的长任务」；例子暴露的是「无清单的长任务」。两者的完成判据不同。**
> 这是本文与 `long-horizon-todo` 的分水岭，也是把「长程能否完成」再走一遍的理由。

### 1.6 ⚠️ `MaxRounds` 是**唯一**的回合内防失控机制——另一个是空的

决定「`max_rounds` 设极大 / 不设」之前必须知道：**今天回合内只有一条防线，且它是死的**。

- `MAX_CONSECUTIVE_ERRORS = 3`（`basic.rs:14`）看似是「同一工具连续错 3 次就停」，但
  **它的分支体是空的**（`basic.rs:517-520`：只有一句注释「继续循环…模型应看到反复出现的错误并停止」）。
  ⇒ **这是一个已记录、但未生效的守卫**：计数照涨，行为为零。
- 于是回合的终点只剩四种（§2.2），其中**能主动刹住「模型原地打转」的只有 `MaxRounds`**。
- **`-p` / `--json` 连中止都没有**：`run_single_turn` **不传 `boundary`**（`main.rs:715` 注释自陈
  「一次性模式没有中途插话/中止的 UI 入口」）⇒ 一次性模式下**既无轮数上限、又无 Abort**。

> ⇒ **把 `max_rounds` 设成极大，等于 TUI 只剩「Ctrl+C」这一条人工兜底，`-p` 想停只能杀进程。**
> 这不是反对——长任务的正确形态本就该是「跑到模型自己停」，人工 Ctrl+C 是合理兜底——
> 但**「可配置 + 极大默认」比「删掉检查」更稳**：机制留着当日后的安全阀（如 CI / headless 场景设一个界），
> 默认又足以让长任务跑完（见 §7 已澄清）。

## 2. 现有架构

### 2.1 三级控制流（判据：**是否另起一个新回合**）＋ as-built 状态

| 层级 | 定义 | 位置 | 增回合数 | 实现状态 |
|---|---|---|---|---|
| **轮**（Round） | 回合内一次「模型调用 +（可能的）工具执行」 | `basic.rs` `loop`（`:93`） | 否 | ✅ |
| **回合**（Turn） | 一次输入 → 一个最终回答 | `run_turn`（`basic.rs:48`） | 否 | ✅ |
| **压缩**（Compaction） | 轮边界的上下文家务 | Step 4b（`basic.rs:134`） | 否 | ✅ |
| **追问**（Follow-up） | **回合之间**、**系统**发起 | `app_loop`（设计稿 `2026-09-15-follow-up.md:49-63`） | **是** | ❌ **未实现** |

`app_loop` 的 `Request::Prompt` 臂今天**就是一个回合**；follow-up 的设计是把它包进
`while let Some(msg) = pending.take()` 循环——**这是闭环唯一已设计好的落点**（`follow-up.md:55-63`）。

### 2.2 「完成」的四条出路

| StopReason | 触发点 | 含义 | 算「完成」吗 |
|---|---|---|---|
| `Completed` | 模型本轮无 tool call（`basic.rs:408`） | 模型自称做完 | **是**（唯一的正面信号） |
| `MaxRounds` | `rounds >= max_rounds`（`basic.rs:115`） | 预算耗尽 | **否**——且 `final_message: None`，无收尾 |
| `Truncated` | provider `finish_reason = length`（`basic.rs:334`） | 输出被截断 | **否**（ADR-0020 诚实终止） |
| `Cancelled` | 轮边界 `Boundary::Abort`（`basic.rs:95`） | 用户中止 | **否**（用户永远赢） |

> 另有每工具 **300s** 硬超时（`basic.rs:470`，`bash_timeout.unwrap_or(300)`）——长任务里单个卡住的命令会被此兜住，
> 与回合预算正交。

### 2.3 状态活多久

- **会话**落盘 JSONL，跨进程可 `--resume`（ADR-0026）⇒ 历史能活。
- **计划**只活在对话里，压缩一摘就没（`long-horizon-todo/context.md` §3.3）。
- 今天真正「活过压缩」的「下一步」形态 = 压缩摘要里的 `## Next Steps` **散文**（无类型，`compact.rs:92-110`）。

### 2.4 外部依赖

无新增。全部能力已在 `ys-loop` / `ys-component` / `apps/coding-agent` 内。

## 4. 需求范围

### 范围内（本轮应回答）

1. **「完成」的定义与判据**——何时算一个长任务做完？（§5 Q1）
2. **无清单长任务撞 `MaxRounds` 后如何不烂尾**——本例正落在此格（§5 Q2）。
3. **单回合预算的定位**——硬顶 / 可配 / 软顶 + 有界续跑（§5 Q3）。

### 范围外（明确不做）

- **todo 本身的落点**——ADR-0024 已定（真值落 `<stem>.todo.json`、回合边界注入、删除判据 = 无 open 项）。
- **subagent 形态**——ADR-0022 已定。
- **模型调用重试 / 429 处理**、**`/compact` 命令的占位**——独立缺口（truncation-guard / capabilities 各已列）。

### 关键场景

| # | 场景 | 今天会发生什么 | 0024 落地后会怎样 |
|---|---|---|---|
| **S1** | 「把这 12 个文件里的 API 用法统一」（模型写了 todo） | 一个回合做完，或撞 `MaxRounds` 烂尾 | ✅ 覆盖：有未完成项 ⇒ 追问续跑 |
| **S2** | **「对照 Pi 找出差距」**（探索型，**不写 todo** —— 即本例） | 撞 `MaxRounds` 烂尾，无收尾 | ❌ **仍烂尾**（`NoPlan ⇒ 永不追问`） |
| **S3** | 单回合跑到 10 轮但任务还差一步 | `final_message: None`，用户拿到半截流 | ❌ 未覆盖（同上，无清单） |
| **S4** | `-p "长任务"` 一次性模式 | `run_single_turn` 跑一轮即退出 | ❌ 未覆盖（`-p` 不走 `app_loop`） |
| **S5** | 用户 Ctrl+C 后想「接着上次」 | `Abort` 生效、`Cancelled`；`--resume` 可续历史，但**计划在压缩里可能已丢** | 部分（todo 落盘后更稳） |

### 异常 / 边界

- **预算与成本**：调大 `max_rounds` 不改变**每轮**成本（缓存命中下增量小），但改变**回合总成本上限**——
  一个失控的长回合会连续烧 R 轮。硬天花板因此仍有必要。
- **无清单 = 无终止判据**：探索型任务的「做完了」只有模型自己知道（§1.1），代码无从判定 ⇒ 续跑只能有界。
- **`-p` 与 TUI 的分叉**：`app_loop` 与 `run_single_turn` 是两条驱动路径，任何续跑机制要么都覆盖、要么明确放弃 `-p`。

## 6. 后续建议

**三项裁决已收敛出两条改动，都在 `app_loop` 层，零 `BasicLoop` 改动**（§3 的「最高爆炸半径」约束天然满足）：

| # | 改动 | 落点 | 体量 |
|---|---|---|---|
| **① 放开单回合预算** | `max_rounds` 可配 + 默认极大 | `resolve_limits()`（`main.rs:361`）+ `config.rs` | 极小 |
| **② 完工复核** | `Completed` ⇒ 发一条复核消息、另起一回合；停滞即停 | `app_loop` `Request::Prompt` 臂（`app_loop.rs:114`） | 小（照 `follow-up.md:55-63`） |

- **建议进入 `arch-design`**：把 ① ② 定稿（含 §7 Q1 的四个「待定」——复核措辞、UI 呈现、计数上限、与 todo 判据的优先级）。
- **建议先用 `prototype` 验证**（便宜且高价值）：
  1. **① 是否足够**——用现有 e2e 复跑 `/arch-explore` 形态（10 轮 → 极大），看它跑到第几轮自然 `Completed`、触发几次压缩；
  2. **② 的「停滞判据」是否真的停得住**——模型在下一次复核里是否真会「不调工具地确认完工」（而非每轮找活）；
     这是 `MAX_CHECKS` 取 1 还是 3 的实测依据。
- **不建议**动 `BasicLoop`（`notes.md` ③）。

## 7. 已澄清（第二轮，2026-10-08）

> 保留原选项（供对照），加「已定」一行。

### Q1 ★ 「完成」由谁判定？—— **已定：模型自觉 + 一道「完工复核」回合**

用户裁决原话：「**模型自觉完成，不过需要提示模型确认是否完工**——模型认为完工之后，我们再发条消息找他 check。」

| 选项 | 结论 |
|---|---|
| a. 模型自觉「我停手了」 | **采纳为基础**（`stop_reason == Completed` 即「自称完工」） |
| b. 清单全绿 | 不采纳（依赖 todo，本例无清单） |
| **c. 可验证验收** | **部分采纳、换形态**：不引入独立验证器（测/构建），而是**把复核交给模型自己**——system 再发一条「确认是否真的完工」 |
| d. 用户显式确认 | 不采纳（交互冗余） |

**机制形状（照 ADR-0014 的 follow-up seam，落 `app_loop`，零 `BasicLoop` 改动）—— 「只问一次」**：

```
回合结束（stop_reason == Completed，且本回合干过活）
    ⇒ 系统主动发一条「是否已完工 / 还需继续吗」消息，另起一个回合
    ⇒ 该复核回合无论怎么结束 —— 链到此为止（不再问第二次）
```

**为什么「只问一次」就够**：每用户输入至多多出一个复核回合 ⇒ **结构上有界**，
**不需要计数上限、不需要停滞判据**（本文上一版设的 `MAX_CHECKS` 与「停滞护栏」是为「反复追问」预备的，只问一次用不上）。

**两道门（缺一不可）**：
1. **只在 `Completed` 后问**：`Cancelled`（用户 Ctrl+C）/ `Truncated` **绝不**问——用户中止永远赢（照 ADR-0024 决策 3 护栏 ③）。
2. **只在「本回合调用过工具」时问**：否则每问一句「这函数干啥」、模型答完都要被追一句「还要继续吗」= 纯噪音。
   判据 = 本回合出现过 `ToolUse` / `ToolResult`。

**落点**：`app_loop` 的 `Request::Prompt` 臂（`app_loop.rs:114`）包成循环（照 `follow-up.md:55-63` 的
`while let Some(msg) = pending.take()`）。**不碰** `ys-loop` / `ys-runtime` / `ys-protocol`。

**待定（设计阶段）**：
- **复核消息措辞** + 纯函数性（ADR-0024 决策 2：同内容恒同字节，不得含时间戳/回合号）。
- **UI 呈现**：复核使 `Envelope.turn` +1（`follow-up.md` §6 已记为待定）；复核消息作 `UserMessage` 显示还是标注为「系统复核」。
- **模型在复核里答「还要继续」**：它接着干、再停 —— **不再问**（因「只问一次」）。接受否？
- **`-p` / `--json` 无复核**（不走 `app_loop`）——与「无闭环」同一处功能退化。
- **与将来 todo 判据的顺序**（ADR-0024 落地后）：todo 有 open 项时本不该 `Completed`；两条判据谁的优先级高待定。

### Q2 ★ 无清单的长任务怎么办？—— **已定：放开单回合预算，不靠续跑**

用户裁决原话：「**不设置 `MaxRounds`，或者可以设置的极大**」。

| 选项 | 落点 | 结论 |
|---|---|---|
| a. 逼模型先写 todo | 提示词 | **不采纳**（依赖模型遵从，仍是自觉） |
| b. `MaxRounds ⇒ 有界续跑` | `app_loop` | **不采纳**（本例由放开预算直接解决，无需新控制流） |
| **c. 调大 / 取消预算 ✅** | `resolve_limits` + `config` | **采纳**（极端形态 = 取消单回合上限） |
| d. 接受烂尾 | —— | 不采纳 |

**采纳理由（本案）**：① 长任务的正确形态是「跑到模型自己停」；② 落点最轻（一参数），不引新控制流、
不碰 `BasicLoop`；③ 直接救本例——放开后 `/arch-explore` 会继续跑到 `Completed`。

### Q3 `max_rounds` 的定位 —— **已定：保留机制、可配、默认极大**

- **保留字段与 `StopReason::MaxRounds`**（不删检查）：机制留着当**日后安全阀**（CI / headless / 长任务失控时设一个界），
  默认值取极大（或 `u32::MAX`）⇒ 行为上等于「不设」。
- **来源**：`config.json` 新增 `max_rounds` 段（照 `context_window` / `compaction` 的既有三级解析形状），
  可选加环境变量。`resolve_limits()`（`main.rs:361`）是**唯一**接线点。

> ⚠️ **代价如实（§1.6）**：默认极大后，TUI 的回合内兜底只剩 Ctrl+C；`-p` / `--json` **连 Abort 都没有**
> （`run_single_turn` 不传 `boundary`）。若日后要 headless 长任务，需同时给 `-p` 一个可配的界或中止入口。

### 9.4 48 小时需求带来的两处修订（第二轮，2026-10-08）

用户追加需求：**「需要支持 48 小时的长程任务」**，并确认**把模型调用重试纳入本轮**。这改写了 ① 与范围：

- **① 的默认值变了**：48h ≈ **3k–29k 轮**（按 6–30 s/轮，见 `design.md` §4.2）⇒ 1,000 / 10,000 **都不够**；
  而任何装得下 48h 的轮数上限都已大到**不再是阀**。⇒ **`max_rounds` 默认 `u32::MAX`（不设）**，
  真正的兜底改为 **wall-clock 预算（默认 48h，`app_loop` 计时器 → `Boundary::Abort`，零 `BasicLoop` 改动）**。
  代价如实：收场是 `Cancelled`（与 Ctrl+C 同态，靠一条 `Outbound::Output` 行区分）。
- **③ 新增，且与既有上下文冲突**：本仓 `docs/arch/llm-api-unavailable/context.md` 当时的范围外明确
  「**不做自动重试**」（需求是「报错并终止」）。48h 无人值守要求自愈 ⇒ **ADR-0028 supersede 该一条**（仅限模型调用路径），
  落**适配器**（只有它知道 HTTP 状态码；且 `ys-model` 不得引 tokio）。三条硬规则：
  **只在未吐 delta 时重试**、**按 HTTP 语义判可重试性**、**有界退避**；超时用**连接 + 流空闲**两个旋钮（非单一总超时）。
  **前置关系**：没有超时，黑洞端点会永久挂起，根本轮不到重试 ⇒ 超时与重试**成对**做。
- **决策记录**：[`../../adr/0028-model-call-retry-and-timeout.md`](../../adr/0028-model-call-retry-and-timeout.md)。
- **仍记账（不做）**：`llm-api-unavailable` 的两个**完整性缺口**（200 + 非 SSE 错误体被判成功、无 `[DONE]` 的半截流被判完整）
  —— 48h 下它们**比缺重试更危险**（静默丢工作），应尽快单独设计。
