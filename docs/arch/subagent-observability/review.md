# Subagent 执行可观测 — 架构质量分析报告

## 分析范围

- **对象**：`docs/arch/subagent-observability/design.md`（修订后版本）
- **维度**：全量（可行性 / 可维护性 / 可理解性 / 性能与可靠性）
- **来源**：design.md + 直接代码核对（`subagent.rs` / `basic.rs` / `event.rs` / `tool.rs`）

## 各维度判断

| 维度 | 判断 | 关键发现 |
|---|---|---|
| 1.1 技术可实现性 | 🟢 | 四条提醒的注入点、事件出口、文件生命周期全部有既有先例可循 |
| 1.2 依赖成熟度 | 🟢 | 零新增依赖（`serde_json` 已是 `apps` 依赖） |
| 1.3 实现周期 | 🟢 | 改动集中在 3 个文件，无跨 phase 依赖 |
| 2.1 模块边界 | 🟡 | `JournalingSink` 放 `apps` 正确；但 `ys-loop` 要发事件给「只关心子 agent 的消费者」，耦合了一层 |
| 2.2 接口稳定性 | 🟢 | `AgentEvent` 是 `#[non_exhaustive]`，外部消费者已有通配臂，破坏面是编译器指出来的少数几处 |
| 2.3 错误处理 | 🟡 | journal 写盘失败**静默忽略** ⇒「journal 存在」不可作为「有现场」的判据 |
| 2.4 并发安全 | 🟡 | 并发派发达 16，每个 sink 各持一个文件句柄；序号用 `Relaxed` 原子，唯一性够用 |
| 2.5 资源管理 | 🟡 | 无 FD 上限说明；无文件不存在的 TOCTOU 处理（见 R3） |
| 3.1 概念一致性 | 🟡 | `session` / `transcript` / `journal` 三个近义概念并存，靠文档区分 |
| 3.2 文档完整度 | 🟢 | 修订后覆盖了矛盾、上限、失败路径、Step 4/5 错位 |
| 4.1 性能模型 | 🟡 | 在 async `emit` 里做**同步写盘**，与 `debug_log` 的「独立 writer 线程」原则不一致（有量化论证） |
| 4.2 故障模式 | 🟢 | 降级路径完整：写失败静默、md 失败留 journal、崩溃留 journal |
| 4.3 可观测性 | 🟢 | 本需求就是可观测性本身 |

## 风险排序

| # | 风险 | 影响 | 可能性 | 优先级 | 说明 |
|---|---|---|---|---|---|
| R1 | **工作区已有按旧设计写好的代码** | 高 | 已发生 | **P0** | 两个 subagent 在修订前写出了 +560/−17 行，含 `JournalingSink`（`subagent.rs:617`）。它**没有**单文件上限、**没有**正文截断、且按旧设计「优雅 Abort 也留 journal」——与修订后的设计冲突 |
| R2 | journal 写盘失败静默 | 中 | 中 | P1 | 磁盘满 / 权限错时，用户以为有现场，实际空文件。至少应在诊断里标记 |
| R3 | pid 复用导致 journal 覆盖旧文件 | 中 | 低 | P1 | 文件名 `<pid>_<seq>.jsonl`，`seq` 每进程从 0 起。重启后 pid 复用 + 7 天内残留 ⇒ 若用 `create` 而非 `create_new`，会**追加到上一次运行的现场**，伪造因果 |
| R4 | 同步 IO 在 async `emit` 里 | 低 | 低 | P2 | 已量化：4 KiB 写约 10–50 µs，轮次间隔秒级。但违反既有「消费侧绝不碰文件 IO」原则 |
| R5 | 范围偏大 | 中 | 高 | P1 | 用户原始诉求是「验证软提醒有没有用」——那只需要 `AdviceInjected`（约 50 行）。journal（约 300 行）解决的是「崩了要现场」，是两个需求 |
| R6 | `AdviceInjected` 进 `--json` | 低 | 高 | P2 | 新增 tag，对兜底解析的脚本无害；对穷尽 `match` tag 的消费者会报未知值 |

## 改进建议

### 易修复（低风险快速改进）

1. **R3**：journal 用 `OpenOptions::new().create_new(true)`，失败即降级为纯内存。避免 pid 复用污染。
2. **R2**：journal 打不开时，在最终诊断里补 `journal=unavailable`，而不是完全静默。写盘中途失败则停写并置 `truncated`（与上限触顶同一路径）。
3. **补一条测试**：`journal_pid_reuse_does_not_append_to_stale_file`。

### 需讨论（需要决策）

4. **R5 拆不拆**：建议**拆成两步落地**。
   - 第一步只做 `AdviceInjected`（改动 ≈ 50 行，`ys-event` +4 处 emit + 补臂）。
   - 它单独就能回答 `subagent-budget/context.md` 未澄清问题 1。
   - journal 单独成一个需求，它的价值与软提醒无关。

   理由：用户偏好「最简、反对过度设计」。当前 560 行的实现里，约 300 行服务于用户**没提过**的崩溃排障场景。

5. **R4 要不要照 `debug_log` 起线程**：建议**不起**。会引入 channel + 生命周期管理，而收益（省 10–50 µs/轮）远低于复杂度。但应在代码注释里写明这个偏离及量化依据（design.md 已写）。

6. **R1 处置**：当前工作区代码要么按新设计返工，要么回滚重做。**不建议保留现状**——它缺上限、缺截断，等于把一个无界写盘留在派发路径上。

### 架构级

7. **`session` / `transcript` / `journal` 三概念并存**。长期看应统一术语：`session` = 可恢复状态（只有主 agent 有）、`transcript` = 事后可读的完整记录、`journal` = 崩溃现场的追加日志。建议在 `docs/CONTEXT.md` 补这三行定义，否则新人会持续混淆。

8. **`ys-loop` 发「消费者可能只关心子 agent」的事件**。`AdviceInjected` 对主 agent 也有意义（主 agent 也会收到提醒），所以当前设计没错；但要在 `event.rs` 的文档注释里写清「这是 harness 内部状态的外化，不是模型输入」，防止将来有人拿它做流程控制（违反「Event 只观察」）。

## 总体评价

**整体健康度：可用，但需返工。**

设计文档经修订后已自洽：原先的验证矩阵内部矛盾（优雅 Abort 与崩溃混为一谈）、journal 无界、md 失败销毁唯一记录、`Batch`/`FinalReport` 的阈值与轮次陷阱都已补上。

**最大风险不是设计，而是实现与设计的错位**（R1）：工作区里已有一份按旧设计写的代码，它缺少上限与截断——恰好把「写盘无界」这个本就存在的风险放大到派发路径上。

**推荐下一步**：

1. 先决定 R5（拆不拆）——这决定 300 行 journal 要不要现在做。
2. 若保留 journal，按 R1 返工 + 采纳 R2/R3。
3. 若拆，先只落 `AdviceInjected`，它能立即回答「软提醒到底触发过没有」。
